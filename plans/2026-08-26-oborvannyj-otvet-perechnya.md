# Оборванный ответ на стадии «Перечень из гранд-сметы» — дробить чанк, а не ронять задачу

## Проблема

Задачи АР1 и ОВ (перечень из гранд-сметы) упали с ошибкой
«Ответ слишком большой, разбейте выполнение на подэтапы» —
`ResponseTruncatedError` из `claude_service.call_claude`: API вернул
`stop_reason == "max_tokens"`, JSON оборван на полуслове.

Почему упирается именно перечень:

* чанк — 250 строк файла (`file_parser.chunk_rows`);
* лимит ответа — 32 000 токенов (дефолт `max_tokens`);
* ответ длиннее входа: промпт разворачивает каждую расценку в блок
  «работа + все её материалы», каждая позиция — объект из 5 полей.
  Плотные разделы (АР, ОВ) на 250 строках дают ответ больше лимита.

Ретрая нет намеренно (`_call_claude_json_with_retry`): тот же промпт упрётся
в тот же лимит и спишет деньги ещё раз. Кнопка «Повторить» по той же причине
бесполезна — стадия стартует с чекпоинта и снова спотыкается о тот же чанк.

В смете этот случай уже закрыт: `_fetch_price_chunk` и `_fix_empty_prices`
режут чанк пополам и считают половины. В стадии перечня такой обработки не
было — ошибка уходила в общий `except`, сохранялся частичный перечень и
задача помечалась ошибкой.

## Решение

Перенести приём «оборвался → делим пополам» в стадию перечня, оба входа:
xlsx и PDF. Дробление рекурсивное, до одной строки (xlsx) / одной страницы
(PDF). Дно рекурсии ничего не выдумывает: строки без ответа объявляются
потерянными позициями и попадают в предупреждение `lost_positions_warning`.

`max_tokens` не поднимаем: 64 000 токенов вывода у Sonnet 5 без стриминга
рискуют упереться в HTTP-таймаут SDK (10 мин), а вызовы перечня идут
non-streaming. Дробление дешевле и предсказуемее.

## Фазы

### [x] Фаза 1. Деление чанка по границе группы

* `file_parser.split_chunk_in_half(rows)` — режет чанк надвое по ближайшей к
  середине границе работы (строка без единицы и объёма), как это делает
  `_chunk_one_sheet`; нет границы — режет по середине; меньше двух строк —
  `None` (дно).
* `pdf_ocr_extractor.split_pdf_chunk(text)` — режет текстовый чанк по границе
  страницы («--- Страница N …»); одна страница — `None`.
* Тесты: граница не рвёт группу «работа + материалы», деление всегда
  уменьшает обе половины, дно возвращает `None`.

### [x] Фаза 2. Рекурсия в стадии перечня

* `TaskProcessor._list_grand_rows(rows, label)` — запрос по строкам чанка;
  при `ResponseTruncatedError` делит и считает половины. Лист и номера
  позиций ЛСР считаются для своей половины (`_chunk_sheet`,
  `attach_source_numbers`), поэтому дробление не путает вкладки и нумерацию.
* `TaskProcessor._list_grand_pdf_chunk(text, label)` — то же для PDF.
* Циклы `_handle_list_from_grand_xlsx` / `_handle_list_from_grand_pdf`
  зовут эти методы вместо прямого вызова ИИ.

### [x] Фаза 3. Тесты стадии

* Оборванный ответ на целом чанке → задача доходит до конца, в перечне
  позиции обеих половин.
* Дно рекурсии (одна строка, ответ всё равно оборван) → позиция не выдумана,
  её номер назван в предупреждении.
* PDF: оборванный ответ → чанк считается постранично.
* Прогон всего набора тестов бэкенда.

## Итог

Реализован целиком. Стадия перечня больше не падает на оборванном ответе:
чанк дробится пополам до тех пор, пока ответ не помещается в лимит, а то,
что не поместилось даже поштучно, называется номерами в предупреждении.
