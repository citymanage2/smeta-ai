# Anthropic API через посредника (обход геоблока с РФ-сервера)

## Проблема

Сервер на РФ-IP. Прямой вызов `api.anthropic.com` падает с
`403 {"type":"forbidden","message":"Request not allowed"}` — геоблок Anthropic по
региону на эдже Cloudflare. Это НЕ ошибка ключа (та была бы `401 authentication_error`).
С локальной машины (не-РФ egress) те же вызовы работают.

Решение: серверу нужен не-РФ выход через посредника. Код одинаков локально (прямой
доступ) и на сервере (через посредника) — вся разница только в env.

## Фазы

### [x] Фаза 1 — env-схема

`backend/app/config.py`, класс `Settings`:
- `ANTHROPIC_BASE_URL: str = ""` — endpoint посредника. Пусто → напрямую на
  `api.anthropic.com` (локалка). Задан → через посредника.
- `ANTHROPIC_PROXY_SECRET: str = ""` — только для СВОЕГО прокси, уходит заголовком
  `X-Proxy-Secret`. Агрегатору не нужен.
- `ANTHROPIC_API_KEY` — без изменений (на сервере это ключ агрегатора; локально —
  настоящий Anthropic-ключ; при своём прокси — настоящий ключ).

### [x] Фаза 2 — ленивая фабрика клиента

`backend/app/services/claude_service.py`:
- Было: модульный singleton `_client = anthropic.AsyncAnthropic(...)`, создаётся
  жадно при импорте.
- Стало: `_client: Optional[...] = None` + `_get_client()` — ленивое создание с
  кэшем в модульной переменной. Пустой `ANTHROPIC_API_KEY` → понятный `RuntimeError`.
  `base_url` и `default_headers={"X-Proxy-Secret": ...}` подставляются из env условно.
- 6 точек вызова `_client.` → `_get_client().` (messages.create ×2, batches
  create/retrieve/results/cancel). Бизнес-логика вызовов не тронута.

### [ ] Фаза 3 — выбор посредника и деплой (deploy-зависимо)

Рекомендация — СВОЙ тонкий прокси в ЕС (см. ниже). На сервере (Timeweb) выставить
env, задеплоить, прогнать один тестовый вызов.

## Разграничение окружений

| | `ANTHROPIC_API_KEY` | `ANTHROPIC_BASE_URL` | `ANTHROPIC_PROXY_SECRET` |
|---|---|---|---|
| Локально | настоящий Anthropic-ключ | пусто | пусто |
| Сервер + свой прокси | настоящий Anthropic-ключ | адрес прокси | секрет прокси |
| Сервер + агрегатор | ключ агрегатора | endpoint агрегатора | пусто |

## Выбор посредника — рекомендация: СВОЙ прокси в ЕС

Почему не агрегатор:
- **Приватность.** Трафик смет (чужие сметы, суммы контрактов) уходит третьей
  стороне, может кэшироваться/логироваться. Для внутреннего инструмента с
  коммерческими данными — риск.
- **Паритет фич.** Агрегаторы отстают по model id и параметрам. Нам нужны актуальные
  `claude-opus-4-8`, `claude-sonnet-5`, `claude-haiku-4-5` (сейчас в коде
  `claude-sonnet-4-6`), сквозной streaming и `output_config.effort` без сюрпризов.
- **Аутентификация.** Агрегатору нужен ЕГО ключ (иначе 401); свой прокси работает
  на настоящем Anthropic-ключе — ничего в биллинге не меняется.

Свой прокси = тонкий reverse-proxy на не-РФ egress (VPS в ЕС / Cloudflare Worker),
который просто форвардит на `https://api.anthropic.com`, ничего не парсит →
автоматический 100% паритет моделей, streaming и всех параметров. Защита от
открытости — проверка заголовка `X-Proxy-Secret` (для чего и добавлена
`ANTHROPIC_PROXY_SECRET`).

Приватность при первых тестах: гонять на выдуманных данных.

Если своего прокси пока нет — как временная мера подойдёт агрегатор с OpenAI-совместимым
Anthropic-endpoint, но проверить model id, streaming и `output_config.effort` до боевого
использования, и не пускать реальные сметы до валидации приватности.

## Проверка после деплоя (один тестовый вызов)

- `403 forbidden` → `ANTHROPIC_BASE_URL` не проставился, идём напрямую с РФ-IP.
- `401` → не тот ключ (для агрегатора нужен ключ агрегатора).
- Успех → ответ модели пришёл.

## Итог

Код-часть готова (Фазы 1–2): фабрика клиента + env-схема, синтаксис валиден,
бизнес-логика вызовов не изменена. Фаза 3 (выбор/поднятие посредника и деплой) —
вне кода, выполняется на инфраструктуре.
