# Номер позиции из исходной сметы в перечне

Дата: 2026-08-06
Тип: новая функция (размер M)

## 1. Задача

При составлении перечня из Гранд-сметы (`LIST_FROM_GRAND`, xlsx) добавить
**первой колонкой** номер позиции из исходной сметы — «№ п/п» ЛСР.

Зачем: менеджер сверяет перечень со сметой заказчика построчно. Сейчас в
перечне только собственная сквозная нумерация, и найти строку в исходном файле
можно лишь поиском по наименованию.

## 2. Исследование

### Как перечень собирается сейчас

| Шаг | Где |
|---|---|
| Разбор xlsx Гранд-сметы → строки `{name, unit, quantity, is_section, sheet}` | `file_parser.parse_xlsx_grand` |
| Разбиение на чанки | `file_parser.chunk_rows` |
| Чанк → текст для ИИ | `file_parser.rows_to_text` |
| ИИ возвращает позиции `{type, name, unit, quantity, notes}` | `PROMPT_LIST_FROM_GRAND` |
| Позиции → xlsx (6 колонок) | `excel_service.generate_list` → `_write_perechen_sheet` |
| xlsx → строки документа редактора | `xlsx_generic.parse_xlsx_to_generic_rows` |
| Строки документа → колонки таблицы | `adapters/genericAdapter.ts` |
| Правка строк → позиции задачи | `generic_items.generic_rows_to_items` |

Ключевая находка: **номер позиции уже читается** — `_parse_grand_sheet` берёт
`row[num_col]` и по `_POSITION_NO` решает, позиция это или внутренность
расценки (`__numbered`). Значение тут же выбрасывается. Колонку «№ п/п» ищет
`_find_number_col` левее наименования.

### Как донести номер до позиции перечня — три варианта

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. ИИ возвращает номер** — дописать номер в `rows_to_text` и поле `"no"` в промпт | просто | ИИ может выдумать номер; +токены на каждый чанк; риск просадить качество извлечения |
| **B. ИИ возвращает индекс строки чанка** | номер берётся из файла, не из ИИ | всё те же +токены и та же ошибка сопоставления, только косвенная |
| **C. Детерминированное сопоставление в коде** — после ответа ИИ сопоставить позиции чанка со строками того же чанка по наименованию | ноль токенов, ноль галлюцинаций, промпт не трогаем, тест с точными числами | наименование, изменённое ИИ, не находит пары → пустая ячейка |

**Вывод: вариант C.** Промпт уже требует «не изменяй наименования», ИИ копирует
их дословно — тот же принцип, на котором держится весь перечень. Деградация
мягкая: не нашли пару — пустая ячейка, а не чужой номер. И ничего не стоит:
стоимость обработки сметы ~$10, из них большая часть — токены.

Сопоставление в два яруса:
1. точное совпадение нормализованного наименования (регистр, пробелы);
2. если точного нет — единственный неиспользованный кандидат, у которого одно
   наименование является началом другого (ИИ иногда обрезает хвост). Кандидатов
   больше одного — не берём ничего.

Сопоставление идёт внутри чанка: одинаковые наименования в разных разделах не
перепутаются, повторы внутри чанка разбираются по порядку.

## 3. Границы

**В границах:** перечень из Гранд-сметы в формате xlsx.

**Вне границ (и почему):**
- **PDF-скан Гранд-сметы** — в OCR-тексте структурной колонки «№ п/п» нет,
  сопоставлять не с чем. Колонка просто не появится.
- **Проверка полноты и смета** — другие документы, заказчик их со своей сметой
  построчно не сверяет. Чтобы номер не появлялся там случайно и вразнобой,
  поле вычищается из полезной нагрузки промпта полноты.
- **Перечень из проектной документации** — исходной сметы нет.

## 4. Критерии приёмки

1. Перечень из xlsx Гранд-сметы содержит первой колонкой «№ в исходной смете».
2. Значение = «№ п/п» той строки ЛСР, из которой позиция получена.
3. Позиция без номера в исходнике (ресурс расценки со своей стоимостью) даёт
   пустую ячейку, а не чужой номер.
4. Колонка появляется только если хоть у одной позиции номер есть: перечень из
   проекта и проверка полноты остаются шестиколоночными, как были.
5. Колонка первая и в скачиваемом файле, и в редакторе.
6. Правка строки в редакторе номер не теряет.
7. Нумерация листов: номера у каждого листа свои — сопоставление идёт внутри
   чанка, а чанк границу листа не пересекает.

## 5. Фазы

### [x] Фаза 1. Номер доезжает от файла до позиции

- `file_parser._parse_grand_sheet`: класть `source_no` в строку.
- Новый `utils/source_numbers.py`: `attach_source_numbers(items, rows)` —
  два яруса сопоставления.
- `task_processor._handle_list_from_grand_xlsx`: вызов после `_tag_sheet`.
- Тесты: точное сопоставление, повтор наименования, обрезанный хвост,
  строка без номера, чужой чанк.

### [x] Фаза 2. Колонка в файле и в редакторе

- `excel_service`: `_write_perechen_sheet(..., with_source_no)`, заголовок
  «№ в исходной смете», ширина; `generate_list` включает колонку, если номер
  есть хоть у одной позиции.
- `generic_items`: колонка переживает правку в редакторе.
- `genericAdapter.ts`: колонка первая в таблице.
- Тесты: 7 колонок при номерах / 6 без них, круговой рейс через редактор,
  порядок колонок.

### [x] Фаза 3. Полнота не тянет номер за собой

- `_handle_check_completeness`: `source_no` не уходит в промпт.
- Тест: в полезной нагрузке полноты поля нет.
