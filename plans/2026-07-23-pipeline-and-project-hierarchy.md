## 1. Проблема

Текущая модель «задачи / проекты / канбан» вызывает трение:

1. **Канбан надет на строго линейный процесс.** Колонки доски = *этапы*
   фиксированного конвейера (Перечень → Полнота → Смета → Оптимизация), а не
   статусы. Пользователь вручную перетаскивает карточку между колонками там,
   где порядок и так предопределён. Канбан силён для *гибкого потока по
   статусам*, а не для детерминированного пайплайна — это антипаттерн
   (подтверждено исследованием; ближайший корректный аналог — CI/CD-пайплайны
   со стадиями и гейтами, а не таск-трекеры).
2. **Иерархия «проект → сметы» не выражена в интерфейсе.** В одном объекте
   (проекте) несколько смет (кровля, фасад, электрика…), но UI показывает
   доску, где проект и смета смешаны. При этом в БД проект уже задуман как
   контейнер: у него есть `summary_total` (сводная себестоимость) и страница
   `/summary`.
3. **Перегрузка сущностей и статусов.** Карточка-контейнер (`WorkflowCard`)
   тащит до 4 подзадач; у задачи два параллельных статуса — технический
   (`pending/processing/completed/failed/cancelled`) и бизнес
   (`unestimated/estimated/optimizing/optimized`). Плюс отдельная страница
   «задач-сирот».
4. **Спиннеры вместо прогресса.** AI-джобы идут секунды-минуты, но показывается
   крутилка «идёт обработка» — непонятно, сколько ждать. Исследование (NN/g):
   конкретный счётчик «124 из 500» повышает терпимость к ожиданию в ~3 раза.

## 2. Цель и критерии приёмки

Целевая модель — трёхуровневая иерархия и три экрана «от общего к частному»:

**Проект (объект) → несколько смет → конвейер каждой сметы (4 этапа).**

- [x] **КП-1.** Иерархия «Проект → сметы» выражена в UI: у проекта виден список
  его смет и сводная сумма по объекту; смета — самостоятельная единица работы,
  идущая по конвейеру. _(Фаза 2: `SmetaList` — дефолтный вид ProjectDetail.)_
- [ ] **КП-2.** Вид одной сметы — **пайплайн-степмер** (дорожка из 4 этапов), а
  не колонки канбана. Продвижение автоматическое по завершении джоба; drag как
  способ продвижения убран.
- [ ] **КП-3.** Блокировки переходов (нынешние hard/soft из `computeGuard`)
  показываются как **гейты-замки на этапе** с причиной («нужна полнота»), а не
  как красный баннер после попытки перетащить.
- [ ] **КП-4.** Для идущего этапа показывается **конкретный прогресс**
  («N из M позиций») из `progress_data`, а не генерический спиннер.
- [ ] **КП-5.** Главный экран — **Входящий**: готовые к проверке сметы, упавшие
  джобы (с resume/retry), ждущие решения на гейте. Экран «задач-сирот»
  поглощён входящим.
- [ ] **КП-6.** Двойной статус задачи схлопнут в одно представление: **шкала
  стадии** (где смета в конвейере) + **состояние текущей стадии** (идёт / готово
  / ошибка), без двух конкурирующих бейджей.
- [ ] **КП-7.** Канбан-доска понижена до **необязательного представления**
  (переключатель), а не единственного экрана; либо удалена (см. открытый
  вопрос O-2).
- [ ] **КП-8.** Ничего не сломано из уже работающего: создание задач, обработка
  всех 6 типов, resume-с-чекпоинта, сводная себестоимость, редакторы смет.

## 3. Контекст (карта кода)

### Фронтенд
- Доска и колонки: `frontend/src/components/kanban/KanbanBoard.tsx`,
  `KanbanColumn.tsx`, `KanbanCard.tsx`.
- Диспетчер контента этапов (1338 строк): `kanban/CardStageContent.tsx` →
  `ListStage` / `CompletenessStage` / `EstimateStage` / `OptimizationStage`.
- Guard-логика переходов: `frontend/src/stores/kanban.ts`, функция
  `computeGuard` (hard/soft-блокировки) — **переиспользуется** как условия
  доступности гейтов, не выбрасывается.
- Страница проекта (переключатель «Список/Канбан»): `pages/ProjectDetail.tsx`.
- Дашборд (будущий «Входящий»): `pages/System.tsx` + `components/dashboard/*`
  (`DashboardQueue`, `DashboardErrors`, `DashboardFunnel`, `DashboardProjects`…).
- Задачи-сироты: `pages/UnassignedTasks.tsx` (роут `/projects/unassigned`).
- Создание задачи: `pages/TaskCreate.tsx`. Роуты: `App.tsx`.
- Типы: `types/workflow.ts` (`WorkflowCard`, `KanbanStage`, `TaskStatus`),
  `types/index.ts` (`TASK_TYPE_LABELS`, наборы типов).

### Бэкенд
- Модели: `backend/app/models/project.py` (`summary_total`),
  `task.py` (`status`, `estimation_status`, `project_id`, `progress_data`),
  `workflow_card.py` (`stage`, 4 слота `*_task_id`) — де-факто это и есть «Смета».
- Константы/маппинги: `backend/app/constants.py` (`TASK_TYPE_LABELS`,
  `TASK_TYPE_TO_STAGE`, `ESTIMATION_STATUS_*`).
- Обработка/прогресс: `services/task_processor.py` (пишет `progress_data`,
  `progress_message`; диспетчер по `task_type` ~стр. 1046).

**Ключевое наблюдение:** `WorkflowCard` уже = «смета» (привязана к проекту,
держит 4 этапа-слота). Большая часть переработки — **фронтовая подача**, а не
новая модель данных. Радикальная смена схемы БД не требуется на старте.

## 4. Фазы

> Каждую фазу с изменением кода вести через skill `bulletproof`.
> При любом изменении `models/*.py` — сначала миграция в
> `alembic/versions/0NN_*.py` с `IF NOT EXISTS` (правило проекта).

### Фаза 1 — Терминология и связь «Проект → сметы» `[x]`
- Ввести в UI-словарь сущность **«Смета»** как то, что сейчас `WorkflowCard`
  (пользователь видит «сметы», не «карточки»).
- На фронте: типы и лейблы (`WorkflowCard` → отображать как «Смета»), без слома
  API. Бэкенд-переименование модели — опционально и позже (риск/миграции).
- Критерий: в интерфейсе проекта смета называется сметой, видно, что проект
  содержит несколько смет.

### Фаза 2 — Экран «Проект и сметы» `[x]`
- Переработать `ProjectDetail.tsx`: основной вид — **список/таблица смет**
  проекта (имя сметы, текущий этап, состояние, сумма) + **сводная сумма по
  объекту** (уже есть `summary_total`) + «＋ Добавить смету».
- Опционально — двухпанельно (слева проекты, справа сметы), как в макете.
- Канбан оставить доступным через переключатель (пока не трогаем — Фаза 7).
- Критерий: КП-1.

**Реализовано (2026-07-24):**
- Новый компонент `frontend/src/components/SmetaList.tsx` — таблица смет
  (столбцы: Смета / Этап / Состояние / Сумма), переиспользует `useKanbanStore`
  + `getWorkflowCards` (тот же источник, что и канбан; загрузка не дублируется),
  поллинг 5s. Клик по строке → `/projects/:projectId/cards/:cardId`.
- `ProjectDetail.tsx`: три режима вида — **Сметы** (по умолчанию), **Канбан**,
  **Задачи** (прежний список сырых задач сохранён). Сводная себестоимость и
  счётчики в шапке не тронуты.
- «＋ Добавить смету» → `CreateCardModal` (stage=list). Добавлен опциональный
  проп `onCreated` в `CreateCardModal`; после создания вид переключается на
  канбан, где отложенный файл перечня подхватывается `CardStageContent`
  (в списке/на странице карточки запуск перечня пока недоступен — см. ограничение).
- **Ограничение API:** списочный эндпоинт `GET /workflow-cards` не отдаёт сумму
  сметы (в `WorkflowCardResponse`/`TaskBrief` нет `cost`). Чтобы не плодить N
  запросов к `/detail`, столбец «Сумма» показывает «—». Полноценная сумма — при
  появлении поля в списочном ответе (бэкенд в этой фазе не трогали).

### Фаза 3 — Пайплайн-степпер (вид одной сметы) `[ ]`
- Новый компонент дорожки: 4 узла-этапа + коннекторы, состояния
  `wait / lock / run / done`. Заменяет колоночную раскладку для одной сметы.
- Продвижение — по факту завершения джоба (данные уже есть в статусах задач),
  без drag. Контент этапа (загрузка файла, запуск, результат) переиспользует
  логику из `CardStageContent.tsx`.
- Гейты: `computeGuard` → показывать замок с причиной на недоступном этапе
  (hard = замок; soft = предупреждение с «Пропустить», как сейчас, но на этапе).
- Критерий: КП-2, КП-3.

### Фаза 4 — Прогресс-счётчики вместо спиннеров `[ ]`
- На идущем этапе показывать `progress_data` как «N из M» (+ короткий
  `progress_message`), fallback на спиннер только если счётчика нет.
- Данные уже пишет `task_processor.py`; работа в основном фронтовая.
- Критерий: КП-4.

### Фаза 5 — Главный экран «Входящий» `[ ]`
- Переосмыслить `System.tsx` в inbox «что требует меня»: готовые к проверке,
  упавшие (resume/retry), ждущие решения на гейте. Переиспользовать
  `DashboardQueue` / `DashboardErrors`.
- Поглотить `UnassignedTasks` — «ничейные» становятся строками входящего;
  роут `/projects/unassigned` → редирект/удаление.
- Каждый элемент помечен `Проект · смета «…»`.
- Критерий: КП-5.

### Фаза 6 — Схлопнуть двойной статус `[ ]`
- В UI показывать одно: шкалу стадии (позиция в конвейере) + состояние текущей
  стадии (идёт/готово/ошибка). `estimation_status` использовать как бизнес-факт
  (есть ли сумма), но не как второй конкурирующий бейдж.
- Модель БД не ломать; это правило отображения.
- Критерий: КП-6.

### Фаза 7 — Понизить/убрать канбан + чистка `[ ]`
- Канбан → необязательное представление (по умолчанию — пайплайн/список) либо
  удаление `KanbanBoard/Column/Card` (см. O-2).
- Убрать мёртвый код (`"OPTIMIZE_SMETA"` в `task_processor.py`, лишние ветки).
- Критерий: КП-7, КП-8 (регресс-проверка).
