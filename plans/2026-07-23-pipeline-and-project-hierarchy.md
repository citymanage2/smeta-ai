## 1. Проблема

Текущая модель «задачи / проекты / канбан» вызывает трение:

1. **Канбан надет на строго линейный процесс.** Колонки доски = *этапы*
   фиксированного конвейера (Перечень → Полнота → Смета → Оптимизация), а не
   статусы. Пользователь вручную перетаскивает карточку между колонками там,
   где порядок и так предопределён. Канбан силён для *гибкого потока по
   статусам*, а не для детерминированного пайплайна — это антипаттерн
   (подтверждено исследованием; ближайший корректный аналог — CI/CD-пайплайны
   со стадиями и гейтами, а не таск-трекеры).
2. **Иерархия «проект → сметы» не выражена в интерфейсе.** В одном объекте
   (проекте) несколько смет (кровля, фасад, электрика…), но UI показывает
   доску, где проект и смета смешаны. При этом в БД проект уже задуман как
   контейнер: у него есть `summary_total` (сводная себестоимость) и страница
   `/summary`.
3. **Перегрузка сущностей и статусов.** Карточка-контейнер (`WorkflowCard`)
   тащит до 4 подзадач; у задачи два параллельных статуса — технический
   (`pending/processing/completed/failed/cancelled`) и бизнес
   (`unestimated/estimated/optimizing/optimized`). Плюс отдельная страница
   «задач-сирот».
4. **Спиннеры вместо прогресса.** AI-джобы идут секунды-минуты, но показывается
   крутилка «идёт обработка» — непонятно, сколько ждать. Исследование (NN/g):
   конкретный счётчик «124 из 500» повышает терпимость к ожиданию в ~3 раза.

## 2. Цель и критерии приёмки

Целевая модель — трёхуровневая иерархия и три экрана «от общего к частному»:

**Проект (объект) → несколько смет → конвейер каждой сметы (4 этапа).**

- [x] **КП-1.** Иерархия «Проект → сметы» выражена в UI: у проекта виден список
  его смет и сводная сумма по объекту; смета — самостоятельная единица работы,
  идущая по конвейеру. _(Фаза 2: `SmetaList` — дефолтный вид ProjectDetail.)_
- [x] **КП-2.** Вид одной сметы — **пайплайн-степмер** (дорожка из 4 этапов), а
  не колонки канбана. Продвижение автоматическое по завершении джоба; drag как
  способ продвижения убран. _(Фаза 3: `PipelineStepper` в `ProjectCardPage`.)_
- [x] **КП-3.** Блокировки переходов (нынешние hard/soft из `computeGuard`)
  показываются как **гейты-замки на этапе** с причиной («нужна полнота»), а не
  как красный баннер после попытки перетащить. _(Фаза 3: замок+причина на узле,
  soft — предупреждение над контентом этапа.)_
- [x] **КП-4.** Для идущего этапа показывается **конкретный прогресс**
  («N из M частей» + счётчик найденных позиций) из `progress_data`, а не
  генерический спиннер. _(Фаза 4: `ProgressCounter` в контенте этапа + компактное
  «N/M» на узле степпера; данные — через whitelist-выжимку в `TaskBrief`.)_
- [x] **КП-5.** Главный экран — **Входящий**: готовые к проверке сметы, упавшие
  джобы (с resume/retry), ждущие решения на гейте. Экран «задач-сирот»
  поглощён входящим. _(Фаза 5: `System.tsx` → инбокс; `UnassignedInbox`.)_
- [x] **КП-6.** Двойной статус задачи схлопнут в одно представление: **шкала
  стадии** (где смета в конвейере) + **состояние текущей стадии** (идёт / готово
  / ошибка), без двух конкурирующих бейджей. _(Фаза 6: хелпер `taskStatusView` +
  `StageStateBadge`; estimation_status → тонкая пометка, не второй бейдж.)_
- [ ] **КП-7.** Канбан-доска понижена до **необязательного представления**
  (переключатель), а не единственного экрана; либо удалена (см. открытый
  вопрос O-2).
- [ ] **КП-8.** Ничего не сломано из уже работающего: создание задач, обработка
  всех 6 типов, resume-с-чекпоинта, сводная себестоимость, редакторы смет.

### Фаза 3 — Пайплайн-степпер (вид одной сметы) `[x]`
- Новый компонент дорожки: 4 узла-этапа + коннекторы, состояния
  `wait / lock / run / done`. Заменяет колоночную раскладку для одной сметы.
- Продвижение — по факту завершения джоба (данные уже есть в статусах задач),
  без drag. Контент этапа (загрузка файла, запуск, результат) переиспользует
  логику из `CardStageContent.tsx`.
- Гейты: `computeGuard` → показывать замок с причиной на недоступном этапе
  (hard = замок; soft = предупреждение с «Пропустить», как сейчас, но на этапе).
- Критерий: КП-2, КП-3.

**Реализовано (2026-07-24):**
- Новый компонент `frontend/src/components/pipeline/PipelineStepper.tsx` —
  дорожка из 4 узлов (Перечень → Полнота → Смета → Оптимизация) + коннекторы.
  Состояние узла считает `computeNodeState(card, stage)`: `done` (task completed),
  `run` (pending/processing/paused), `error` (failed/cancelled — расширение поверх
  4 базовых, перезапуск живёт в контенте этапа), `lock` (`computeGuard` даёт
  hard-блок для входа в этап), `wait` (доступен, не запускался). Замок рисуется
  прямо на узле + подпись с причиной из `computeGuard(...).message`. Цвета — те же
  токены, что в SmetaList/канбане (done=#10b981, run=#3b82f6, lock=#94a3b8+замок,
  wait=нейтральный, error=#ef4444).
- `computeGuard` экспортирован из `stores/kanban.ts` (был приватным) и
  переиспользуется как условие доступности гейтов — логика гейтов не продублирована.
- **Drag убран** для вида одной сметы: продвижение визуальное, по статусам задач
  (поллинг 5s через тот же `useKanbanStore`, что канбан/SmetaList). `KanbanBoard`
  не тронут (Фаза 7 / O-2).
- `pages/ProjectCardPage.tsx` переписан: сверху `PipelineStepper`, снизу —
  `<CardStageContent card={{ ...card, stage: выбранныйЭтап }} />`. Показ контента
  выбранного узла сделан **наименее инвазивно**: `CardStageContent` рендерит по
  `card.stage`, поэтому клик по узлу не двигает карточку через `moveCard` и не
  пишет в БД — просто передаётся поверхностная копия карточки с переопределённым
  `stage`. Логика загрузки файлов и запуска джобов (`ListStage`/`CompletenessStage`/
  `EstimateStage`/`OptimizationStage`) вызвана как есть, без изменений и без экспорта
  под-компонентов. Побочный плюс: ограничение Фазы 2 (запуск перечня со страницы
  карточки был недоступен) снято — `ListStage` подхватывает `pendingListTasks`.
- Soft-гейт (`estimate` без завершённой полноты) показывается как жёлтое
  предупреждение над контентом этапа с кнопкой «Продолжить» (не блокирует; сам
  запуск сметы — через существующую кнопку в контенте).
- Начальный выбранный этап — `defaultStage`: идёт → ошибка → первый доступный
  незапущенный → последний завершённый. Дальше меняется только по клику.
- Проверки: `npm run build` зелёный, `npm test` — 43/43 зелёные (включая
  ProjectDetail.test.tsx). Логика этапов не тронута → регресс по запуску всех
  типов джобов исключён переиспользованием.

### Фаза 4 — Прогресс-счётчики вместо спиннеров `[x]`
- На идущем этапе показывать `progress_data` как «N из M» (+ короткий
  `progress_message`), fallback на спиннер только если счётчика нет.
- Данные уже пишет `task_processor.py`; работа в основном фронтовая.
- Критерий: КП-4.

**Реализовано (2026-07-24):**
- **Находка по структуре `progress_data`.** Единый надёжный счётчик «N из M» по
  типам задач — это *чанки*: `chunks_done` / `total_chunks` (LIST_FROM_GRAND,
  LIST_FROM_PROJECT(_PDF), CHECK_*_COMPLETENESS, ESTIMATE_FROM_LIST); оптимизация
  пишет `chunks_total`. Общее число *позиций* заранее неизвестно (позиции
  накапливаются) — поэтому M считаем по частям, а число найденных позиций
  показываем отдельно как `items_count = len(items)`. Помимо счётчиков в
  `progress_data` лежат тяжёлые/чувствительные поля: `items` (позиции с ценами),
  `ocr_pages`/`ocr_pages_partial` (сырой OCR PDF), `claude_results`, `matched`,
  `unmatched`, `proposals`, `abc_breakdown`, `batch_id`, `_stage` и т.п.
- **Доставка на фронт — через сериализатор, без доп. запросов.** До правок
  `TaskBrief` (в `card.*_task`, которым уже питается страница сметы) НЕ содержал
  `progress_data` — только `progress_message`. Полный `progress_data` отдаётся
  лишь через `GET /tasks/{id}/status` (используется старой `TaskStatus.tsx` и
  тулбаром оптимизации — его НЕ трогали). Выбран путь: добавить в сериализатор
  `TaskBrief` поле `progress_data` с **whitelist-выжимкой** (миграция не нужна —
  поле в модели уже есть). Страница сметы поллит workflow-cards каждые 5s →
  счётчик доступен без N доп. запросов.
- **Whitelist (безопасность):** новый `backend/app/utils/progress_summary.py`
  → `build_progress_summary()` отдаёт ТОЛЬКО скаляры: `chunks_done`,
  `total_chunks` (+нормализация `chunks_total`), `partial_count`, `opt_step`,
  `status`, и производный `items_count` (длина списка, без содержимого). Всё
  чувствительное (items, ocr_pages, claude_results, matched, proposals, batch_id,
  _stage, error…) отброшено. Покрыто тестом
  `backend/tests/test_progress_summary.py` (6 кейсов, включая «запрещённые поля
  не утекают»).
- **UI:** `frontend/src/components/kanban/ProgressCounter.tsx` — тонкая полоса +
  «N из M частей · найдено X позиций» (цвета/токены как в степпере/бренде);
  вставлен в 3 места спиннеров `CardStageContent.tsx` (Перечень / Полнота /
  Смета). Опционально — компактное «N/M» на идущем узле `PipelineStepper.tsx`.
  Fallback: нет числового прогресса → прежний спиннер + `progress_message`.
- **Типы:** `TaskBrief.progress_data?: ProgressSummary` в `types/workflow.ts`.
- **Проверки:** backend — `ruff check .` зелёный, `pytest` (test_admin +
  test_progress_summary) 14/14; frontend — `npm run build` зелёный, `npm test`
  51/51 (добавлен `__tests__/ProgressCounter.test.tsx`, 8 кейсов). Сериализатор
  не падает при `progress_data=None` (проверено).
