# Комплект материалов к работе по нормам расхода

Дата: 2026-08-06. Размер: M (bulletproof, стадии 1–10).

## Проблема

В смете строка 155: **«Устройство перегородок из гипсоволокнистых листов (ГВЛ) с
одинарным металлическим каркасом и двухслойной обшивкой с обеих сторон: с одним
дверным проемом», м², 5,475, цена работы 1300**.

Что не так:

1. **Материалов каркасной системы в смете нет вообще.** Ни листов ГВЛ, ни
   профилей ПН/ПС, ни саморезов, ни дюбелей, ни ленты, ни шпаклёвки швов.
   Единственное, что стоит под работой, — утеплитель (5,639 м²) и кровельная
   плита ТЕХНОРУФ 45 (0,51 м³), которая к перегородке отношения не имеет и
   оказалась рядом только потому, что так лежала в файле заказчика.
2. **Объём листов, если бы их добавили, был бы взят равным объёму работы.**
   Правильный объём — `5,475 × 2 слоя × 2 стороны = 21,9 м²` без подрезки.

## Почему так вышло — факты по коду

**Материалы не появляются, потому что их нет в исходном файле.** В ЛСР
ГРАНД-Сметы материалы, *учтённые расценкой*, по наименованиям не раскрываются —
только суммой в строке «4 М». Мы берём из файла ровно то, что там написано.
Зафиксировано в «Осталось за рамками» плана
[2026-08-05-zadvaivanie-materialov.md](2026-08-05-zadvaivanie-materialov.md).

**Объём не считается, потому что механизм норм не подключён к основному потоку.**
В проекте уже есть:

| Что | Где |
|---|---|
| Поля `qty_per_work_unit`, `norm_reference`, `work_row_id` | `backend/app/schemas/estimate_version.py:25-29` |
| Пересчёт объёма материала при правке объёма работы | `frontend/src/utils/estimateRecalc.ts` |
| Определение норм через ИИ | `task_processor.py:_enrich_rows_with_gesn_norms` |
| Привязка материала к работе «ближайшая работа выше» | `estimate_parser.py:link_materials_to_works` |

Но вызываются они **только** в ветке `ESTIMATE_OPTIMIZATION` — загрузка чужой
готовой сметы (`task_processor.py:3140` и `:3174`). В потоке
*гранд-смета → перечень → смета* `items_to_rows` (`backend/app/utils/estimate_rows.py`)
не проставляет ни `work_row_id`, ни норм. Материал стоит рядом с работой только
по порядку строк.

**Единственное место, где материалы могли бы дописываться, — шаг «Полнота»**
(`PROMPT_CHECK_COMPLETENESS`, `task_processor.py:188`). Промпт сформулирован
общо: «проверь, все ли материалы учтены по ГЭСН/ФСНБ». Никаких правил каркасных
систем (слои, стороны, шаг стойки, крепёж) в нём нет — поэтому ИИ и не
разворачивает перегородку в комплект.

## Смежная дыра, найденная при разборе (закрываем здесь же)

Правки, сделанные человеком в редакторе документа «Полнота», **не доезжают до
сметы**. `save_rows` (`backend/app/routers/estimate_versions.py:174`) пишет
`version.rows` и пересобирает xlsx, но не трогает `task.progress_data['items']`.
А смета со стадии 2 «После проверки полноты» читает именно
`progress_data['items']` (`task_processor.py:2493`).

Без закрытия этой дыры выбранное решение «расхождение показать, решает человек»
не работает: человек поправит объём, а в смету уедет старое число. Поэтому
синхронизация — обязательная фаза этого плана, а не смежное улучшение.

## Принятые решения (согласованы 2026-08-06)

| Вопрос | Решение |
|---|---|
| Где разворачивать комплект | На шаге **«Полнота» перечня** — до расчёта цен, новые материалы сразу получают цену из прайса/ИИ |
| Источник норм | **Гибрид**: детерминированный справочник в коде для каркасных систем + ИИ по ГЭСН для остальных работ |
| Как применять | **Добавлять сразу**, помечать цветом и обоснованием в примечании |
| Цена работы в прайсе | **Чистая работа**, материалы отдельными строками → задваивания денег нет |
| Подрезка и отходы | **Чистый объём**, без коэффициента запаса. ГВЛ = 21,9 м², а не 24,09 |
| Материал уже есть в перечне с другим объёмом | **Не трогать**, пометить расхождение: «по норме 21,9, в файле 5,475» |
| Охват справочника | **Каркасные ГКЛ/ГВЛ**: перегородки, облицовки стен, подвесные потолки |
| Параметры не читаются из наименования | **Типовой дефолт** (1 слой × 2 стороны) + явная пометка «принято 1×2, проверьте» |

## Архитектура решения

```
LIST_FROM_GRAND (перечень как в файле)
        │
        ▼
CHECK_LIST_COMPLETENESS ─── новый шаг «разворачивание комплекта» ───┐
        │                                                           │
        │  1. Справочник: работа → конструктивная система           │
        │     распознана?                                           │
        │       да  → детерминированный расчёт комплекта            │
        │       нет → как сейчас, ИИ по ГЭСН                        │
        │  2. Дедупликация против уже имеющихся материалов          │
        │  3. Новые строки: qty = объём работы × норма              │
        │     notes = «Добавлено по норме: 5,475 × 2 слоя × 2       │
        │     стороны = 21,9 м² (КНАУФ С-112)»                      │
        ▼                                                           │
   документ «Полнота» ◄────────────────────────────────────────────┘
   (подсветка новых строк и расхождений)
        │  правки человека ─► синхронизация в progress_data['items']
        ▼
ESTIMATE_FROM_LIST со стадии 2 → цены из прайса → смета
```

### Новый модуль: `backend/app/data/material_kits.py`

Справочник — данные, а не код. Одна конструктивная система = одна запись:

```python
KIT_GKL_PARTITION = MaterialKit(
    id="gkl_partition",
    title="Перегородка каркасная ГКЛ/ГВЛ",
    match=(r"перегородк\w*", r"(гкл|гвл|гипсокартон|гипсоволокн)"),
    work_unit="м2",
    defaults={"layers": 1, "sides": 2},
    materials=[
        KitMaterial("Лист ГВЛ 12,5 мм", "м2", lambda p: p.layers * p.sides, "КНАУФ С-112"),
        KitMaterial("Профиль стоечный ПС 50×50", "м", lambda p: 2.0, "КНАУФ С-112"),
        ...
    ],
)
```

Требования к модулю:

- **Чистые функции, ноль обращений к БД и ИИ.** Вход — наименование работы,
  единица и объём. Выход — список позиций. Проверяется тестом с точными числами.
- **Распознавание параметров из наименования**: «двухслойной» → `layers=2`,
  «с обеих сторон» → `sides=2`, «однослойной» → 1, «облицовка» → `sides=1`.
  Не распозналось — берётся `defaults` и в `notes` пишется, что принято по
  умолчанию.
- **Единица работы обязана совпасть.** Расценка в м³ или пог. м с
  `work_unit="м2"` не разворачивается — иначе получим объём материала, умноженный
  не на ту величину.

### Черновая таблица норм — ТРЕБУЕТ ВАШЕГО ПОДТВЕРЖДЕНИЯ

На 1 м² перегородки, одинарный металлический каркас, шаг стойки 600 мм. Веб-поиск
по КНАУФ точную таблицу на 1 м² не отдаёт (в альбомах расход дан на конкретную
перегородку 11 м²), поэтому числа ниже — общеупотребительные ориентиры, а не
подтверждённый норматив.

| Материал | Ед. | Норма на 1 м² | Для строки 155 (5,475 м²) |
|---|---|---|---|
| Лист ГВЛ/ГКЛ | м² | `слои × стороны` = 4 | **21,9** |
| Профиль стоечный ПС | пог.м | 2,0 | 10,95 |
| Профиль направляющий ПН | пог.м | 0,8 | 4,38 |
| Лента уплотнительная | пог.м | 0,8 | 4,38 |
| Шурупы TN 25 (1-й слой) | шт | 20 | 109,5 |
| Шурупы TN 35 (2-й слой) | шт | 34 | 186,15 |
| Дюбель-гвоздь 6×40 | шт | 1,6 | 8,76 |
| Лента армирующая (серпянка) | пог.м | 1,2 | 6,57 |

Каждое число в справочнике сопровождается ссылкой на источник в комментарии и
тестом с точным результатом. Ошибка здесь = ошибка в каждой смете, поэтому
таблица не уходит в код, пока вы её не подтвердите.

### Дедупликация и расхождения

Материал комплекта считается уже присутствующим, если среди материалов той же
работы есть позиция с совпадающим нормализованным именем
(`embedding_service.normalize_name`, `:30`) и той же единицей.

- Совпал, объём в пределах ±5 % от расчётного → ничего не делаем.
- Совпал, объём расходится сильнее → строка помечается расхождением, число
  заказчика **не меняется**, в примечание пишется: «По норме 21,9 м², в файле
  5,475 м² — проверьте».
- Не совпал → добавляем новую строку сразу после последнего материала этой работы.

## Challenge log

**1. Решает ли это проблему?** Да, обе части: комплект появляется (Фазы 3–4),
объём считается формулой `объём работы × норма` (Фаза 3), результат доезжает до
сметы (Фазы 4–5) и виден человеку (Фаза 6).

**2. Самое ли это эффективное решение?** Рассмотрены три:

- *Только ИИ по ГЭСН* — дешевле в разработке, покрывает любые работы. Отклонено:
  ИИ путает шифры и нормы, каждый прогон даёт другое число, тестом не закрепить.
  Для сметы, с которой идут на тендер, это неприемлемо.
- *Только справочник* — детерминированно, но покрывает малую долю строк сметы.
- *Гибрид* — справочник даёт точность там, где цена ошибки высока и типовых
  систем немного; ИИ закрывает хвост с пометкой «требует проверки». Выбран.

Отдельно рассмотрено «читать колонку Обоснование (ФЕР/ГЭСН-шифр) из ЛСР и
разворачивать по шифру». Точнее распознаёт систему, но требует базы ГЭСН, которой
у нас нет. Оставлено как возможное развитие: шифр можно использовать как
дополнительный признак `match`.

**3. Нет ли кода ради кода?** Всё привязано к двум симптомам из проблемы. Не
делаем: коэффициенты подрезки (решено — чистый объём), автоматическую правку
объёмов заказчика (решено — только пометка), расширение справочника за пределы
каркасных систем (следующая итерация), подключение норм к основному потоку
`ESTIMATE_FROM_LIST` (комплект разворачивается в «Полноте», дублировать не нужно).

## Риски

- **Нормы неверны** → ошибка в каждой смете. Снимается Фазой 1 (ваше
  подтверждение) и тестами с точными числами.
- **Работа распознана ошибочно** (например, «Разборка перегородок из ГКЛ» —
  демонтаж, материалы не нужны) → в `match` обязательны стоп-слова: разборка,
  демонтаж, снятие, очистка.
- **Смета вырастает в объёме** — 10 новых строк на каждую перегородку. Ожидаемо:
  материалы обязаны быть в смете. Но итог по деньгам вырастет, и это надо
  проговорить с отделом продаж до внедрения.
- **Двойной счёт с ИИ**: ИИ на том же чанке добавит свой профиль. Снимается
  Фазой 4 — распознанные работы явно исключаются из зоны ответственности ИИ.
