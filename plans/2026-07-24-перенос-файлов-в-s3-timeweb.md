## Проблема

Все загруженные и сгенерированные файлы хранятся как BLOB (`LargeBinary` / `BYTEA`) прямо в PostgreSQL:

- `task_input_files.content` — входные файлы пользователя ([task_input_file.py:21](../backend/app/models/task_input_file.py#L21))
- `task_results.file_data` — результаты и сметы по слотам ([result.py:20](../backend/app/models/result.py#L20))
- `tasks.input_file_data` — legacy base64 в JSON ([task.py:32](../backend/app/models/task.py#L32))

**Почему это плохо:**

1. **БД раздувается.** Каждый PDF/xlsx (до 20 МБ) лежит в основной БД. Растут размер, время бэкапа/восстановления, стоимость managed-Postgres на Render.
2. **Дорогие бэкапы и репликация.** Бинарные данные гоняются вместе с транзакционными.
3. **Лимит 20 МБ** ([config.py:15](../backend/app/config.py#L15)) — прямое следствие BLOB-архитектуры (крупный BLOB переполняет буфер соединения, см. комментарий на [tasks.py:309-310](../backend/app/routers/tasks.py#L309-L310)).
4. **Нагрузка на пул соединений.** Скачивание файла держит соединение к БД всё время стриминга.

## Цель

Вынести бинарное содержимое файлов в S3-совместимое объектное хранилище **Timeweb Cloud** (`https://s3.twcstorage.ru`, регион `ru-1`, AWS Signature V4). В БД оставить только метаданные + ключ объекта в S3.

## Критерии приёмки

- [ ] Новые загрузки (`POST /tasks`, `POST /tasks/{id}/files`, `POST /tasks/{id}/input-files`) пишут содержимое в S3, в БД — только `storage_key`.
- [ ] Скачивание (`GET .../download`, `GET .../input-file/{i}`) отдаёт файл из S3.
- [ ] Обработка задач (`task_processor`) читает исходники из S3.
- [ ] Все существующие файлы (BLOB) перенесены в S3 без потерь (backfill).
- [ ] Удаление задачи/результата удаляет и объект в S3 (нет «сирот»).
- [ ] Обратная совместимость на переходный период: если `storage_key` пуст — читаем из BLOB (fallback).
- [ ] S3-недоступность обрабатывается явно (ретраи + понятная ошибка, не 500 без контекста).
- [ ] Credentials только через env, не в git.
- [ ] Лимит размера файла можно поднять (S3 больше не упирается в буфер соединения БД).

## Вне scope (Non-Goals)

- Presigned URL для прямой отдачи с S3 клиенту (фронт качает напрямую) — отдельная оптимизация, не в этой итерации. Пока стримим через backend (проще, безопаснее, не меняет фронт).
- Миграция на другого провайдера / мультиклауд.
- CDN перед бакетом.
- Шифрование на стороне клиента.

## Архитектурное решение

### Почему S3-абстракция, а не прямой boto3 в роутах

Единый сервис `storage_service.py` со всеми операциями (`put`, `get`, `get_stream`, `delete`, `exists`). Роуты и `task_processor` работают с ним, не зная про boto3. Это даёт:
- одну точку конфигурации и ретраев;
- лёгкую подмену на локальную файловую систему / MinIO в тестах;
- возможность позже добавить presigned URL без правок вызывающего кода.

### boto3 vs aioboto3

FastAPI async, но boto3 синхронный. Варианты:
1. **`boto3` + `run_in_threadpool`** (рекомендуется) — стабильный, официальный SDK, оборачиваем блокирующие вызовы в `starlette.concurrency.run_in_threadpool`. Минус — поток на операцию.
2. `aioboto3` — нативно async, но тоньше поддержка, лишняя зависимость поверх aiobotocore.

**Выбор: boto3 + run_in_threadpool.** Операции с файлами редкие (не hot path на тысячи rps), overhead потока незначим. Меньше рисков, официальная поддержка.

### Схема ключей в S3

```
tasks/{task_id}/input/{file_index}-{sanitized_name}
tasks/{task_id}/result/{slot}-{sanitized_name}
```

Префикс по `task_id` → удобно удалять все объекты задачи одним `list+delete` по префиксу при каскадном удалении.

### Стратегия миграции (expand → migrate → contract)

Классический безопасный паттерн, без даунтайма и без «большого взрыва»:

1. **Expand.** Добавляем nullable-колонку `storage_key` в обе таблицы. BLOB-колонки делаем nullable, но НЕ удаляем.
2. **Dual-read / new-write.** Новые файлы → S3 (`storage_key` заполнен, `content`=NULL). Чтение: если `storage_key` есть → S3, иначе → BLOB (fallback). Prod работает на смешанных данных.
3. **Backfill.** Скрипт переносит существующие BLOB → S3, проставляет `storage_key`, обнуляет `content`/`file_data`. Идемпотентный, батчами, с логом.
4. **Contract.** После проверки (0 строк с BLOB и без ключа) — миграция дропает BLOB-колонки. Лимит размера поднимаем.

### Фаза 4 — Backfill существующих файлов `[x]`

> **Реализовано (2026-07-25).** `scripts/backfill_files_to_s3.py` — идемпотентный перенос BLOB→S3 батчами (task_input_files.content, task_results.file_data) + legacy `tasks.input_file_data` (base64→S3+строка task_input_files). Флаги `--dry-run` (только объёмы) и `--no-verify` (без re-read сверки; по умолчанию верифицирует). Переносит независимо от S3_ENABLED. Пост-проверка: остаток BLOB без storage_key. Функции принимают `session_factory` — 2 теста через SQLite (перенос+идемпотентность, dry-run). **Запуск — на реальной БД после деплоя dual-read кода** (иначе старый код сломается на обнулённых BLOB).

Скрипт `backend/scripts/backfill_files_to_s3.py`:

- Идёт батчами по `task_input_files` и `task_results`, где `content/file_data IS NOT NULL AND storage_key IS NULL`.
- Для каждой строки: `put_object` → проставить `storage_key` → `UPDATE ... SET content=NULL` (в отдельной транзакции на батч).
- Идемпотентный (повторный запуск пропускает уже перенесённые), с прогресс-логом и счётчиком.
- Ключ `--dry-run` для проверки без записи.
- Обработать legacy `tasks.input_file_data` (base64 в JSON): декодировать base64 → `put_object` → создать/обновить строку в `task_input_files` со `storage_key` → обнулить JSON-поле (или пометить перенесённым). Отдельная ветка скрипта.

**Проверка после прогона:** `SELECT count(*) FROM task_input_files WHERE content IS NOT NULL AND storage_key IS NULL` = 0 (и то же для results).

**Gate:** прогон на копии прод-БД, сверка контрольных сумм нескольких файлов (S3 vs исходный BLOB) до обнуления.

### Фаза 5 — Каскадное удаление объектов S3 `[x]`

> **Реализовано (2026-07-25).** Хелпер `storage_service.delete_key_safe` (None-safe, best-effort). Гарантия «нет сирот после удаления задачи»: **permanent-delete задачи → `delete_prefix(tasks/{id}/)`** (все объекты разом, best-effort). Промпт-чистка при явных операциях: перезапись слота (upload), удаление слота, удаление input-файла, перезапись в `save_result` — удаляют прежний объект после коммита. **Soft-delete объекты НЕ трогает** (корректно by design). ## Риски и как решаем

| Риск | Решение |
|------|---------|
| S3 недоступен во время загрузки → потеря файла | Ретраи boto3 (3 попытки); при неудаче — 503 с понятной ошибкой, файл не теряется (транзакция БД откатывается, не создаём запись без объекта) |
| «Сироты» в S3 (объект есть, строки нет) | Каскадное удаление по префиксу (фаза 5) + опциональный cron-аудит orphan-объектов |
| Backfill повредит данные | Идемпотентность, `--dry-run`, сверка контрольных сумм ДО обнуления BLOB, батчи в отдельных транзакциях |
| Порядок «сначала S3, потом БД» → объект без записи | Сначала `put_object`, при успехе — INSERT/commit; при падении commit объект удаляем (best-effort) или оставляем на cron-чистку |
| Утечка чужих файлов | Доступ к файлу только через проверку принадлежности `task_id` (как сейчас); бакет приватный; ключи не угадываются (но не полагаемся только на это) |
| path traversal через имя файла в ключе | `sanitize_filename` + генерация ключа только из `task_id`+`file_index`/`slot`, имя файла не влияет на путь |

## Что НЕ делаем (борьба с «кодом ради кода»)

- Не строим абстракцию «мультипровайдер» — только Timeweb S3 (интерфейс сервиса и так позволит подменить позже).
