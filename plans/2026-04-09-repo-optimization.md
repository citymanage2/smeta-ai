## БЛОК 3 — Рефакторинг хранения истории (History/Revert)

**Цель:** сохранить функционал откатов оптимизации, убрать неправильное хранение данных.

### Проблема подробно

Сейчас при каждой оптимизации система сохраняет полный xlsx-файл (~500 КБ)
в поле `previous_value: dict` таблицы `task_history` — как Base64-строку внутри JSON.
Это значит файл хранится дважды: в `task_results` (правильно) и в `task_history` (неправильно).

**Последствия:**
- Каждая запись истории = +700 КБ в БД
- PostgreSQL медленнее работает с большими JSON-полями
- При 100 оптимизациях таблица весит 70 МБ только в JSON-полях

### Правильное решение

Хранить файловые снимки в `task_results` со специальными слотами-версиями
(`optimized_v1`, `optimized_v2` и т.д.). В `task_history` хранить только метаданные:
какой слот, какое имя файла, ID записи.

- [x] **3.1** `backend/app/models/result.py` → `slot: String(20)` расширен до `String(50)`
- [x] **3.2** `_run_optimization_background` в `tasks.py`: при наличии предыдущего "optimized"
  слот переименовывается в `optimized_v{n}` (архив), создаётся новый "optimized" с новыми байтами.
  `previous_value` содержит только `{"result_slot": "optimized_v{n}", "estimation_status": ...}` — без base64
- [x] **3.3** `revert_history`: если `previous_value["result_slot"]` существует — переименовывает
  версионный слот обратно в "optimized"; обратная совместимость со старым форматом `file_data_b64`
- [x] **3.4** Миграция Alembic `009_widen_result_slot.py`: `ALTER COLUMN slot VARCHAR(50)`
- [x] **3.5** `task_history.previous_value/new_value` больше не хранят файловые байты —
  только метаданные (`result_slot`, `file_name`, `estimation_status`)
- [x] **Бонус**: исправлена совместимость моделей `Task` и `Project` с SQLite-тестами
  (заменён `server_default=text("gen_random_uuid()")` на `default=lambda: str(uuid4())`)
- [x] **Тесты**: `test_task_history.py` обновлён под новый формат; добавлены тесты на
  восстановление файла из версионного слота и обратную совместимость legacy-формата

**Итог блока 3:** откаты работают, данные хранятся правильно, БД не раздувается.
