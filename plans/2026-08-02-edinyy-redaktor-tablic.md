## Challenge Log

**Проблема.** Пять типов документов редактируются пятью разными таблицами через три разные точки входа, а смета вдобавок хранится в двух местах и молча расходится. Итог: непредсказуемые цифры в смете и тройная стоимость любой доработки.

**Выбранное решение.** Трёхслойный единый редактор: оболочка `DocumentEditor` (общее поведение) → адаптер документа (колонки, правила, доступные действия) → `react-data-grid` как слой отрисовки + собственный слой буфера обмена. Плюс единый источник правды по смете и одна страница на смету.

**Рассмотренные альтернативы:**

1. **Fortune-Sheet («Excel в браузере»)** — отклонено: работает с файлом, а не с данными; умная логика сметы (связь работа→материалы, пересчёт объёмов материалов, ABC, отрицательный объём, проверки) на свободных ячейках не воспроизводится. Библиотека уже в проекте и остаётся тестовой вкладкой в админке.
2. **Единый плоский формат данных для всех пяти типов** — отклонено: уничтожает умные функции сметы, ради которых продукт и существует. Пользователь выбрал вариант «одна оболочка, два адаптера».
3. **Платный грид с готовым буфером обмена (AG Grid Enterprise ~$1000/год, MUI X Premium ~$588/год)** — отклонено: $600–1000 в год за одну недостающую функцию во внутреннем инструменте на несколько человек. Свой слой буфера — ~150 строк с тестами.
4. **TanStack Table (headless)** — отклонено: пришлось бы заново писать виртуализацию, редактирование ячеек и навигацию, которые в react-data-grid уже есть и работают в проде проекта.
5. **Оставить `GenericGrid` как ядро** — отклонено: самописная таблица не умеет ни навигации по ячейкам, ни перетаскивания, ни связей между строками; дотянуть её дороже, чем удалить.

**Почему выбранное лучше.** Переиспользуем то, что уже работает (react-data-grid покрывает ~90% списка умений), удаляем 653 строки самописной таблицы и две дублирующие модалки, платим ноль за лицензии, и получаем архитектуру, в которую «разный функционал у разных типов» ложится штатно, а не костылём.

**Проверка на «код ради кода».** Каждая фаза привязана к критериям приёмки спеки. Правки, не привязанные к критериям (косметика, попутный рефакторинг соседних модулей), в этот план не входят — отдельной задачей.

## Ключевые архитектурные решения

### Модель «документ»

```ts
type DocumentKind = 'list' | 'completeness' | 'estimate' | 'optimization' | 'summary-section'

interface DocumentRef {
  cardId: string          // карточка сметы
  kind: DocumentKind      // тип документа = набор колонок и действий
  versionId?: string      // конкретная версия (по умолчанию — активная)
}
```

Единый API поверх существующих хранилищ — новый роутер `backend/app/routers/documents.py`:

| Метод | Назначение |
|---|---|
| `GET /documents/{card_id}/{kind}` | метаданные: версии, права, коэффициент, `rev`, статус задачи, кто редактирует |
| `GET /documents/{card_id}/{kind}/rows` | строки активной или указанной версии |
| `PUT /documents/{card_id}/{kind}/draft` | автосохранение черновика (без пересборки файла) |
| `POST /documents/{card_id}/{kind}/apply` | «Применить»: черновик → рабочие строки, пересборка xlsx, запись истории, `rev++` |
| `GET /documents/{card_id}/{kind}/history` | история правок |
| `POST /documents/{card_id}/{kind}/revert/{entry_id}` | откат |
| `POST /documents/{card_id}/{kind}/heartbeat` | присутствие «кто редактирует» |
| `POST /documents/{card_id}/{kind}/export` | выгрузка-ведомость |

### Схема БД (миграция 042)

     2000 строк раздувала бы базу на десятки мегабайт. Откат доступен для 10 последних
     правок, ещё 10 остаются справкой без отката.
  4. **Старый эндпоинт `PUT .../rows` теперь двигает `rev`.** На переходный период он
     пишет в те же строки; без этого открытый рядом новый редактор молча затёр бы его
     правки.
  5. **Защита от гонки сделана условным `UPDATE ... WHERE rev = client_rev`,** а не только
     сравнением в коде: между проверкой и коммитом было окно, в котором два «Применить»
     проходили оба.
  6. **`summary-section` отложен до Фазы 7** — в списке файлов Фазы 1 моделей сводной нет,
     и её хранилище (секции внутри одной записи) требует своих колонок черновика.
     Сервис спроектирован под добавление этого типа без переделки.

## Порядок и параллельность

```
Ф1 (бэкенд-фундамент)
 └─> Ф2 (ядро + перечень)
      ├─> Ф3 (одна страница)          ← можно параллельно с Ф4
      ├─> Ф4 (полнота + шапки)
      └─> Ф5 (смета, единый источник) ← только после Ф3
           └─> Ф6 (оптимизация)
                └─> Ф7 (сводная)
                     ├─> Ф8 (коэффициент + проценты)
                     ├─> Ф9 (выгрузка)      ← после Ф8 (цены с коэффициентом)
                     ├─> Ф10 (прайс)        ← можно параллельно с Ф9
                     └─> Ф11 (аналоги)      ← после Ф10
                          └─> Ф12 (чистка)
```

Ф3 и Ф4 независимы — можно вести в двух сессиях. Ф9 и Ф10 независимы между собой.
