# Снижение числа вызовов Claude в смете

Дата: 2026-07-28
Продолжение: `plans/2026-07-28-учёт-и-ограничение-web-search.md`
Research: `thoughts/research/2026-07-28-почему-смета-подорожала.md`

## Проблема

Каждый вызов Claude в смете тянет за собой платные web-поиски (22% счёта
Anthropic на замере 28.07). Значит стоимость сметы определяется **числом
запросов**, а не только объёмом текста. Мелкий чанк, лишние проходы и повторы
одного и того же запроса бьют по счёту напрямую.

## Фазы

### [x] Фаза 1 — обрезанный ответ больше не оплачивается трижды

Было: при `stop_reason = max_tokens` бросался голый `ValueError` **до**
логирования, а `_call_claude_json_with_retry` ретраил его как временную ошибку —
три полных вызова по 32k output (~$1.44), все оплаченные, все обречённые (промпт
не менялся) и ни один не попал в метрику.

- [x] `ResponseTruncatedError` — отдельный тип вместо голого `ValueError`.
- [x] usage логируется ДО падения: оборванный ответ оплачен, значит должен быть виден.
- [x] Оба ретрай-обёртчика не повторяют такой запрос (повтор бессмыслен).
- [x] `_fetch_price_chunk` и `_fetch_batch` дробят порцию пополам и считают
      половины; одна позиция — пропускается с предупреждением.

Verification: `tests/test_truncated_response.py` — типизированная ошибка,
логирование, ровно один вызов вместо трёх, дробление 5 → 2 + 3 с проставленными
ценами. На откате правок файл не собирается (нет `ResponseTruncatedError`).

### [x] Фаза 2 — один проход-добор вместо двух

Было: после основного прохода шли два отдельных прохода чанками по 5 —
пропущенные Claude и вернувшиеся с нулевой ценой. Это одна и та же проблема
«цены нет», а платили за неё дважды.

- [x] `_ids_without_price` — общий предикат для обоих случаев.
- [x] Один проход-добор, чанк `ESTIMATE_RETRY_CHUNK = 10` вместо 5. Каждая
      позиция по-прежнему получает ровно одну дополнительную попытку.

Ожидаемый эффект: до −50% запросов в фазе добора.

### [x] Фаза 3 — batch-режим больше не отдаёт смету с пустыми ценами

`resume_from_batch` был MVP «одна проходка»: что пачка пропустила или вернула с
нулевой ценой, так и уходило в Excel. В fast-режиме для этого есть добор — в
batch его не было.

- [x] Тот же добор после сбора пачки, синхронно (обычно это единицы позиций —
      второй часовой пачки ради них не нужно), чанками `ESTIMATE_RETRY_CHUNK`.
- [x] Общий `_fetch_price_chunk` вместо копии кода: fast и batch считают позиции
      одним и тем же путём, включая дробление при обрезке.
- [x] Ошибка добора (баланс) фиксирует `pre_excel`-чекпоинт до падения — пачка
      уже оплачена, пересчитывать её нельзя.

Verification: `tests/test_batch_retry_parity.py` — добор запрашивает ровно
непосчитанные позиции, не трогает уже посчитанные, не вызывается когда всё
посчитано, и сохраняет чекпоинт при падении.

### [x] Фаза 4 — порог поиска по прайсу 0.82 → 0.78

Каждая позиция, найденная в локальном прайсе, не уходит в Claude вообще — ни
токенов, ни платных поисков.

- [x] `PRICE_SIMILARITY_THRESHOLD = 0.78` в конфиге (env-настройка), в
      `price_service` берётся оттуда.

Риск: цена от похожей, но не той позиции. Поэтому значение в env — если в сметах
пойдут неверные цены, поднять обратно без деплоя кода. **После выката выборочно
проверить 10-15 позиций, подставленных из прайса.**

### [ ] Фаза 5 — размер основного чанка 10 → 15-20 (решение по данным)

Не делаем вслепую. Блок 9 скрипта замера (`safe_chunk_by_peak`) показывает,
сколько позиций влезает в `max_tokens = 32000` по худшему наблюдавшемуся ответу
с запасом 20%, и сколько вызовов подходили к лимиту вплотную
(`calls_near_limit`).

Риск обрезки после Фазы 1 перестал быть дорогим: чанк дробится пополам, а не
повторяется трижды. Поэтому решение сводится к арифметике из блока 9:
- `safe_chunk_by_peak >= 20` → ставить 15-20 смело;
- 12-15 → ставить 12 и смотреть `calls_near_limit` на следующей неделе;
- < 12 → оставить 10, лимит упирается в объём ответа, а не в наш выбор.
