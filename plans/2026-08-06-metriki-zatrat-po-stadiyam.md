# План: метрики затрат и времени по стадиям сметы

Дата: 2026-08-06
Спека: `specs/2026-08-06-metriki-zatrat-po-stadiyam.md`
Исследование: `thoughts/research/2026-08-06-metriki-stoimosti-po-stadiyam.md`
Размер: **M** (новая функция, ~10 файлов, бэкенд + фронтенд)

## Решения пользователя

1. **Видимость:** метрики видны всем ролям. Отдельного гейта не делаем.
2. **Колонка «Сумма»** в списке смет должна показывать сумму сформированной сметы
   (последняя оптимизация, иначе смета) — сейчас там всегда «—», это недоделка.
   Она входит в объём этой задачи.
3. **Подпись затрат** — «Сумма затрат», чтобы визуально отделить от суммы сметы.

## Challenge Log

**1. Решает ли это задачу?**
Все 10 критериев приёмки закрыты фазами 1–6: учёт (Ф1–Ф2), агрегация (Ф3),
контракт (Ф4), UI стадий и итогов (Ф5), колонка «Сумма» (Ф6).

**2. Самое ли это эффективное решение?**

| Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| **A. Новая таблица метрик** | явная схема | дублирует `api_call_log`, два источника правды о деньгах, расхождение с дашбордом | ✗ |
| **B. Считать на лету из `api_call_log`, отдавать в уже поллящемся списке карточек** | ноль новых таблиц, ноль новых запросов с фронта, один SQL на поллинг | список карточек чуть тяжелее | **✓ выбран** |
| **C. Отдельный endpoint `/usage` на карточку и на проект** | изоляция | +2 поллинга на экран, N+1 по карточкам, рассинхрон с уже поллящимися данными | ✗ |
| **D. Материализованная вьюха / кэш агрегатов** | быстро на больших объёмах | преждевременно: у проекта ≤100 карточек, индекс по `task_id` уже есть | ✗ (пересмотреть, если поллинг начнёт тормозить) |

Ключ к варианту B: метрики едут в `TaskBrief` внутри
`GET /api/projects/{id}/workflow-cards`, который фронт **уже** поллит каждые 5 с.
Тогда сумма по смете и сумма по проекту считаются на фронте из тех же чисел —
одной функцией в одном файле (тот же принцип, что `estimateCalc.ts`).
Новых endpoint'ов не появляется вовсе.

**3. Нет ли кода ради кода?**
Дотягивание `task_id`/`db` до шести вызовов `call_claude` выглядит побочным
рефакторингом, но без него метрика «допы» всегда 0 (AC-4 не выполняется) — это
прямо в области. Ничего сверх этого не трогаем: дашборд, промпты, редактор — нет.

## Что важно не сломать

- `ETag` на списке карточек (`workflow_cards.py:198`) — тело ответа меняется чаще
  (метрики растут), 304-ответов станет меньше. Это цена показа живых цифр;
  тело остаётся маленьким, проверить, что ETag по-прежнему считается и отдаётся.
- `lazy="raise"` на связях `WorkflowCard` — задачи грузим только через
  `selectinload`, как сейчас; в агрегатор передаём уже загруженные объекты.
- `_build_card_response` вызывается из 6 мест — новый аргумент делаем
  необязательным, чтобы одиночные ответы не падали.
- Тесты бэкенда падают по одному файлу — гонять весь набор (`pytest backend/tests`).

## Фаза 3. Один агрегатор метрик [x]

**Файл:** `backend/app/services/usage_metrics.py` — единственная точка расчёта.

```python
async def usage_for_tasks(db, tasks: list[Task]) -> dict[str, TaskUsage]
```

- один SQL: `GROUP BY task_id` по `api_call_log` с `FILTER (WHERE is_extra)`;
  токены = `input + output + cache_read + cache_creation`;
- время: `queue_seconds = started_at − created_at`, `work_seconds = finished_at − started_at`;
- задача в очереди (`started_at IS NULL`, статус активный) → `queue_seconds`
  считается «до сейчас», флаг `queue_running=True`;
- задача идёт (`finished_at IS NULL`) → `work_seconds` до «сейчас», `work_running=True`;
- задача не начата и не активна → оба `None`;
- пустой список задач → пустой словарь без обращения к БД.

**Тесты:** `backend/tests/test_usage_metrics.py` — точные числа: разделение
main/extra, суммирование токенов всех четырёх видов, время очереди и работы,
краевые (нет вызовов; не стартовала; идёт сейчас; несколько прогонов).
