# План: дата цены в прайсе

**Дата:** 01.09.2026
**Спека:** `specs/2026-09-01-data-tseny-v-prayse.md`
**Исследование:** `thoughts/research/2026-09-01-data-tseny-v-prayse.md`

## Задача

`updated_at` у позиции прайса должна означать «когда эта цена стала такой», а не
«когда запись последний раз трогали».

## Challenge Log

**1. Решает ли это проблему?**
Все четыре пути, которые сегодня двигают дату зря (PUT каталога, пакетное добавление,
загрузка файлом, перезаливка объединённого файла), правятся одним общим правилом.
Критерии приёмки 1–9 закрываются тестами, критерий 10 — правкой подписи.

**2. Самое ли это эффективное решение?**

| Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| Триггер БД / `onupdate` | ноль кода | обновляет дату на любой UPDATE — это и есть проблема | ✗ |
| Таблица истории цен (SCD-2) | полная история цен | миграция, ретеншен, новый экран; решает другую задачу | ✗ отдельная задача |
| Сравнение значений перед записью даты | минимальная правка, контракт API не меняется, правило одно на все пути | нужно не забыть в новых точках записи — закрываем модулем + тестом | ✓ |

**3. Нет ли кода ради кода?**
Правится ровно то, что двигает дату. Заодно переименовывается колонка — это не
украшательство: без него подпись «Обновлено» вводит в заблуждение (критерий 10).
Перезаливка объединённого файла (Фаза 3) — не побочный рефакторинг: без неё цель
не достигается, одна изменённая цена «обновляет» весь прайс.

## Фазы

### [x] Фаза 1. Правило «что считается изменением цены»

Новый модуль `backend/app/utils/price_change.py` — рядом с `price_min.py`
(«какая цена идёт в расчёт») и `unit_compat.py` («сводимы ли единицы»).

- `price_changed(old, new, old_unit, new_unit)` — для материала;
- `prices_changed(old: dict, new: dict, old_unit, new_unit)` — для работы;
- сравнение денег до копейки (порог 0.005), «нет цены» = None/0/мусор;
- единицы через `unit_normalizer.canonical_unit` + `lower()`; смена считается
  только между двумя непустыми написаниями.

Тесты: `backend/tests/test_price_updated_at.py` — точные числа (0.004 / 0.006),
«м²» = «кв. м» = «м2», «» → «м2» не изменение, появление/исчезновение подрядчика.

### [x] Фаза 2. Точечные пути записи

- `routers/prices_catalog.py` — PUT работ и материалов: снять старые значения до
  присваивания, дату ставить только при изменении цены.
- `services/price_bulk.py` — в `UPDATE ... values(...)` подставлять `updated_at`
  только при изменении; для материалов читать `PriceMaterial.price` (сейчас не читается).
- `models/price.py` — комментарий, почему у поля нет `onupdate`.

Тесты: критерии 1–5.

### [x] Фаза 3. Загрузка прайса файлом

- `routers/admin.py` `_upload_single` — при обновлении существующей позиции класть
  `updated_at` в values только при изменении цены.
- `routers/admin.py` `upload_combined_prices` — перед `DELETE` снять карту
  «нормализованное имя → (цена, единица, дата)», при вставке переносить старую дату,
  если цена и единица прежние.

Тесты: критерии 6–8.

### [x] Фаза 4. Подпись колонки и документация

- `frontend/src/pages/PriceCatalog.tsx` — «Обновлено» → «Цена от» на вкладках
  `all`, `works`, `materials`; на вкладках кеша подпись не трогать.
- `routers/prices_catalog.py` — заголовок выгрузки «Дата обновления» → «Цена от».
- `CLAUDE.md` — правило в список «что легко нарушить» + строка в навигации.

«переименование не двигает дату» краснеет, с включённой — зеленеет.

Миграция БД не нужна: схема не менялась, в `models/price.py` только комментарий.
