# Timeweb: архитектура деплоя и доработки в коде

**Дата:** 2026-07-24
**Связано с:** [план durable-очереди](2026-07-24-durable-task-queue.md), [spec](../specs/2026-07-24-durable-task-queue.md), [research](../thoughts/research/2026-07-24-durable-task-queue.md)
**Назначение:** зафиксировать выводы по развёртыванию на Timeweb Cloud App Platform и перечень доработок в коде, специфичных для платформы (сверх фаз плана).

---

## 1. Выводы по архитектуре на Timeweb

### 1.1. Что выбрали
- **Платформа:** Timeweb Cloud **App Platform** (PaaS, «Добавить App») — сборка из git, сервер не администрируем.
- **Способ деплоя:** **Docker Compose** (App Platform его поддерживает) — несколько контейнеров из одного `docker-compose.yml` в корне.
- **Очередь:** PostgreSQL (без Redis), claim на своей таблице `jobs`.

### 1.2. Итоговая топология
```
┌─────────────────── один App (Docker Compose) ───────────────────┐
│  web-контейнер     ← ПЕРВЫЙ сервис → получает домен/HTTPS-прокси   │
│    uvicorn app.main:app                                           │
│    гонит alembic upgrade head при старте                          │
│                                                                   │
│  worker-контейнер  ← HTTP не нужен (прокси только у первого)       │
│    python -m app.worker                                           │
│    миграции НЕ гонит                                              │
└───────────────────────────────────────────────────────────────────┘
        │                                   │
        └──────────► managed PostgreSQL ◄───┘   (DBaaS Timeweb, отдельная услуга)

  статик-фронтенд  ← отдельный App (тип Frontend/статик), как сейчас
```

### 1.3. Ключевые ограничения платформы (влияют на архитектуру)
| Ограничение Timeweb | Следствие для нас |
|---|---|
| Прокси/домен — **только у первого сервиса** в compose | `web` ставим первым; `worker` без публичного порта |
| Тарификация — **за App (конфиг сервера) целиком**, не за контейнер | web+worker в одном compose = **один тариф** (дешевле двух App) |
| Запрещены `volumes`, `privileged`, `network_mode: host`, `cap_add` и др. | контейнерный Postgres нельзя → **только managed DBaaS**; прод-compose без volume-монтирования кода |
| Редеплой = пересоздание контейнеров (SIGTERM) | нужен **graceful shutdown** worker + durable-очередь (задачи не теряются) |

### 1.4. Платные единицы
**1 App (web+worker)** + **managed PostgreSQL** + **статик-фронтенд**. (Раньше ошибочно оценивали как «три платных App» — с Docker Compose web и worker живут в одном App.)

## 2. Доработки в коде под Timeweb (сверх фаз плана)

Ниже — то, что нужно именно из-за платформы/managed-БД, дополнительно к 5 фазам плана.

### 2.1. Прод-compose без запрещённых директив `[ ]`
- Новый `docker-compose.yml (корневой, прод)` в корне (App Platform читает из корня):
  - `web`: команда `sh -c "alembic upgrade head && uvicorn app.main:app --host 0.0.0.0 --port ${PORT:-8000}"`, **без** `volumes`, **без** `--reload`.
  - `worker`: команда `python -m app.worker`, без портов, без volumes.
  - Оба — образ из `backend/Dockerfile`.
  - Никаких `db`-контейнеров (база managed).
- Локальный `docker-compose.yml` оставить как есть для разработки (там volumes/reload допустимы).
- Проверка: `docker compose -f docker-compose.yml (корневой, прод) config` — валиден, запрещённых директив нет.

### 2.2. Один владелец миграций (убрать гонку) `[ ]`
- Сейчас `alembic upgrade` гонится в ДВУХ местах: `backend/Dockerfile` CMD и `app/main.py` lifespan (`main.py:125-128`).
- При двух контейнерах (web+worker) это гонка. Решение:
  - Миграции — **только в команде `web`** (compose command), убрать `alembic upgrade` из `main.py` lifespan.
  - `worker` миграции не запускает.
- Первый деплой: применить миграции руками/через web до старта worker (или worker ретраит коннект — см. 2.3).

### 2.3. Worker: ретрай подключения к БД на старте `[ ]`
- App Platform не гарантирует порядок старта контейнеров, а managed-БД может «прогреваться».
- В `app/worker.py` — цикл ретраев коннекта к Postgres (экспоненциальный бэкофф) перед входом в poll-loop, чтобы worker не падал, пока web накатывает миграции / БД поднимается.

### 2.4. SSL к managed PostgreSQL `[ ]`
- Managed-БД Timeweb обычно требует TLS. Драйвер — asyncpg.
- Проверить строку `DATABASE_URL`: возможно, нужен `?ssl=require` (asyncpg-стиль) или `connect_args={"ssl": ...}` в `create_async_engine` (`database.py:17-31`). Сейчас в `database.py` SSL не настроен — заложить параметр из env (`DB_SSL_MODE`), не ломая локальную разработку (локально SSL не нужен).

### 2.5. Graceful shutdown worker по SIGTERM `[ ]`
- Редеплой Timeweb шлёт SIGTERM. Worker должен:
  - перестать брать новые job,
  - дать текущим либо дойти, либо корректно отпустить claim (вернуть job в `queued`),
  - остановить APScheduler (`scheduler.shutdown()`).
- Реализовать обработчик сигналов в `app/worker.py`. (Durable-очередь + reclaim это подстрахуют, но чистый shutdown уменьшает «подвисшие running».)

### 2.6. Пул asyncpg под число воркеров `[ ]`
- Сейчас `pool_size=5, max_overflow=10` (`database.py:20-23`) на процесс.
- worker с `WORKER_CONCURRENCY` слотов + heartbeat + внутризадачные запросы легко упрётся. Поднять пул (env `DB_POOL_SIZE`/`DB_MAX_OVERFLOW`), считать: слоты × (сессия job + heartbeat) + запас.
- Учесть **лимит соединений managed-БД** Timeweb (у тарифа есть потолок) — суммарно web-пул + worker-пул + поллеры ≤ лимита.

### 2.7. Переменные окружения в панели Timeweb `[ ]`
Задать для App (общие web+worker, если платформа позволяет общие; иначе продублировать):
- `DATABASE_URL` (managed, с SSL), `ANTHROPIC_API_KEY`, `COHERE_API_KEY`, `JWT_SECRET`, `USERS`/`ADMIN_PASSWORD` (см. Phase 0), `CORS_ORIGINS` (новый домен), новые: `WORKER_CONCURRENCY`, `ANTHROPIC_MAX_CONCURRENCY`, `FAST_CHUNK_CONCURRENCY`, `JOB_VISIBILITY_TIMEOUT_S`, `JOB_POLL_INTERVAL_S`, `JOB_MAX_ATTEMPTS`, `DB_POOL_SIZE`, `DB_MAX_OVERFLOW`, `DB_SSL_MODE`.
- Секреты — только через панель (в git не коммитить).

### 2.8. CORS и домен фронтенда `[ ]`
- `CORS_ORIGINS` (`config.py`) → новый домен фронтенда на Timeweb.
- Фронтенд `VITE_API_BASE_URL` → новый домен backend-App.
- Обновить после того, как Timeweb выдаст домены (аналог текущих значений в `render.yaml:20,32`).

### 2.9. Healthcheck-эндпоинт `[ ]`
- App Platform может пинговать web для проверки живости. Убедиться, что есть лёгкий `/health` (или `/`) без обращения к тяжёлым сервисам; worker в проверках не участвует (нет прокси).

### 2.10. Логи в stdout `[ ]`
- Платформа собирает логи из stdout/stderr. `structlog` уже есть — проверить, что и web, и worker пишут в stdout (worker — новый процесс, настроить логирование симметрично web).

### 2.11. Судьба render.yaml `[ ]`
- После переезда `render.yaml` устаревает. Либо пометить комментарием «legacy, см. Timeweb», либо привести в соответствие (web+worker), чтобы не путать. Не удалять до подтверждённого переезда.

## 3. Порядок первого деплоя на Timeweb (черновик рантбука)
1. Создать managed PostgreSQL (DBaaS), получить `DATABASE_URL` (+ SSL).
2. Создать App (Docker Compose) из репозитория, ветка/коммит, `docker-compose.yml (корневой, прод)`.
3. Прописать env-переменные (раздел 2.7) в панели.
4. Первый деплой: поднимется `web` → накатит миграции `030`,`031`; `worker` дождётся БД (ретрай) и войдёт в poll-loop.
5. Создать индивидуальные аккаунты (Phase 0: через `USERS` env или admin-эндпоинт).
6. Обновить `CORS_ORIGINS` и `VITE_API_BASE_URL` под выданные домены, передеплоить фронтенд.
7. Смоук-тест: логин под личным аккаунтом → поставить 2–3 задачи разными юзерами → убедиться, что worker исполняет параллельно и round-robin работает; проверить, что редеплой не теряет задачу.
