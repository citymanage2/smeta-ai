# План: Аккаунты сотрудников и матрица прав доступа (RBAC)

**Дата:** 2026-07-26
**Статус:** черновик (ожидает аннотаций пользователя перед реализацией)
**Размер:** L (изменение auth, новый сервис прав, 10+ файлов, миграция данных)

## Спецификация (WHAT & WHY)

### Проблема
Сейчас вход — по общим паролям ролей (`USER_PASSWORD`/`ADMIN_PASSWORD` в env). Все аутентифицированные видят все проекты и задачи. Нет персональной ответственности: непонятно, чей проект, кто что делает. Админ входит только по паролю, без логина.

### Цель
Персональные аккаунты сотрудников с логином/паролем, три роли и матрица прав. Каждый проект и задача принадлежат сотруднику. Изоляция данных по владельцу с учётом роли.

### Роли и матрица прав

| Действие | Проектный менеджер (`project_manager`) | Руководитель отдела продаж (`head_of_sales`) | Админ (`admin`) |
|---|---|---|---|
| Видеть свои проекты/задачи (активные + архив) | ✅ | ✅ | ✅ |
| Видеть чужие проекты/задачи (активные + архив) | ❌ | ✅ (все) | ✅ (все) |
| Редактировать свои | ✅ | ✅ | ✅ |
| Редактировать чужие | ❌ | ✅ | ✅ |
| Архивировать / вернуть из архива | ✅ (свои) | ✅ (любые) | ✅ (любые) |
| Переназначать владельца проекта/задачи | ❌ | ✅ | ✅ |
| Управлять аккаунтами (создать/роль/сброс пароля/деактивация) | ❌ | ❌ | ✅ |

**Пояснения к развилкам (по ответам пользователя):**
- Доступ **везде по владельцу + роли**. Концепции «данные, видимые всем» нет.
- **Архив** — ортогональное состояние (`is_archived`): проект/задача вручную перемещается в архив, **не показывается в основной панели**, доступен только в разделе «Архив». Видимость в архиве — **та же, что в активных** (ПМ — своё, РОП/админ — всё).
- **Архивирует тот, кто может редактировать:** ПМ — своё, РОП/админ — любое.
- РОП — **полный доступ** ко всем проектам/задачам + **переназначение владельца**. Управление аккаунтами — нет.
- Аккаунтами управляет **только админ**.
- **Старые данные** переносятся на аккаунт админа и помечаются `is_archived=true` → лежат в архиве админа (ПМ их не видит, панель у ПМ чистая).

### Критерии приёмки
1. Админ входит по **логину + паролю** (`ADMIN_USERNAME` + `ADMIN_PASSWORD`), получает полный доступ и `owner_id`.
2. Существуют три роли: `admin`, `head_of_sales`, `project_manager`.
3. Каждый **новый** проект и задача получают `owner_id = создатель` при создании (`is_archived=false`).
4. ПМ через API/UI видит только свои проекты/задачи (активные и архивные); чужое — 404/403, не в списках.
5. РОП и админ видят все проекты/задачи; могут редактировать любые и переназначать владельца.
6. **Архив:** проект/задачу можно вручную архивировать/вернуть (право = право правки). Архивные скрыты из основной панели, видны только в разделе «Архив». Видимость в архиве = как в активных.
7. Все **существующие** проекты/задачи (owner NULL) привязаны к админу и помечены `is_archived=true` (в архив админа).
8. Админ управляет аккаунтами: создать сотрудника (логин, ФИО, роль, пароль), сменить роль, сбросить пароль, деактивировать.
9. Деактивированный сотрудник не может войти; его проекты/задачи сохраняются (owner_id не теряется).
10. Frontend: поле логина на входе, страница «Сотрудники» (только админ), метка владельца на карточках, раздел «Архив» с действием архивировать/вернуть, фильтр по владельцу и переназначение (РОП/админ).
11. Обратная совместимость: legacy-вход по общему паролю продолжает работать в переходный период (не ломаем прод до смены env).

### Non-Goals
- Никакого внешнего policy-движка (Casbin/OPA) — избыточно для 3 ролей.
- Никаких команд/иерархий сотрудников (плоская модель: владелец + роль).
- Никакого аудита действий/логов доступа (отдельная задача при необходимости).
- Двухфакторная аутентификация — вне объёма.

### Ограничения
- Роль в JWT-payload (`role`) и колонках БД (`users.role`, `tasks.user_role`) сейчас `VARCHAR(10)` — значение `project_manager` (14) и `head_of_sales` (13) не влезают → расширить колонки.
- `owner_id` при удалении пользователя = `SET NULL`. Поэтому удаление — **soft (is_active=false)**, чтобы не осиротить данные.
- Backfill владельца-админа возможен только в рантайме (id админа известен после сидинга), не в самой миграции.

## Challenge Log (bulletproof Stage 3)

**1. Решает ли проблему?** Да — каждый критерий приёмки покрыт фазой (см. трассировку в конце фаз).

**2. Самое ли эффективное решение?** Рассмотрены альтернативы:
- **(A) Внешний RBAC-движок (Casbin/oso).** Плюс: гибкие политики. Минус: новая зависимость, кривая обучения, оверкилл для 3 ролей и одного измерения (владелец). ❌
- **(B) Отдельная таблица прав/ACL на каждый ресурс.** Плюс: гранулярно. Минус: сложно, не нужно — доступ выводится из `owner_id` + `role`. ❌
- **(C) [ВЫБРАНО] Роль в JWT + `owner_id` на ресурсах + чистые SQL-фильтры видимости в одном модуле `permissions.py`; `is_archived` — ортогональный флаг.** Переиспользует уже готовую инфраструктуру (`Task.owner_id`, `current_user_id()`). Минимум нового кода, вся логика в одном месте. ✅

**3. Нет ли «кода ради кода»?** Каждое изменение привязано к критерию. `full_name`/`is_active` — не украшательство: ФИО нужно для меток владельца (крит. 10), `is_active` — для деактивации без осиротения (крит. 9). `is_archived` — крит. 6/7. Drive-by рефакторинг не делаем.

## Технический подход

### Значения ролей
Канонические: `admin`, `head_of_sales`, `project_manager`. Legacy `user` трактуется как `project_manager` (наименьшие права). Расширить `users.role` и `tasks.user_role` до `VARCHAR(32)`.

### Модуль прав — `backend/app/utils/permissions.py` (новый)
Единая точка правил:
```
ROLE_ADMIN, ROLE_SALES_HEAD, ROLE_PM = "admin", "head_of_sales", "project_manager"
MANAGER_ROLES = {ROLE_ADMIN, ROLE_SALES_HEAD}   # видят/правят всё

def is_manager(role) -> bool
def project_visibility_filter(user) -> ColumnElement | None   # None = без фильтра (менеджер)
def task_visibility_filter(user) -> ColumnElement | None
def can_edit_project(user, project) -> bool
def can_edit_task(user, task) -> bool
def can_reassign(role) -> bool                                 # менеджеры
```
Фильтр видимости ПМ: `owner_id == uid`. Правка ПМ: `owner_id == uid`. Менеджер: без фильтра (всё).
`is_archived` — **ортогонален** правам: не влияет на видимость/правку, только определяет раздел (активные `is_archived=false` / архив `is_archived=true`). Списки по умолчанию отдают `is_archived=false`; раздел «Архив» — `is_archived=true`. Действие архивации/возврата разрешено, если `can_edit_*`.

### Зависимости FastAPI (`utils/auth.py`)
- Оставить `get_admin_user`.
- Добавить `get_manager_user` (admin | head_of_sales) — для переназначения.
- `current_user_id()` уже есть.

### Сидинг админа с логином (`main.py::_initialize_users`)
Добавить `ADMIN_USERNAME` (env, дефолт `admin`). Создать/обновить именованный аккаунт `admin` с ролью `admin` и `ADMIN_PASSWORD` — это **бутстрап** первого админа (иначе некому создавать аккаунты в UI). Этот аккаунт — **канонический владелец** для backfill.
**Убрать** парсинг env-переменной `USERS` из `_initialize_users` (решение пользователя: аккаунты сотрудников — только через UI). Саму настройку `USERS` в `config.py` пометить deprecated/удалить.

### Backfill старых данных (рантайм, после сидинга админа)
Идемпотентно:
```
UPDATE projects SET owner_id=<admin_id>, is_archived=true WHERE owner_id IS NULL;
UPDATE tasks    SET owner_id=<admin_id>, is_archived=true WHERE owner_id IS NULL;
```
После перехода новые строки всегда с owner_id, поэтому условие `IS NULL` больше не срабатывает.

## Фазы

### Фаза 1 — Модель данных и миграция `[ ]`
- `models/user.py`: `role`→`String(32)`; добавить `full_name String(100) nullable`, `is_active Boolean default true`.
- `models/project.py`: добавить `owner_id Integer FK users.id ON DELETE SET NULL, nullable, index`; `is_archived Boolean default false, index`.
- `models/task.py`: добавить `is_archived Boolean default false, index`; `user_role`→`String(32)`.
- Миграция `036_employee_accounts_rbac.py` (всё через `IF NOT EXISTS` / `ALTER COLUMN TYPE`): расширение `role`/`user_role`, новые колонки, индексы. Данные (backfill владельца) — **не здесь**, а в рантайме.
- Gates: `py_compile`, `alembic upgrade head` на чистой БД, `ruff`.

### Фаза 2 — Auth-ядро и права `[ ]`
- `config.py`: `ADMIN_USERNAME: str = "admin"`; убрать/deprecate `USERS`.
- `utils/permissions.py` (новый) — правила и фильтры.
- `utils/auth.py`: `get_manager_user`.
- `main.py::_initialize_users`: сидинг именованного админа (бутстрап); убрать парсинг `USERS`; **backfill** старых проектов/задач на админа + `is_archived=true`.
- `routers/auth.py`: логин уже поддерживает username+password — проверить, что именованный админ входит; корректный `expires_in`.
- Тесты: вход админа по логину; фильтры прав (unit на `permissions.py`).

### Фаза 3 — Изоляция данных в роутерах `[ ]`
Применить фильтры видимости и проверки правки во всех эндпоинтах, отдающих/меняющих проекты и задачи:
- `routers/projects.py` — списки/деталь/апдейт/удаление; при создании `owner_id=current_user`. Списки фильтруют `is_archived=false` по умолчанию, `?archived=true` — архив.
- `routers/tasks.py` — списки/деталь/мутации; убедиться, что создание ставит `owner_id`; фильтр `is_archived`.
- `routers/workflow_cards.py`, `routers/summary.py`, `routers/estimate_versions.py`, `routers/results.py`, `routers/dashboard.py` — фильтрация по владельцу задачи/проекта.
- **Архивация:** `PATCH /projects/{id}/archive` и `PATCH /tasks/{id}/archive` (body `{archived: bool}`) — разрешено, если `can_edit_*`.
- **Переназначение владельца:** `PATCH /projects/{id}/owner` и `PATCH /tasks/{id}/owner` — только `get_manager_user`.
- Тесты: ПМ не видит чужое (404); архивные скрыты из активных списков и видны в `?archived=true`; РОП видит всё и переназначает; ПМ не может переназначить (403), но может архивировать своё.

### Фаза 4 — Управление аккаунтами (админ) `[ ]`
- `routers/admin_users.py` (новый, `get_admin_user`): `GET /admin/users`, `POST /admin/users`, `PATCH /admin/users/{id}` (роль/ФИО/is_active), `POST /admin/users/{id}/reset-password`. Удаление — через `is_active=false`.
- Валидация: уникальность username, роль из допустимого множества, нельзя деактивировать/разжаловать последнего админа.
- Тесты: CRUD; не-админ получает 403; защита последнего админа.

### Фаза 5 — Frontend `[ ]`
- `stores/auth.ts`: хранить `role`, вычислять `isManager` (admin|head_of_sales), `isAdmin`.
- Экран входа: поле «Логин» + «Пароль» (username опционален для legacy).
- `ProtectedRoute`: поддержка `requireAdmin`/`requireManager`.
- Страница «Сотрудники» (только админ): список, создание, смена роли, сброс пароля, деактивация.
- Карточки проектов/задач: метка владельца (ФИО), кнопка «В архив»/«Вернуть», фильтр по владельцу (менеджеры), кнопка «Переназначить» (менеджеры).
- Раздел/переключатель «Архив» (активные ↔ архив) в панели проектов и задач.
- Gates: `tsc --noEmit`, `lint`.

### Фаза 6 — Интеграция, ревью, безопасность `[ ]`
- Прогон всех тестов (backend `pytest`, frontend). Impact-анализ: не сломаны ли legacy-вход, worker (`Job.owner_id`), скачивание файлов.
- Проверка отсутствия IDOR: прямой доступ по id к чужому ресурсу → 404/403 во всех роутерах.
- `/security-review` или semgrep.
- Обновить `.business/история/…`, memory (архитектура прав).

**Как завести руководителя и менеджеров:** админ входит по своему логину (`ADMIN_USERNAME`/`ADMIN_PASSWORD`) → страница «Сотрудники» → создать аккаунты (логин, ФИО, роль head_of_sales / project_manager, пароль). Env `USERS` не используется.

## Инкремент 3 (2026-07-28) — доархивация старых данных

По факту эксплуатации: старые задачи, созданные под общими аккаунтами (owner = shared user, а не NULL), не попадали в архив и висели активными как «Ответственный: #N».
1. **Backfill расширен** (`_initialize_users`): в архив админа переносятся не только `owner_id IS NULL`, но и данные под аккаунтами без логina (`username IS NULL` — деактивированные общие). Реальные аккаунты не трогаются. Идемпотентно.
2. **`PATCH /tasks/{id}/archive`** (новый) — архивировать/вернуть задачу «Без проекта»; право = право редактирования.
3. **Фронтенд:** во «Входящем» переключатель «Активные / Архив» для задач без проекта; кнопка «В архив» на карточке; «Вернуть из архива» в архивном виде. `getUnassignedTasks(archived)`, `archiveTask(id, archived)`.
Тесты: архивация задачи (своя/чужая, скрытие из активных/показ в архиве), backfill shared-owned → админ+архив.
