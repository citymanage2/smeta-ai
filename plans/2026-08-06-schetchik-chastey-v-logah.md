# Счётчик частей в истории обработки

## Проблема

На этапе расчёта цен смета уходит в Claude чанками («частями»). Счётчик «готово N из M»
живёт только в строке статуса (`update_progress_message` — намеренно мимо `progress_log`,
иначе тик раз в 10 секунд раздул бы историю на сотни строк).

Следствия:

1. **В истории обработки счётчика нет вообще.** Видно «Отправляем 9 чанк(а) в Claude…»,
   а сколько из них вернулось — нет. Задача встала на паузу по балансу — в логе только
   «⏸ На паузе: баланс API исчерпан», без единой цифры о проделанной работе.
2. **После возобновления кажется, что всё считается заново.** Строка «Отправляем 9 чанк(а)»
   печатает `len(chunks)` — полный список, хотя в Claude уходит только `pending` (позиции
   без сохранённого ответа). Если бы часть чанков была посчитана, пользователь всё равно
   увидел бы «9» и решил, что платит второй раз.
3. **При ошибке и таймауте — та же слепота.**

Механика возобновления при этом исправна: `claude_results` восстанавливаются из чекпоинта
`claude_partial` (`task_processor.py:2769`), `_pending_chunks` вычитает посчитанные позиции.
Проблема только в том, что этого не видно.

## Цель

В истории обработки на каждой вехе видно, сколько частей посчитано и сколько осталось —
и в процессе, и при паузе, и при ошибке. Пользователь может сам убедиться, что после
возобновления оплачивается только остаток.

## Критерии приёмки

1. Строка запуска этапа печатает **реальное** число отправляемых частей и, если что-то
   восстановлено из чекпоинта, сколько позиций уже посчитано и не оплачивается повторно.
2. После каждой группы чанков (там же, где пишется чекпоинт) в историю идёт строка вида
   «Части: посчитано X из Y, осталось Z».
3. При обрыве группы (пауза по балансу, ошибка чанка, таймаут) такая же строка попадает
   в историю до того, как задача сменит статус.
4. Сообщение о паузе по балансу содержит счётчик частей, если этап чанков успел начаться.
5. То же для сообщений об ошибке и о превышении срока этапа.
6. Повторный проход по позициям без цены («Повторный расчёт») ведёт свой счёт и не
   сбрасывает счётчик основного прохода в ноль.
7. Живая строка статуса по-прежнему идёт мимо истории — никаких сотен строк.

## Вне рамок

- Изменения логики возобновления и чекпоинтов: она корректна, меняем только видимость.
- Счётчик в других типах задач (перечень, полнота, оптимизация) — там свои этапы;
  трогаем только сообщения, общие для всех (пауза/ошибка), и то лишь если счётчик задан.

## Фазы

### [x] Фаза 1. Тесты (red)

`backend/tests/test_chunk_tally_visible.py`:

- `_chunk_tally_line` формирует «посчитано X из Y, осталось Z» и пустую строку без данных;
- после группы чанков веха попадает в `update_progress` (история), а не только в статус;
- при исключении внутри группы веха пишется до проброса ошибки;
- сообщение о паузе по балансу содержит счётчик, когда он задан, и не ломается без него.

### [x] Фаза 2. Реализация (green)

- `TaskProcessor._chunk_tally` + `_set_chunk_tally` / `_note_chunk_progress` /
  `_chunk_tally_line`.
- В шаге 2 сметы: счёт по `pending`, веха после каждой группы и при обрыве, честная строка
  запуска с числом восстановленных позиций.
- В `run()`: дописывать счётчик к сообщениям паузы, ошибки и дедлайна.

### [x] Фаза 3. Gates

`pytest` целиком (по памяти проекта — только весь набор), `ruff check`.

```
Прайс: 10 позиций найдено, 137 — нет. Отправляем 9 чанк(а) в Claude...
Расчёт цен: посчитано 8 из 9 частей, осталось 1.
⏸ На паузе: баланс API исчерпан. … Расчёт цен: посчитано 8 из 9 частей, осталось 1.
```

```
Прайс: 10 позиций найдено, 137 — нет. Отправляем 1 чанк(а) в Claude...

```
