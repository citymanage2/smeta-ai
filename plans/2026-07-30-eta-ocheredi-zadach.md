**2. Самое ли эффективное решение?**
Рассмотрены (детали — в исследовании): жёсткие константы; медиана по типу без объёма;
линейная модель с калибровкой + симуляция очереди; ML-регрессия.
Выбрана линейная модель с калибровкой и симуляцией: единственная, которая учитывает
объём (прямое требование) и не устаревает при смене промптов/модели. Константы врали бы
уже через месяц, медиана без объёма игнорирует разброс ×40 между перечнями, ML — оверкилл
при десятках наблюдений в неделю.

**3. Нет ли кода ради кода?**
- Не трогаем порядок очереди, приоритеты, число воркеров.
- Не вводим настройки коэффициентов в UI — калибровка автоматическая.
- Не переписываем `DashboardQueue`, добавляем одну колонку.
- Поля `started_at`/`finished_at` — не «на будущее», без них калибровка невозможна:
  `updated_at - created_at` включает многочасовое ожидание в очереди.

## Модель прогноза (суть)

```
длительность(задача) = база(тип) + ставка(тип) × объём

ставка(тип)  = медиана по последним завершённым задачам того же типа:
               (факт_длительность − база) / объём;
               нужно ≥3 наблюдения, иначе — дефолт (прогноз помечается «грубый»);
               результат зажат в [0.2×дефолт, 5×дефолт] — защита от мусорных выборок.

ожидание     = симуляция list-scheduling по WORKER_CONCURRENCY слотам:
               слоты заняты бегущими задачами (их остатком), очередь разбирается
               по created_at; batch-задачи слот не занимают.
```

Для уже считающейся задачи, если в `progress_data` есть честная доля выполненных чанков
(≥15%), остаток берётся экстраполяцией по факту, а не по модели: `остаток = прошло × (1−доля)/доля`.

Ключ калибровки — `(task_type, processing_mode)`: batch-режим `ESTIMATE_FROM_LIST` живёт по
другим таймингам (пачка считается на серверах Anthropic).

## Риски и что с ними делаем

| Риск | Решение |
|---|---|
| Round-robin по владельцу ≠ порядок по `created_at` | Симуляция приблизительна, в UI везде «≈» |
| Пауза по балансу / ретраи растягивают факт | Медиана + клампы гасят выбросы |
| Резюмированная задача даёт заниженную ставку | `started_at` пишется на каждый прогон; клампы ограничивают перекос |
| Пробинг xlsx на 50 МБ тормозит создание | `read_only=True` + `asyncio.to_thread` + ошибка ⇒ `None` |
| Лишняя нагрузка на `/dashboard/stats` | Одна калибровка на запрос (200 строк), симуляция в памяти |

## Что всплыло по ходу и было исправлено

1. **Тяжёлый `progress_data`.** Первая версия грузила активные задачи целиком, а
   там лежат позиции сметы и OCR-текст страниц — мегабайты. При опросе статуса
   раз в 3 с это было бы дорого. Введён `TaskSnapshot`: из JSON достаются только
   четыре скаляра (`_stage`, `batch_id`, `chunks_done`, `total_chunks`)
   через JSON-доступ, работающий и на JSONB, и на SQLite.
2. **ETag канбан-доски.** Посекундный прогноз менял бы тело ответа на каждом
   опросе и убивал 304-ответы. Прогноз округляется до минуты, абсолютное время
   кладётся на минутную сетку.
3. **Дозапуски портили калибровку.** Оптимизация и «исправить пустые цены»
   работают по уже посчитанной смете и меняют статус в обход
   `TaskProcessor.update_status`. Теперь они ставят `started_at` (чтобы прогноз
   для них был живым) и гасят `finished_at` — короткий дозапуск не попадает в
   калибровку как «расчёт сметы целиком».
4. **Дашборд не был покрыт тестами** из-за `date_trunc` (PostgreSQL-функция).
   Добавлены `type_=DateTime` в запрос и SQLite-заглушка `date_trunc` в
   `conftest.py` — эндпоинт очереди теперь тестируется целиком.

## Итог

Реализовано целиком, все шесть фаз закрыты.

- **Как было:** в очереди видно только «висит 5 ч 57 мин» — непонятно, ждать или отменять.
- **Как стало:** видно «старт ≈ через 25 мин» и «≈ 14:10 (через 40 мин)» — в активной
  очереди, на карточке задачи и на карточках канбана. Оценка строится по объёму
  (позиции / страницы / строки) и самокалибруется по фактическим длительностям.

Осталось за рамками (сознательно, см. Non-Goals спеки): прогноз для задач на паузе,
учёт ретраев, точность «до минуты», уведомления о готовности.
