## Контекст и цель

Текущий поиск похожих позиций в прайсе (`_semantic_match_work/material`) отправляет
200 названий в Claude при каждом поиске. При 50 позициях в смете = 50 API-вызовов Claude
только на семантический матч — медленно и дорого.

**Цель:** заменить Claude-семантику на embedding-поиск через OpenAI:
- Векторы генерируются **один раз** при загрузке прайса
- Поиск — мгновенное сравнение чисел в памяти, без API-вызовов
- Claude полностью убирается из цепочки поиска по прайсу

**Цепочка поиска после изменений:**
```
Точное совпадение → Embedding-поиск (OpenAI) → Веб-поиск (Claude)
```

## Область применения — ВАЖНО

Поиск по прайсу (в том числе через embeddings) определяется **типом результата задачи**,
а не типом самой задачи.

**Правило:** прайс используется когда результат задачи — это **смета** или **оптимизированная смета**.

| Результат задачи | Использует прайс? | Пример |
|---|---|---|
| Перечень позиций (список) | Нет | `LIST_FROM_GRAND` — создаёт перечень из Гранд-сметы |
| Смета (estimate) | Да | будущие типы задач, где результат = готовая смета с ценами |
| Оптимизированная смета | Да | `/optimize/run` — текущий функционал |

**Текущее состояние (2026-04-10):**
Задач с результатом "смета" пока нет. Единственное место где вызывается прайс —
`_run_optimization_background` в `tasks.py` (оптимизированная смета).

**Будущее:** когда появятся задачи с результатом "смета", они также должны будут
вызывать `price_service` для подстановки цен из прайса.

**Где прайс НЕ используется:**
- `LIST_FROM_GRAND` — результат перечень, не смета → прайс не нужен
- Любая задача, результатом которой является не смета

Таким образом, все изменения этого плана затрагивают только:
1. `price_service.py` — сам поиск
2. `admin.py` — загрузка прайса и генерация векторов
3. `_run_optimization_background` в `tasks.py` — единственный текущий вызывающий код
4. Фронтенд панели администратора — управление прайс-листами

## Технические решения

| Решение | Выбор | Обоснование |
|---|---|---|
| Embedding-модель | `text-embedding-3-small` (OpenAI) | Дешёво, быстро, отличное качество для русского |
| Хранение векторов | JSONB-колонка в `price_works` и `price_materials` | Генерируются один раз, не пересчитываются на старте |
| Поиск | numpy cosine similarity в памяти | 3 000–15 000 позиций = ~18–90 МБ RAM, достаточно |
| Порог совпадения | 0.82 (настраиваемая константа) | Ниже — веб-поиск; выше — возвращаем цену |
| Нормализация | `normalize_name()` перед embedding | М-100, M defi 100, м 100 → М100 |

## Требования к нормализации названий

Функция `normalize_name(text)` применяется **везде перед генерацией вектора** —
и при загрузке прайса, и при поиске из сметы. Важно: применять одинаково в обоих местах.

Правила нормализации:
- Латинские буквы, совпадающие с кириллическими, заменяются на кириллические (M → М, C → С)
- Марки материалов приводятся к единому виду: `М-100`, `M defi 100`, `м 100` → `М100`
- Двойные пробелы убираются, текст strip-ается
- Регистр приводится к нижнему для сравнения (оригинал сохраняется для отображения)

Пример:
- "Кладка кирпичная M defi 100" → "кладка кирпичная М100"
- "Кладка кирпичная М-50" → "кладка кирпичная М50"
- Эти два дают разные векторы → не перепутаются
- "M defi 100" и "М100" дают одинаковый вектор → совпадут

### ФАЗА 3 — Поиск по векторам

- [x] **3.1** Заменить `_semantic_match_work` на `_embedding_match_work(name: str)`:
  1. Если `_works_embeddings is None` — вернуть `None` (нет векторов → веб-поиск)
  2. Нормализовать `name` через `normalize_name()`
  3. Один вызов OpenAI: `generate_embedding(normalized_name)` через `asyncio.to_thread`
  4. Cosine similarity: `scores = np.dot(_works_embeddings, query_arr) / (_works_row_norms * query_norm)`
  5. Найти `best_idx = np.argmax(scores)`
  6. Если `scores[best_idx] >= SIMILARITY_THRESHOLD` (0.82) — вернуть `_works_cache[best_idx]`
  7. Иначе — вернуть `None`

## Важные детали реализации

**Batch size:** OpenAI embeddings API принимает до 2 048 текстов за один вызов.
При 3 000+ позициях — разбивать на чанки по 2 000.

**Dimension:** `text-embedding-3-small` возвращает вектор размерности 1 536.
Каждая строка в БД = 1 536 float64 ≈ 12 КБ в JSONB.
3 000 строк = ~36 МБ в БД, ~18 МБ в numpy (float32).

**В памяти хранить float32, не float64** — в два раза легче, точности достаточно для cosine similarity.

**Нормы строк** предвычислять при `load_cache`, не при каждом поиске:
```python
_works_row_norms = np.linalg.norm(_works_embeddings, axis=1)  # shape (N,)
```
