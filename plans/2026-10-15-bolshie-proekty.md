# План: проекты до 100 МБ — загрузка и обработка

**Спека:** `specs/2026-10-15-bolshie-proekty.md`
**Исследование:** `thoughts/research/2026-10-15-bolshie-proekty.md`
**Статус:** planning

## Challenge Log

**Проблема.** PDF проектной документации больше ~10 МБ (десятки листов
чертежей) не превращается в перечень. «Перечень из проекта» шлёт каждый лист в
7500 px и все листы в каждый запрос, а это упирается в лимиты Claude: 10 МБ на
картинку, 32 МБ на запрос, ≤2000 px при >20 картинках. Загрузка тоже не готова к
100 МБ: на доске нет серверного лимита и прогресса, на «Новой задаче» стоит 20 МБ.

**Выбранное решение.**
1. Листы рендерятся в **нативном разрешении модели** — тем же расчётом, которым
   API сам ужимает картинку (`resized_size` из документации Anthropic, high-res
   tier: 2576 px / 4784 токена). Модель видит то же, что сейчас, а запрос в
   5–7 раз легче.
2. Листы разбиваются на **пачки** (≤20 картинок, ≤24 МБ base64). Влезли в одну
   пачку — поведение прежнее. Не влезли — проход 1 и проход 2 идут по пачкам, у
   прохода 2 свой промпт, где «листа нет среди переданных» — законный null.
3. Листы лежат во временной папке на диске, рендер в отдельном потоке.
4. Загрузка: своя константа лимита проекта (100 МБ), чтение с лимитом на
   сервере, процент загрузки на доске, текст ошибки сервера. Если замер покажет,
   что прокси режет меньше 100 МБ, — загрузка частями (фаза 3б).

**Рассмотренные альтернативы.**
1. *Только уменьшить разрешение до 2576 px.* Отклонено: при >20 листах API всё
   равно требует ≤2000 px, а ~10 плотных листов снова дают 32 МБ.
2. *Files API, все листы ≤2000 px к каждому вызову.* Отклонено: бета;
   посредник обхода геоблока может не пропускать `/v1/files`; 150 листов ×
   3,7 тыс. токенов = 550 тыс. токенов на вызов, это упор в ITPM и потолок
   контекста; не масштабируется дальше ~250 листов.
3. *PDF целиком document-блоком.* Отклонено: 100/600 страниц, каждая страница —
   текст + картинка (до ~7 тыс. токенов), большой проект не влезает в контекст;
   разрешение растра выбирает сервер.
4. *Загрузка presigned PUT прямо в S3.* Отложено до замера: требует CORS на бакете
   Timeweb (настройка инфраструктуры пользователем-нетехником), сирот в бакете и
   двухфазного создания задачи. Нужна, только если прокси режет запрос.

**Почему так.** Пачки в нативном разрешении снимают все три лимита API при любом
числе листов, ничего не теряя в том, что видит модель, и не меняют поведение для
проектов, которые уже считаются. Загрузка меняется ровно настолько, насколько
этого требует измеренный лимит прокси.

### Дополнение 15.10.2026: разделы проекта

**Проблема.** Перечень из проекта «пропускает разделы и делает всё одним
файлом»: считается только первый PDF; раздел пишется лишь в примечание, поэтому
в файле один лист; дубль ищется по «имя + тип» на весь проект и выбрасывает
одноимённую позицию другого раздела; упавшая часть PDF (кроме первой)
пропускается молча; полнота по проекту лист не проставляет.

**Выбранное решение** (решения пользователя 15.10.2026: лист на раздел в одном
файле; сбой части — остановить и продолжить).
1. Раздел — поле `section` ответа ИИ (марка по штампу или заголовку), сразу
   переносится в поле строки `sheet` (правило №14). Дальше работает то, что
   уже есть: `generate_list` даёт лист на раздел, редактор — вкладку, полнота и
   смета везут `sheet` полем строки.
2. Наименование раздела одно на весь проект: найденные разделы и раздел конца
   предыдущей части передаются в промпт следующей; совпадающие без учёта
   регистра и пробелов сводятся к первому написанию. Разные марки не склеиваются.
3. Обрабатываются все PDF задачи; части нумеруются сквозь файлы.
4. Дубль — тот же раздел, имя и тип.
5. Сбой любой части прохода 1 останавливает задачу с названием части, файла и
   страниц; чекпоинт `chunks_done` уже есть, «Возобновить» продолжает с неё.
6. Полнота по проекту проставляет лист чанка (`_tag_sheet`), как полнота по
   гранд-смете.

**Рассмотренные альтернативы.**
1. *Раздел по имени файла.* Отклонено как единственный источник: работает, только
   если проект прислан файлами по разделам; сшитый «Том_5.pdf» ничего не даёт.
   Оставлено подсказкой в промпте.
2. *Раздел по закладкам PDF.* Отклонено: закладки есть не всегда, заголовки
   длинные и не совпадают с маркой; ради этого понадобилась бы привязка страниц
   к закладкам.
3. *Отдельный файл на раздел.* Отклонено пользователем: у документа один файл
   результата, полноту, смету и оптимизацию пришлось бы гнать по каждому файлу.
4. *Сбой части — досчитать и предупредить.* Отклонено пользователем: дыру в
   перечне легко не заметить, а ошибка в смете — потери на тендере.

**Почему так.** Вся инфраструктура «лист = раздел» уже есть и обкатана на
перечне из гранд-сметы; не хватает только того, чтобы перечень из проекта её
заполнял и не терял позиции по дороге.

- **Изменения — разделы:**
  - `project_sections.normalize_section(label, known) -> str | None`:

      раздел в `progress_data` и имя листа в файле обязаны совпадать;
    - пусто после очистки («/», «») → `None`;
    - сравнение с `known` без учёта регистра, пробелов **и латиницы-двойника**
      (OB↔ОВ, AP↔АР: ИИ иногда пишет латиницей) → написание из `known`;
    - «Прочее» → `None` (иначе «Прочее (2)» и разъезд с листом файла);
      «Пояснительная записка» → «ПЗ» (иначе openpyxl переименует лист записки);
    - разные марки не сводятся («ОВ» и «ОВиК» — два листа).
  - `apply_sections(items, known, carry)`: поле ответа `section` → `sheet`
    (перезаписывает, даже если ИИ сам вернул `sheet`), поле `section` удаляется.
    Пустой раздел наследуется от предыдущей позиции этой же части, затем от
    `carry` (раздел конца предыдущей части **того же файла**): материал не имеет
    права оторваться от своей работы — комплекты и смета связывают их порядком
    строк. «Прочее» — только позиции, перед которыми раздела нет вовсе.
  - Промпт прохода 1: «РАЗДЕЛЫ: указывай раздел в поле notes» и «notes оставь с
    разделом» → поле `section` (только марка комплекта по штампу или
    заголовку: «АР», «ОВ», «ЭОМ», без расшифровки; не виден — пустая строка);
    `type` — строго «Работа» или «Материал» (тип «Раздел» в смете — строка-
    раздел, `estimate_rows.py:68`). К части дописывается, только если есть что:
    «Файл: <имя>», «Уже найденные разделы: … — пиши ровно так», «Предыдущая
    часть закончилась разделом «…»…». Подсказка о предыдущей части
    **сбрасывается на границе файла** и хранится в чекпоинте (`section_carry`),
    а не выводится из последней позиции — та могла уйти как дубль.
  - Дедупликация: ключ `(раздел без учёта регистра, имя, тип)`. Исключение —
    двойная находка одного чертежа: когда листы идут с каждой текстовой частью
    (одна пачка), ИИ может подписать одну позицию разными разделами. Совпали
    имя, тип, единица и ненулевой объём в другом разделе — это дубль; такие
    случаи **перечисляются в пояснительной записке**, а не теряются молча.
    Заполнение пустого объёма повторной находкой (фаза 2) — тем же ключом.
    Набор найденных при resume собирается по новому ключу.
  - Проход 2: из ответа берутся только `quantity` и `notes`, остальное (имя,
    единица, тип, `sheet`) — от исходной позиции.
  - Проход 2 видит листы **всех** файлов (по пачкам фазы 2), а не
    `chunks[0]["image_pages"]`; временная папка живёт до конца прохода 2.
  - `_handle_check_project_completeness`: `_tag_sheet(chunk_items,
    _chunk_sheet(chunks[i]))` — как в `_check_completeness_chunk`.
- **Изменения — все файлы:**
  - Все PDF задачи по `file_index`; PDF определяется по сигнатуре `%PDF`, а не
    по `mime_type` (браузер шлёт и `application/octet-stream`). Части
    нумеруются сквозь файлы, чекпоинт `chunks_done` сквозной; в чекпоинте и
    `total_chunks` — при расхождении (чекпоинт старой разбивки, до выкладки)
    проход 1 начинается с нуля. Файлы не-PDF → строка в пояснительной записке:
    «Не обработан файл «план.dwg»: поддерживается только PDF». Имя файла —
    `f.get("name")`.
  - Стоимость: N файлов ≈ N× вызовов прохода 1 — это и есть ранее
    пропущенная работа; сказать пользователю при сдаче.
- **Изменения — сбой части не пропускается:**
  - Чекпоинт `{"chunks_done": 0, "total_chunks": N, "items": [], "_stage":
    "pass1"}` пишется **до** цикла: иначе сбой первой части не оставит чекпоинта,
    resume ответит 409, и текст «нажмите Возобновить» соврёт.
  - Обрезанный ответ (`ResponseTruncatedError`, не повторяется) → часть делится
    пополам (текст — по страницам, пачка — по листам) и обрабатывается
    половинами, как `_list_grand_rows` / `_check_completeness_chunk`; иначе
    плотная часть упиралась бы в 64k токенов на каждом «Возобновить».
  - Иной сбой части после повторов (любой, не только первой) → ошибка-
    наследник `RuntimeError` с текстом «Не обработана часть k из N (файл «…»,
