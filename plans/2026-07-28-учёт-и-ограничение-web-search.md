# Учёт и ограничение web search (24% счёта Anthropic были невидимы)

Дата: 2026-07-28
Research: `thoughts/research/2026-07-28-почему-смета-подорожала.md`

## Проблема

Сверка за неделю (28.07.2026):

| | Сумма |
|---|---|
| `api_call_log.cost_usd` (наша метрика) | $121,95 |
| Токены у Anthropic | $125,18 |
| **Всего у Anthropic** | **$161,06** |
| Из них web search | $35,88 |

Модель расчёта токенов верна (расхождение 2,6%). Вся дыра — плата за web search
($10 / 1000 поисков): 22% счёта, которых метрика не видела вообще. Гипотезы о
наценке посредника и непрокинутой batch-скидке цифрами сняты — платим напрямую
Anthropic по прайсу.

Причина бесконтрольного расхода: у `WEB_SEARCH_TOOL` не был выставлен `max_uses`,
то есть потолок числа поисков внутри одного вызова отсутствовал. Это тот самый
рычаг, который был назван главным ещё в замере 15.07 и так и не был применён.

## Фазы

### [x] Фаза 1 — потолок поисков и честный расчёт стоимости

- [x] `WEB_SEARCH_MAX_USES` в конфиге (дефолт 8, снижается через env без деплоя кода).
- [x] `max_uses` в `WEB_SEARCH_TOOL` (claude_service.py) — действует и на обычные
      вызовы, и на batch: оба идут через один и тот же словарь инструмента.
- [x] `_extract_usage` читает `usage.server_tool_use.web_search_requests`
      (у вызова без поиска этого поля нет — возвращаем 0).
- [x] `_calc_cost(..., web_search_requests=N)` добавляет `N × $0.01`. Скидку batch
      на поиски НЕ применяем — консервативно, чтобы снова не занизить счёт.
- [x] Колонка `api_call_log.web_search_requests` + миграция `038` (IF NOT EXISTS,
      старые строки остаются с 0 — там значение неизвестно).
- [x] Обе точки логирования: `call_claude` и `collect_claude_batch`.
- [x] Скрипты `cost_regression_estimates.{sql,py}` показывают факт по поискам.

Self-Audit: все три вызова `_extract_usage` обновлены под кортеж из 5 элементов
(grep подтвердил); `_calc_cost` вызывается из `_log_api_call` и тестов — новый
аргумент со значением по умолчанию, обратная совместимость сохранена.

Verification: `pytest tests/test_claude_batch.py` — 11 passed. Полный набор:
было 22 failed / 350 passed, стало 18 failed / 359 passed — 4 предсуществующих
падения починены (тесты обращались к `cs._client`, который с 25.07 ленивый),
5 тестов добавлено, регрессий нет.

### [x] Фаза 2 — повторная оплата чанков при паузе по балансу

Было: `_process_chunks` применял результаты только после того, как отработает вся
группа из 8 чанков (`ESTIMATE_MAIN_CHECKPOINT_GROUP`), а `_run_chunks_parallel`
при любом исключении выбрасывал весь список результатов. Пауза по балансу или
таймаут в одном чанке обнуляли до восьми уже оплаченных — и после пополнения
баланса они оплачивались второй раз.

- [x] `_run_chunks_parallel(return_exceptions=True)` — исключение воркера
      возвращается на месте результата вместо raise (отмена приходит как
      `CancelledError`: флаг ставится только когда есть незавершённые таски,
      и они тут же отменяются).
- [x] `_process_chunks` применяет успешные чанки, сохраняет `claude_partial`
      и только потом поднимает первую ошибку. Окно потери — один чанк вместо восьми.
- [x] То же для `fix_empty_prices`: найденные цены пишутся в `progress_data`
      перед падением, иначе перезапуск снова видит их пустыми.
- [x] Попутно: в `fix_empty_prices` ошибка баланса попадала в общий `except` и
      батч молча терялся — задача завершалась с пустыми ценами вместо паузы.
      Теперь `InsufficientBalanceError` пробрасывается, как в основном проходе.

Verification: тест `test_fix_empty_prices_saves_paid_batches_before_balance_pause`
проверен на откате правки — на старом коде красный, на новом зелёный. Полный
набор: 18 failed / 362 passed против 18 / 359 до фазы (ровно +3 новых теста,
регрессий нет).

### [ ] Фаза 3 — дубли batch-строк в метрике

`collect_claude_batch` логирует usage при каждом сборе пачки, а
`resume_from_batch` идемпотентен и может собрать её повторно после рестарта
поллера. Реальных денег это не стоит, но завышает `cost_usd`. Нужна защита от
повторного логирования (например, отметка собранного `batch_id` в `progress_data`).

### [ ] Фаза 4 — замер эффекта после деплоя

Через неделю после выката повторить сверку: `Total web search cost` в консоли
Anthropic против прежних $35,88, и `cost_usd` против фактического счёта. Если
расхождение осталось — искать следующую невидимую статью.

## Ограничения

- `WEB_SEARCH_MAX_USES = 8` — оценка сверху, не измеренная величина: на чанк из 10
  позиций восьми поисков достаточно, но проверить это можно только на проде. Если
  начнут появляться позиции без цены — поднять; если поиск всё ещё дорог — снизить
  до 5. Значение живёт в env именно для этого.
- Полный pytest локально идёт на системном python 3.9, часть тестов падала до этих
  правок и падает после (несовместимость окружения, не логика).

## Итог

Фазы 1 и 2 реализованы целиком. Осталось: Фаза 3 (чистота метрики — дубли
batch-строк, реальных денег не стоят), Фаза 4 (замер эффекта после деплоя).
