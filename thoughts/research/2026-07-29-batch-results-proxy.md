# Research — забор результатов Batch API уходит мимо прокси (403 forbidden)

Дата: 29.07.2026
Задача: задача `90c4e0eb-0425-4209-9035-b27a243bd249` (ESTIMATE_FROM_LIST, batch-режим)
упала на шаге «Batch завершён. Сбор результатов и формирование сметы...» с
`Ошибка сборки сметы из batch: Error code: 403 - {'error': {'type': 'forbidden', 'message': 'Request not allowed'}}`.

## Что происходит

`403 forbidden / Request not allowed` — геоблок Anthropic на эдже Cloudflare для РФ-IP,
ровно тот, ради которого заведён посредник (`plans/2026-07-25-anthropic-proxy-access.md`).
Все вызовы идут через `ANTHROPIC_BASE_URL` + `X-Proxy-Secret` (`claude_service.py:282-300`).

Но один вызов уходит мимо прокси:

- `collect_claude_batch` зовёт `_get_client().messages.batches.results(batch_id)`
  (`claude_service.py:697`);
- SDK внутри делает `retrieve(batch_id)` и затем `self._get(batch.results_url, ...)`
  (`anthropic/resources/messages/batches.py:613-627`, версия 0.85.0) — то есть берёт
  **абсолютный** URL из ответа API: `https://api.anthropic.com/v1/messages/batches/<id>/results`;
- `BaseClient._prepare_url` (`anthropic/_base_client.py:474-485`) подставляет `base_url`
  **только для относительных** путей, абсолютный возвращает как есть;
- итог: запрос идёт напрямую на `api.anthropic.com` с РФ-IP → 403.

Все прочие вызовы (`batches.create`, `batches.retrieve`, `batches.cancel`, `messages.create`)
используют относительные пути и корректно проходят через прокси. Поэтому пачка успешно
отправляется и опрашивается, а падает строго на заборе результатов.

**Масштаб:** batch-режим ESTIMATE_FROM_LIST на проде нерабочий целиком — пачка считается
и оплачивается, результат забрать невозможно. Fast-режим не затронут. Локально
(не-РФ egress, `ANTHROPIC_BASE_URL` пуст) баг не воспроизводится — потому и не пойман.

## Вторая половина проблемы: упавшую задачу нельзя добрать

Пачка уже посчитана и оплачена, результаты у Anthropic хранятся 29 дней. Но:

- при падении `resume_from_batch` поллер ставит `failed` (`batch_poller.py:103-107`),
  `progress_data._stage` остаётся `batch_pending`;
- `batch_poller` ищет только `processing`/`cancelled` (`batch_poller.py:32-38`) — мимо;
- `resume_task` возвращает batch-задачу в `processing` **только при статусе `paused`**
  (`tasks.py:769-775`); для `failed` идёт проверка `has_resumable_checkpoint`, а
  `batch_pending` не входит в `RESUMABLE_STAGES` (`checkpoint.py:23`) → 409;
- фронт для такой задачи показывает только «↺ Перезапустить» = `restartTask`, то есть
  полный сброс `progress_data` и пересчёт с нуля (`tasks.py:797-833`) — повторная оплата
  пачки (~$10) при том, что готовый результат лежит у Anthropic.

Значит одного фикса транспорта мало: без Фазы 2 текущая задача пользователя
восстанавливается только за деньги.

## Варианты решения (Фаза 1)

| # | Подход | Плюсы | Минусы |
|---|---|---|---|
| A | Оставить SDK, но задать `ANTHROPIC_BASE_URL` так, чтобы совпал с `results_url` | ничего не писать | невозможно: `results_url` приходит от API с хостом `api.anthropic.com` |
| B | Не звать `batches.results()`: `retrieve` → взять `results_url` → своим httpx-запросом к прокси → парсить JSONL вручную | только публичный API | дублирует авторизацию, ретраи и обработку ошибок SDK (~40 строк) |
| C | Подкласс `AsyncAnthropic` с переопределением `_prepare_url`: абсолютный URL на дефолтном хосте Anthropic → относительный путь → SDK сам склеит с `base_url` | 6 строк, весь механизм SDK (ретраи, ошибки, типы, стриминг) сохраняется, автоматически покрывает будущие абсолютные URL (Files API) | завязка на приватный метод `_prepare_url` |
| D | Свой `httpx.AsyncBaseTransport`, переписывающий хост запроса | публичный API httpx | переписывание не видно по месту вызова, сложнее отлаживать |

Поиск по вопросу: официального параметра «проксировать абсолютные URL» в SDK нет;
рекомендации Anthropic (`DefaultAsyncHttpxClient`, `proxy=`) решают другую задачу —
транспортный прокси, а у нас HTTP-посредник со своим доменом и секретом.

## Вывод — выбран вариант C

`_prepare_url` — стабильная точка (присутствует во всех версиях SDK 0.2x–0.85),
переопределение занимает несколько строк и сохраняет всю машинерию SDK. Риск завязки
на приватный метод снимается тестом: он проверяет **фактический исходящий HTTP-запрос**
через `httpx.MockTransport`, а не факт вызова `_prepare_url`. Такой тест переживёт смену
реализации и упадёт, если после апгрейда SDK запрос снова пойдёт напрямую.

Ограничение переписывания: только абсолютные URL с хостом `api.anthropic.com` и только
когда `ANTHROPIC_BASE_URL` задан. Если Anthropic когда-нибудь начнёт отдавать
`results_url` на постороннем хосте (S3-подобное хранилище) — переписывание не сработает
и запрос уйдёт как есть, то есть поведение не станет хуже текущего.
