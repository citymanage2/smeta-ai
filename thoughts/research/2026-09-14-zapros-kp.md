# Исследование: запрос КП у отдела производства работ

Дата: 2026-09-14
Спецификация: `specs/2026-09-14-zapros-kp.md`
План: `plans/2026-09-14-zapros-kp.md`

## Задача

Менеджер продаж выбирает позиции в документе (перечень / полнота / смета /
оптимизация) и ставит задачу «запросить КП»: материалы — менеджеру снабжения,
работы — менеджеру по работе с подрядчиками. Исполнитель прикрепляет КП, ИИ
разбирает цены, человек проверяет, пишет отчёт и завершает задачу. Цены из КП
проставляются в смету оптимизации, позиция подсвечивается, на позицию может
быть несколько КП.

Решения пользователя (14.09.2026):

| Развилка | Решение |
|---|---|
| Как цены из КП попадают в запрос | **ИИ разбирает файл КП**, человек проверяет и правит |
| Несколько КП на позицию | **Минимальная цена по умолчанию**, выбор можно сменить |
| Когда цены идут в оптимизацию | **Кнопкой, новой версией** «Цены из КП» (откатывается) |
| Доступ новых ролей | **Только свои задачи КП**, без проектов и смет |

## Что есть в коде

### Роли и права
* Роль — строка `users.role` (`models/user.py:17`), без enum и CHECK в БД:
  новая роль миграции не требует. Прошлый опыт — миграция `036_employee_accounts_rbac.py`.
* `utils/permissions.py`: `normalize_role` превращает любую неизвестную роль в
  `project_manager` — **новые роли обязаны попасть сюда**, иначе получат права ПМ.
  `ASSIGNABLE_ROLES` проверяется в `admin_users.UserCreate/UserUpdate`.
* `visibility_filter` всегда `None`, `can_access` всегда `True` — проекты общие.
  Узкие места проверок: `can_access` в 7 роутерах, `document_service.py:39`.
  Но **многие роутеры вообще не зовут `can_access`** (прайсы, выученные цены,
  калькулятор, корректировки) — сужение через `can_access` дырявое.
* В `main.py:233-251` роутеры подключаются списком `include_router` — удобное
  место для зависимости уровня роутера.
* Фронт: `stores/auth.ts` (`type Role = string`, флаги `isAdmin/isManager`),
  подписи `api/adminUsers.ts:59-64`, меню условными кнопками `Layout.tsx:94-140`,
  охрана маршрутов `ProtectedRoute.tsx` (`requireAdmin/requireManager`),
  стартовая `/system` (`App.tsx:38`). Страница сотрудников `pages/Employees.tsx`.
* Отдела (`department`) нет. Уведомлений о назначении нет; есть лента
  `SystemEvent` с опросом раз в 30 с (`useSystemNotifications`) и тосты.

### Задачи
* `Task` + очередь `Job` рассчитаны на обработку ИИ: `pending` означает «в
  очереди», статусы участвуют в ETA и метриках. Ручной задачи для человека
  (исполнитель, отчёт, вложения) нет — **`Task` для запроса КП не подходит**.
* Карточка `WorkflowCard` держит по задаче на стадию (`list/completeness/
  estimate/optimization_task_id`), владельца у карточки нет.
* Очередь: `job_queue.enqueue(kind, payload, owner_id)`, реестр обработчиков
  `worker.HANDLERS`. Образец фоновой ИИ-операции над выбранными строками
  документа — `analogs_service` (`AnalogRun`, `start_run` → job
  `document.analogs`, восстановление брошенного прогона).

### Файлы
* S3 Timeweb: `services/storage_service.py` (`store_*`, `load_bytes`,
  `delete_prefix`), в БД только метаданные и `storage_key`.
* Слоты задач принимают только XLSX; входные файлы задач — PDF/JPEG/PNG/XLSX/XLS/XML,
  50 МБ, 10 файлов. Отдельной модели вложений нет. Скачивание с RFC 5987
  `Content-Disposition` — `tasks.py:1230`, можно переиспользовать.
* Передача PDF/картинок в Claude — `task_processor._build_messages_with_files`
  (`:1084`), JSON-ответ — `_call_claude_json` (`:1177`).

### Редактор и строки
* Выделение строк уже есть: `SelectColumn`, `selectedKeys` в сторе
  (`DocumentEditor.tsx:141, 776-788`); в свёрнутом режиме галочка группы
  разворачивается в ключи настоящих строк. Кнопки действий над выделением —
  полоса `de-actions-bar` (`:986-1065`), компоненты в `editor/actions/`.
* Перечень/полнота — `genericAdapter` (`{row_id, sheet, cells}`), тип позиции
  выводится `generic_items.py`. Смета/оптимизация — `estimateAdapter`
  (`type: work|material`, `price_work`, `price_material`).
* **`row_id` между стадиями не стабилен:** перечень заново получает uuid при
  каждом разборе, смета — в `item_to_row`, оптимизация перечитывает xlsx сметы
  (`services/estimate_parser.py:284-299`) с новыми uuid. `source_no` доезжает до сметы,
  но **теряется в оптимизации** — парсер его не читает.
* Оптимизация: `EstimateVersion.rows`, шаги V1–V5, ручные версии
  `create_manual_version` (`estimate_versions.py:1612`). Шаг берёт последнюю
  неоткатанную версию.
* Запись строк — только `document_service.apply_rows` (`:944`): версия `rev`,
  история, откат. Сигналы `correction_log` пишутся только при
  `operation_type == "document_edit"`; образец автоматической операции —
  `check_price_units` (`:1179`).
* Коэффициент живёт в `version.coefficient`, в `rows` — исходные цены. Цену из
  КП писать **без коэффициента**.
* Пометки «оптимизированная позиция» в новом редакторе нет: `estimateAdapter.rowClass`
  не смотрит на `optimization_*`. Источник цены — `price_list_name`, примечания —
  `notes` / `optimization_note`.
* Цены строк сметы — **без НДС** (`summary_calc.py:20-22`, ставка 22 % в бланке).
  Поставщики присылают КП и с НДС, и без (УСН).
* Сводимость единиц — `utils/unit_compat.py` (правило №8), кратность —
  `unit_normalizer.base_unit`.

## Как это решают другие

Процесс «запрос КП → сравнение предложений → выбор» в закупочных системах
(SAP Ariba RFQ, 1С:ERP «Запрос коммерческих предложений», Битрикс24 «Тендеры»,
Tenderpro) устроен одинаково:

1. **Запрос — отдельная сущность** с позициями-снимками (что, единица, объём),
   а не ссылка на живую строку: документ заказчика меняется, а поставщику
   отправлено конкретное.
2. **Предложение (КП) — отдельная сущность** «поставщик + файл + дата + НДС»,
   цены лежат матрицей «позиция × предложение».
3. **Сравнительная таблица** (bid comparison / конкурентный лист): строки —
   позиции, колонки — поставщики, по умолчанию подсвечен минимум после
   приведения к одной единице и одной ставке НДС; выбор можно переопределить с
   причиной.
4. **ИИ/OCR-разбор КП** (Ariba, Coupa, российские Directum/ELMA) даёт
   черновик, человек подтверждает — автоматическое принятие цены не
   практикуется: ошибка единицы или НДС стоит денег.

## Варианты архитектуры

| # | Вариант | Плюсы | Минусы |
|---|---|---|---|
| A | Новый `task_type` в `tasks` | Готовые корзина/статусы | Очередь, ETA, метрики, `pending`=job — всё придётся обходить исключениями; нет исполнителя и позиций |
| B | **Свои таблицы `kp_requests` / `kp_request_items` / `kp_offers` / `kp_offer_prices`** | Чистая модель «запрос → позиции → КП → матрица цен», как в закупочных системах; ничего не ломает в задачах ИИ | 4 таблицы, свой роутер |
| C | Хранить КП в полях строк документа | Нет новых таблиц | Нарушает «у строки один писатель», теряется при пересчёте, нет задачи для человека |

Сопоставление позиции запроса со строкой оптимизации:

| # | Ключ | Итог |
|---|---|---|
| 1 | `row_id` | Не стабилен между стадиями — годится только если запрос создан на той же оптимизации |
| 2 | `source_no` | Надёжен, но теряется в оптимизации — нужно научить `estimate_parser` читать колонку |
| 3 | Тип + нормализованные наименование + единица (ключ свёртки дублей) | Работает всегда; неоднозначность видна |

Ограничение доступа новых ролей:

| # | Способ | Итог |
|---|---|---|
| 1 | Сузить `can_access` | Дыряво: половина роутеров его не зовёт |
| 2 | **Запрет по умолчанию:** зависимость уровня роутера в `main.py` для всех роутеров, кроме `auth` и `kp_requests`; тест перебирает `app.routes` | Новая ручка автоматически закрыта; правило в одном месте (`permissions.py`) |

## Вывод и рекомендация

* **Модель — вариант B** (свои таблицы), по образцу закупочных систем.
* **Доступ — запрет по умолчанию** на уровне роутеров плюс фильтр «исполнитель =
  я» внутри роутера КП; тест, перебирающий все маршруты.
* **Позиции запроса — снимок** (тип, наименование, единица, объём, лист, №
  исходной сметы, `row_id` источника); одинаковые позиции выделения
  сворачиваются в одну позицию запроса с суммой объёма (ключ свёртки дублей).
* **ИИ разбирает КП в фоне** (job `kp.parse_offer`, по образцу аналогов),
  возвращает цены только для переданных id позиций; каждая цена — черновик
  до подтверждения человеком.
* **Цена за позицию** = минимум по подтверждённым КП **после приведения к
  единице позиции (`unit_compat`) и к «без НДС»**; несводимая единица —
  цена не участвует, причина видна. Ручной выбор КП перекрывает минимум.
* **Применение** — двухшаговое, как у «Эталона» (правило №18): предпросмотр
  (что найдено, что неоднозначно, что не найдено) → «Применить» создаёт новую
  версию оптимизации через `apply_rows` с `operation_type="kp_prices"` (не
  сигнал корректировки). Сопоставление: `row_id` → `source_no`+наименование →
  тип+наименование+единица; неоднозначное не берётся.
* **Подсветка** — поле строки `kp_ref` (едет через `PASSTHROUGH_FIELDS`/
  `STORED_FIELDS`) и класс `de-row-kp`; то же поле красит строку в xlsx.
