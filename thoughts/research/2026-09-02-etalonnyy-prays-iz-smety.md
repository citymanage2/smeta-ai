# Research: эталонный прайс из сметы («цены из файла — единственно верные»)
**Date:** 2026-09-02
**Task size:** M

## Задача пользователя

Есть excel-файл со сметой. Цены работ и материалов из него нужно перенести в
прайс так, чтобы они стали **единственно верными**: если по этой же позиции в
прайсе лежат другие цены — их убрать.

Решения пользователя (02.09.2026):
1. вход — **файл в Каталоге прайсов**, не редактор сметы;
2. у совпавших позиций чужие цены **стираются**;
3. дубли (то же по смыслу, другое написание) — **только с подтверждением
   человеком**, автоудаления нет.

## Как это работает сейчас

### Хранение цен
- `PriceWork` — у работы **набор цен**: `prices = {подрядчик: цена}` плюс
  псевдо-подрядчик `«Из смет»`; в расчёт идёт одно число `min_price`.
- `PriceMaterial` — одна цена `price`.
- `updated_at` — **дата цены**, не дата записи (правило №15 CLAUDE.md).
  Двигает её только переоценка, решает `utils/price_change.py`.

### Какая цена попадает в расчёт
`utils/price_min.compute_min_price`: если есть цена «Из смет» — берётся **она**;
цены подрядчиков работают, только когда цены из смет нет (решение 03.08.2026).

### Порядок источников цены при расчёте сметы
`task_processor` (проходы 3–5) и `price_service.find_work_price`:
1. прайс — точное совпадение нормализованного имени;
2. прайс — поиск по смыслу (вектор, `SIMILARITY_THRESHOLD`);
3. **кеш прошлых задач/веб-поиска** (`price_cache_works` / `price_cache_materials`)
   — сначала точное совпадение, потом вектор;
4. платный веб-поиск через ИИ.

**Вывод, который меняет постановку:** «другая цена по той же позиции» живёт не
только в прайсе. Кеш веб-поиска — полноценный источник, и позиция, названная в
кеше иначе, перебьёт расчёт раньше, чем дойдёт до ИИ. Значит вытеснение обязано
видеть и кеш (в каталоге он уже показан отдельной вкладкой и уже умеет
удаляться — `deleteCacheWork` / `deleteCacheMaterial`).

### Загрузка прайса файлом (существующий путь)
`POST /admin/price-lists/{works|materials}` → `admin._handle_price_upload`:
- разбор `_parse_price_rows`: заголовок ищется по слову «наименование»;
  для работ **каждая колонка с заголовком = подрядчик** (имя колонки — имя
  подрядчика);
- эмбеддинги генерируются одним батчем (FastEmbed, локально — **платы нет**,
  только CPU);
- запись — **merge**: `merged = {**existing_prices, **new_prices}` — чужие цены
  подрядчиков сохраняются; у материала цена перезаписывается;
- дата двигается только при `prices_changed` / `price_changed`;
- в конце — `price_service.load_cache(db)`, иначе расчёт не увидит правку.

UI: `PriceCatalog.tsx` → `ImportButton` (селект «Работы/Материалы» + файл).
Права — `get_admin_user`; прайс относится к управляющим действиям
(`permissions.py`, MANAGER_ROLES).

### Что ещё есть и переиспользуется
- `price_service.find_top_n_works / find_top_n_materials` — top-N кандидатов по
  косинусной близости с оценкой. Ровно то, что нужно для поиска дублей;
  `/prices/match-preview` уже показывает такой список в UI.
- `price_bulk.add_items` — пакетная запись из редактора; там же правило
  приведения «100 м2» → «м2» (`unit_normalizer.unit_price_factor`).

## Принятые в проекте правила, которые здесь обязательны

- правило №8: **единица — часть ключа цены**. Позиция из файла и позиция прайса
  с несводимой единицей — это разные цены, вытеснять вслепую нельзя;
- правило №15: дату двигает только переоценка;
- цена за «100 м2» приводится к цене за «м2» (`unit_price_factor`) — как в
  `price_bulk`;
- после любой записи — `price_service.load_cache(db)`;
- запись в прайс — управляющее действие (менеджерские роли).

## Риски и края

1. **Формат входного файла.** ГРАНД-Смета даёт базисные цены с накрутками
   (НР, СП, ФОТ) и материалы внутри расценки — «цена за единицу как в прайсе»
   оттуда не достаётся честно. Надёжный вход — файл **нашего** формата сметы
   (колонки «Тип», «Наименование», «Ед. изм.», «Цена работы (за ед.)»,
   «Цена материала (за ед.)»), где тип строки и обе цены лежат явно, либо
   простая таблица «Наименование / Ед. изм. / Цена» с выбором типа в селекте.
2. **Смешанный файл.** У сметы работы и материалы в одной таблице, а
   существующий импорт требует выбрать тип заранее. Режим «эталон» должен уметь
   разбирать оба типа из одного файла по колонке «Тип».
3. **Ошибка сопоставления стоит дороже, чем пропуск.** Прайс общий; снесённая
   цена подрядчика не восстанавливается. Отсюда — подтверждение на дубли и
   отказ вытеснять при несводимых единицах.
4. **Порог похожести.** `SIMILARITY_THRESHOLD` настроен под подбор цены. Для
   списка «возможные дубли» его лучше брать **ниже** порога подбора: показать
   лишнее человеку дешевле, чем не показать реальный дубль. Удаляет всё равно
   человек.
5. **Нет векторов — нет поиска дублей.** Если у прайса `embedding` пуст,
   останутся только точные совпадения; это надо честно писать в ответе, как это
   делает `match-preview`.
6. **Размер.** Смета на 1000+ строк × top-N поиск — операция на секунды; делать
   её синхронной в запросе допустимо, но нужен потолок на число позиций (как
   `MAX_ITEMS = 500` в `price_bulk`).

## Поиск готовых решений

Задача доменная и целиком внутри уже написанного кода: механика векторного
поиска, нормализация имён, правило даты цены и приоритет «Из смет» в проекте уже
есть и закреплены тестами. Внешняя библиотека дедупликации (fuzzy/record
linkage) добавила бы второй, несогласованный с расчётом сметы способ считать
«та же позиция» — а расхождение между «как ищет дубли» и «как подбирает цену»
и есть источник ошибки. Поэтому переиспользуем `find_top_n_*`.

## Вывод и рекомендация

**Рекомендуемый подход:** режим «эталон» у существующего импорта в Каталоге
прайсов, реализованный в два шага без хранения состояния на сервере.

1. **Шаг 1 — предпросмотр** (`POST /admin/price-lists/reference/preview`):
   файл разбирается, позиции нормализуются (единица, кратность), возвращается:
   что будет добавлено, у каких позиций какие цены будут стёрты (с указанием
   подрядчика и числа), какие позиции пропущены и почему, и **список возможных
   дублей** — по прайсу и по кешу, с оценкой похожести. Ничего не меняется.
2. **Шаг 2 — применение** (`POST /admin/price-lists/reference/apply`): фронт
   присылает разобранные позиции (JSON, не файл) и id отмеченных к удалению
   дублей. Сервер пишет цены, стирает чужие цены у совпавших позиций, удаляет
   только отмеченное, обновляет `load_cache`.

**Почему так, а не иначе:**
- отдельный эндпоинт не трогает работающий merge-импорт: у обычной загрузки
  прайса подрядчика поведение не меняется ни на строку;
- без состояния на сервере — нет «протухшего» предпросмотра и не нужна таблица
  под черновик операции; эмбеддинги локальные, поэтому повторный проход по
  именам на шаге 2 ничего не стоит, кроме CPU;
- поиск дублей тем же `find_top_n_*`, что и подбор цены, — «дубль» по той же
  мерке, по которой позиция потом найдётся в расчёте.

**За чем следить:**
- вытеснение при несводимых единицах (правило №8) — не стирать, а показывать
  причину;
- дата цены двигается только при реальной переоценке;
- потолок на число позиций в одном файле.
