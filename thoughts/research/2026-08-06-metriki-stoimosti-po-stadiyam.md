# Исследование: метрики стоимости и времени по стадиям сметы

Дата: 2026-08-06
Задача: показать в карточке сметы по каждой стадии — токены, стоимость в $, время
в очереди, время работы, допзапросы (токены/$); плюс суммы по смете и по проекту.

## 1. Что уже есть

### Модель `ApiCallLog` (`backend/app/models/api_call_log.py`)
Готовая таблица учёта каждого вызова Claude:

| Поле | Смысл |
|---|---|
| `task_id` | FK на `tasks.id` (nullable, ondelete SET NULL), проиндексирован |
| `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_creation_tokens` | токены |
| `web_search_requests` | число web-поисков (тарифицируется отдельно, $10/1000) |

| `called_at` | timestamptz |

Вывод: **отдельная таблица метрик не нужна** — всё агрегируется из `api_call_log`.

### Модель `Task` (`backend/app/models/task.py`)
- `created_at` — момент постановки в очередь
- `started_at` — начало фактической обработки (переставляется при каждом прогоне)
- `finished_at` — конец обработки
- `cost` — Numeric(12,2), это **сумма сметы в рублях**, а не стоимость ИИ. Не путать.

Вывод: **время в очереди = `started_at − created_at`**, **время работы =
`finished_at − started_at`**. Дополнительных полей не нужно.

### Карточка сметы (`WorkflowCard`)

## 2. Главная находка: допзапросы почти не логируются

`call_claude()` пишет в `api_call_log` **только если переданы оба аргумента
`task_id` и `db`** (`claude_service.py:209` — `if db is None or task_id is None: return`).

Инвентаризация всех вызовов:

| Место | task_id/db передаются? | Что это |
|---|---|---|
| `task_processor.py:978, 1004` | да | основная обработка стадии |
| `analogs_service.py:291` | **да** | доп: поиск аналогов |
| `routers/tasks.py:1945` (`reprice_estimate_item`) | **нет** | доп: поиск цены одной строки |
| `routers/estimate_versions.py:1138` (`_run_fill_prices_step`) | **нет** | доп: массовое проставление цен |
| `routers/estimate_versions.py:1281` (`optimize_custom`) | **нет** | доп: предложения по строкам |
| `routers/estimate_versions.py:825` (`_run_optimization_step`) | **нет** | шаги оптимизации 1–4 |
| `price_service.py:475, 513` (веб-поиск цены) | **нет** | доп, вызывается из `tasks.py:1519/1524` |

Итог: сейчас 6 из 7 «допов» **не попадают в учёт вообще** — ни в метрику карточки,
ни в дашборд затрат. То есть цифра «допы» без доработки была бы почти всегда 0,
а суммарный счёт Anthropic — занижен. Это не косметика, а дыра в учёте.

**Следствие:** фича обязана дотянуть `task_id`/`db` до всех этих вызовов.

## 3. Как отличить «допы» от основной обработки

Три рассмотренных варианта:

**А. По времени: `called_at > task.finished_at` → доп.**
Плюс: ноль изменений в схеме. Минус: перезапуск задачи переставляет `started_at`
и `finished_at` — все прежние допы задним числом станут «основными». Данные
меняют смысл от постороннего действия. Отвергнут.

**Б. По источнику: отдельная таблица «допзапросов».**
Дублирует `api_call_log`, ломает единый учёт затрат в дашборде. Отвергнут.

**В. Явная колонка-признак в `api_call_log` (выбран).**
`is_extra: bool NOT NULL DEFAULT false`, проставляется на месте вызова.
Плюсы: смысл фиксируется тем, кто знает контекст; перезапуски не влияют;
дашборд может разложить затраты по типу; агрегация — одним `GROUP BY`.
Минус: исторические строки аналогов останутся помечены как основные
(до 2026-08-06). Приемлемо — данных мало, задним числом не восстановить.

Требуется миграция `045_*` (следующий номер по порядку; последняя — `044_analog_runs.py`).

## 4. Как считать (одним запросом на карточку)

```sql
SELECT task_id,
       SUM(input_tokens + output_tokens + cache_read_tokens + cache_creation_tokens)
         FILTER (WHERE NOT is_extra) AS main_tokens,
       SUM(cost_usd) FILTER (WHERE NOT is_extra)                AS main_cost,
       SUM(...) FILTER (WHERE is_extra)                         AS extra_tokens,
       SUM(cost_usd) FILTER (WHERE is_extra)                    AS extra_cost
FROM api_call_log
WHERE task_id = ANY(:task_ids)
GROUP BY task_id;
```

Важно: `filter()`-агрегаты SQLAlchemy на SQLite (тесты) транслируются в
`CASE WHEN`, работают. Индекс по `task_id` уже есть.

Для итога по проекту — тот же запрос с джойном `tasks.project_id = :project_id`.
Один запрос на страницу, не N+1.

## 5. Что показывать: токены одним числом

`input + output + cache_read + cache_creation`. Разбивка (кэш даёт 68% счёта —
см. память проекта `project_estimate_token_economics`) уходит в `title`-подсказку,
чтобы строка метрик не разрослась.

Стоимость — в долларах, как просил пользователь. `cost_usd` уже посчитан
в `_calc_cost()` с учётом batch-скидки и web-поисков — пересчитывать не нужно.

## 6. Риски и края

1. **Задача не стартовала** (`started_at IS NULL`) → время в очереди считаем
   «до сих пор» для активных, «—» для не начатых. Работа — «—».
2. **Задача идёт** (`finished_at IS NULL`, статус processing) → время работы
   считаем от `started_at` до «сейчас»; отдаём флагом, чтобы фронт тикал.
3. **Batch-режим** (`processing_mode='batch'`): `duration_ms` = NULL, но
   `started_at`/`finished_at` у задачи есть — метрики времени корректны.
4. **Перезапуск задачи**: `started_at` переставляется, прежние вызовы остаются
   в `api_call_log` → токены суммируются за все прогоны. Это правильно: деньги
   потрачены. Время же покажет только последний прогон. Разное поведение надо
   явно написать в подсказке.
5. **Приватность**: сумма в долларах — чувствительная информация. RBAC в проекте
   есть (`utils/permissions.py`: admin / head_of_sales / project_manager).
   Требует решения пользователя (вопрос в план).
6. **ETag на списке карточек** (`workflow_cards.py:198`) — метрики в `files-meta`,
   не в списке, ETag не трогаем.

## 7. Вывод — рекомендуемое решение

1. Миграция `045`: `api_call_log.is_extra BOOLEAN NOT NULL DEFAULT false` (+ IF NOT EXISTS).
2. `call_claude(..., is_extra: bool = False)` → прокидывается в `_log_api_call`.
3. Дотянуть `task_id`/`db` до шести неучтённых вызовов, пометить допы `is_extra=True`.
4. Один агрегатор `backend/app/services/usage_metrics.py`: метрики пачкой по
   списку task_id и по проекту. Единственная точка расчёта — как `estimate_store`
   для строк и `estimateCalc` для итогов.
5. `StageDetail` += `metrics`; новый `GET /api/projects/{id}/usage` для шапки проекта;
   `CardDetailResponse` += `totals` для шапки сметы.
6. Фронт: компонент `UsageChips` — одна строка чипов, переиспользуется в трёх местах
   (заголовок секции стадии, строка сметы, шапка проекта).

Экономия: ноль новых поллингов, ноль дублирующих таблиц, один SQL на экран.
