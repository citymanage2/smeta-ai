# Research — уведомление «баланс API пополнен, задачи возобновлены»

Дата: 2026-07-28
Задача: сделать так, чтобы после пополнения баланса Anthropic пользователь получал
явное уведомление о том, что пополнение дошло и какие задачи возобновлены.

## Проблема (из реального инцидента 2026-07-28)

Пользователь пополнил баланс. Задача осталась с текстом
«⏸ На паузе: баланс API исчерпан. Возобновление произойдёт автоматически после
пополнения. Ответ API: 400 Your credit balance is too low…».

Невозможно отличить три разных состояния:
1. Ещё не прошёл 10-минутный тик поллера.
2. Поллер отработал, но API всё ещё отвечает 400 (деньги не дошли / не тот счёт).
3. Воркер мёртв, поллер вообще не крутится.

Все три выглядят в UI одинаково — как застывший текст паузы.

## Как устроено сейчас

| Компонент | Файл | Поведение |
|---|---|---|
| Пауза | `backend/app/services/task_processor.py:1324-1348` | `InsufficientBalanceError` → статус `paused` + текст в `progress_message` |
| Авто-резюме | `backend/app/services/resume_poller.py` | раз в 10 мин берёт ВСЕ `paused`, атомарно `paused→pending` + durable-job |
| Расписание | `backend/app/worker.py:230` | `scheduler.add_job(resume_paused_tasks, "interval", minutes=10)` |
| Ручное резюме | `backend/app/routers/tasks.py:727` | `POST /tasks/{id}/resume` (кнопка «Продолжить сейчас») |
| Диагностика | `backend/app/routers/admin.py:1201` | `GET /admin/api-health` → `api_ping()` |
| Проба API | `backend/app/services/claude_service.py:607` | `api_ping()`: `max_tokens=1`, возвращает `ok/is_balance_error/status_code/base_url` |
| Тосты задач | `frontend/src/hooks/useGlobalTaskPoller.ts` | опрос раз в 5 с ТОЛЬКО по `trackedTasks` (задачи, добавленные в текущей вкладке) |
| Тосты | `frontend/src/utils/notify.ts` + `sonner` | `toast.success/error` + Web Notification + звук |

### Два ключевых дефекта текущей механики

**1. Слепой перезапуск.** Поллер каждые 10 минут переводит все `paused` в
`pending` и ставит job, не проверяя, есть ли вообще деньги. Если баланс пуст,
задача заново стартует, доходит до первого вызова Claude, падает и возвращается в
`paused` — «тихо, self-healing» (комментарий в `resume_poller.py:1-9`). Это:
- бесполезная нагрузка на воркер каждые 10 минут при каждой paused-задаче;
- у задач без чекпоинта — реальный риск платных вызовов до точки отказа;
- полное отсутствие следа в UI (пользователь не видит, что попытка была).

**2. Уведомления привязаны к вкладке.** `useGlobalTaskPoller` опрашивает только
`trackedTasks` — Map в памяти Zustand-стора (`stores/notificationStore.ts`), не
персистентный. После перезагрузки страницы список пуст. Пауза по балансу длится
часами (пока не пополнят) — к моменту возобновления вкладка почти наверняка
перезагружена, и задача уже не отслеживается. Значит уведомление о восстановлении
**невозможно** построить на существующем механизме: нужен серверный источник
события.

## Как решают эту задачу другие

Проверенный отраслевой паттерн для «внешний ресурс восстановился» — **health-gate
перед восстановлением + событие о смене состояния (state-transition event)**:

- **Circuit breaker (Hystrix / resilience4j / Polly)**: в состоянии `open` не
  пропускать трафик; периодически пускать один пробный запрос (`half-open`); при
  успехе — `closed` + событие `CircuitBreakerOnStateTransition`. Наш случай —
  один в один: `paused` = open, `api_ping()` = half-open probe, «баланс пополнен» =
  переход в closed.
- **Stripe / GitHub / Sentry**: при исчерпании квоты письмо шлётся на два события —
  «квота исчерпана» и «квота восстановлена, обработка возобновлена», с перечнем
  того, что было задержано.
- **Персистентная лента событий** (таблица + курсор `since_id`), а не push: у нас
  событие рождается в воркере, а показать его надо в браузере, который в этот
  момент может быть закрыт. WebSocket/SSE потребовал бы отдельного канала и
  переживания рестартов — избыточно для внутреннего инструмента с 3-10
  пользователями, где уже есть поллинг раз в 5 секунд.

## Вывод: лучшее решение

**Half-open probe в resume_poller + персистентное системное событие + курсорный
поллинг во фронте.**

Три части, каждая закрывает свою половину боли:

1. **`api_ping()` как гейт.** При наличии `paused`-задач поллер сначала делает один
   дешёвый пробный вызов (`max_tokens=1`, доли цента). Функция уже написана и
   используется в `/admin/api-health` — переиспользуем, не пишем новую.
   - `ok` → возобновляем (как сейчас) и фиксируем событие;
   - не `ok` → **не трогаем задачи вообще** (убирает слепые перезапуски) и
     обновляем `progress_message` каждой paused-задачи текстом с временем
     проверки и ответом API.

   Побочный выигрыш: вместо N холостых перезапусков — один ping. Дешевле и тише,
   чем сейчас.

2. **Таблица `system_events`.** Одна строка на переход «баланс восстановлен» с
   payload `{resumed_task_ids: [...]}`. Пережидает рестарт воркера и закрытую
   вкладку. Хранить в payload только id — названия и права берём из актуальных
   `tasks` в момент отдачи (нет рассинхрона и дублирования данных).

3. **`GET /notifications/system?since_id=N`** + хук во фронте с курсором в
   `localStorage`. Отдаёт события с RBAC-фильтрацией списка задач через
   существующий `visibility_filter` (`backend/app/utils/permissions.py:47`):
   менеджер видит все возобновлённые задачи, ПМ — свои и общие.

### Отвергнутые альтернативы

| Вариант | Почему нет |
|---|---|
| WebSocket/SSE-push из воркера | Отдельный канал, переподключения, состояние при рестарте. Поллинг раз в 30 с уже покрывает потребность — событие такого рода происходит раз в недели. |
| Событие в памяти воркера | Воркер и web — разные процессы (`docker-compose.yml`), web его не увидит. Плюс теряется при рестарте. |
| Считать на фронте: «была paused → стала processing» | Требует, чтобы вкладка непрерывно отслеживала задачу часами. `trackedTasks` не персистентны — после перезагрузки страницы информация потеряна. |
| E-mail/Telegram | Нет ни SMTP, ни бота в проекте. Отдельная инфраструктура ради одного события. |
| Расширить `/admin/api-health` до «истории проверок» | Только для админа, требует ручного захода. Пользователь просил именно уведомление. |
| Просто участить тик поллера до 1 мин | Не решает главного — по-прежнему нет сигнала «пополнение дошло», и в 6 раз больше холостых перезапусков. |

## Риски и как их снять

| Риск | Митигация |
|---|---|
| Существующие тесты `test_resume_poller.py` вызывают `resume_paused_tasks()` без мока — реальный ping в CI | Параметр `pinger=None` с инъекцией, как уже сделано для `runner`. Дефолт — `api_ping`. |
| Событие пишется каждый тик при живом балансе | Пишем только если реально захвачено ≥1 задачи (`claimed`), иначе строки не будет. |
| Спам старыми событиями при первом заходе | Нет курсора в `localStorage` → сохраняем максимальный id молча, без тостов. |
| ПМ увидит чужие названия задач | Список фильтруется `visibility_filter`; событие показывается, если пользователю видна хотя бы одна возобновлённая задача (менеджеру — всегда). |
| `progress_log` засорится строками «проверка баланса» каждые 10 минут | Пишем только в `progress_message`, в `progress_log` не добавляем. |
| Ping не `ok` не из-за баланса (сеть, 401) | В тексте различаем: `is_balance_error` → «баланс всё ещё пуст», иначе → «API недоступен: код». Задачи в обоих случаях не трогаем. |
