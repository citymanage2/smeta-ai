# Почему смета подорожала после «оптимизаций»

Дата: 2026-07-28. Метод: разбор кода + git-хронология. Прод-замера в этой сессии не было.

## Короткий ответ

Ни одно из внедрённых изменений не снижало стоимость сметы напрямую. Главный рычаг из
замера 15.07 (`max_uses` для web search) так и не сделан. При этом три изменения
объективно увеличили расход, а два — исказили измерение.

## Хронология

| Дата | Что | Влияние на $ |
|---|---|---|
| 19.05 | `8ca6336` чанк 25 → 10 (ответ не влезал в max_tokens) | ×2.5 запросов → ×2.5 поисков |
| 15.07 | `eaf09e2` сокращение формата ответа | −3…7% (только output, 18% счёта) |
| 21.07 | `08d2b2f`/`403fd66` fast-режим (gather, concurrency 4) | 0 по токенам, + риск таймаутов |
| 21.07 | `6a0f850` batch-режим | −50% по прайсу Anthropic, если посредник даёт скидку |
| 23.07 | `137b738`/`a16d499` чекпоинт группы + пауза по балансу | + повторная оплата групп |
| 25.07 | `74e07b2` доступ через посредника | + наценка, вне модели расчёта |

## Причины, по убыванию вклада

### 1. Посредник: реальная цена токена больше не равна прайсу в коде
`_calc_cost` (claude_service.py:86-121) считает по прайсу Anthropic
(3/15/0.30/3.75 за Mtok). С 25.07 запросы идут через посредника
(`ANTHROPIC_BASE_URL`, claude_service.py:222-240). Признак агрегатора с предоплатой —
`InsufficientBalanceError` / 402 (claude_service.py:61-83). Наценка агрегатора,
непрокинутая batch-скидка и непрокинутая скидка на cache-read в логе не видны вообще.
Фаза 3 плана `plans/2026-07-25-anthropic-proxy-access.md` (свой прокси в ЕС на
настоящем ключе) не закрыта.

### 2. Ошибка одного чанка выбрасывает результаты всей группы из 8 — и они оплачиваются повторно
`_process_chunks` (task_processor.py:2237-2247) сначала выполняет все воркеры группы
через `_run_chunks_parallel`, и только потом применяет результаты. В
`_run_chunks_parallel` (task_processor.py:930-946) `gather(return_exceptions=True)`
дожидается **всех** чанков (все уже оплачены), после чего первое же исключение
поднимается наружу — `_apply_chunk_items` не вызывается, `_save_claude_partial`
не сохраняется. На resume `_pending_chunks` считает эти чанки несделанными и
оплачивает их заново. Окно потери — `ESTIMATE_MAIN_CHECKPOINT_GROUP = 8`
(task_processor.py:48).

Триггеры штатные, не экзотические:
- `InsufficientBalanceError` — пробрасывается намеренно (task_processor.py:2215-2217);
  ровно та «пауза по балансу», которую добавляли 23.07;
- `asyncio.TimeoutError` — пробрасывается без ретрая (task_processor.py:819-820);
  бюджет 1200 с включает бэк-офф по 429 (до 900 с, claude_service.py:194-197).

Итог: «пополнили баланс → resume» может стоить до 8 чанков лишних денег каждый раз.

### 3. Стоимость самого web search не считается нигде
`_calc_cost` учитывает только токены. Плата за поиски ($10/1000) и токены
затянутых страниц в модель не входят. Число поисков пропорционально числу запросов,
а запросов стало больше: основной проход чанками по 10 (task_processor.py:2252),
ретрай пропущенных по 5 (2286), ретрай null-цен по 5 (2310), `fix_empty_prices` по 5
(2673). Каждый мелкий чанк заново запускает свой набор поисков.

### 4. Fast-режим не экономит ни цента
Параллельность (`FAST_CHUNK_CONCURRENCY=4`, семафор процесса 6 — config.py:44-45)
меняет только время. Токены те же, а вероятность 429 → бэк-офф → таймаут выше,
что ведёт к п.2.

### 5. Кеш промпта фактически не работает
`cache_control` стоит только на system (claude_service.py:296-303), а `SYSTEM_BASE` —
около 120 токенов (task_processor.py:75-85), ниже минимума кешируемого префикса
(1024 токена для sonnet-4-6). Большой `PROMPT_ESTIMATE_FROM_LIST` лежит в
user-сообщении без `cache_control` и всё равно уникален на чанк. Значит
`cache_creation` (68% денег в замере 15.07) — это автокеш внутренних раундов
web search, которым мы управляем ровно одним параметром: `max_uses` в
`WEB_SEARCH_TOOL` (claude_service.py:199-202). Он не выставлен.

## Искажения метрики (лог ≠ реальность)

Занижают `cost_usd`:
- плата за web search не учитывается;
- неуспешные и таймаутнутые вызовы не логируются вовсе (лог пишется после успешного
  ответа, claude_service.py:401-414), хотя сгенерированные токены тарифицируются;
- наценка посредника не учитывается;
- `batch=True` уполовинивает стоимость безусловно (claude_service.py:118-120), даже
  если посредник batch-скидку не даёт.

Завышают `cost_usd`:
- `resume_from_batch` идемпотентен по смыслу, но `collect_claude_batch` логирует usage
  при **каждом** сборе (claude_service.py:648-650) → дубли строк в `api_call_log`
  после любого рестарта поллера.

## Что замерить, чтобы подтвердить

1. `backend/scripts/token_breakdown_estimates.sql` по периодам: до 15.07 / 21-25.07 /
   после 25.07, отдельно `fast` и `batch`. Смотреть не только `avg_usd`, но и
   среднее число вызовов на смету.
2. Сверить сумму `cost_usd` за период с фактическим списанием у посредника →
   получить коэффициент наценки.
3. Для batch-задач: число строк `api_call_log` на задачу против числа чанков —
   покажет дубли из п. «завышают».

## Что делать, по эффекту

1. `max_uses` в `WEB_SEARCH_TOOL` — единственный прямой рычаг по статье в 68% счёта.
2. Чекпоинт на чанк вместо группы из 8: применять успешные результаты и сохранять
   partial до того, как поднимать исключение. Убирает повторную оплату при паузе.
3. Учесть web search в `_calc_cost` и логировать неуспешные вызовы — иначе любые
   дальнейшие замеры остаются слепыми.
4. Пересмотреть размер чанка вверх (10 → 15-20): формат ответа сокращён 15.07, ради
   чего и делалась та правка.
5. Закрыть Фазу 3 плана по прокси — свой прокси на настоящем ключе вместо агрегатора.
