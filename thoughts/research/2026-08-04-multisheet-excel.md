# Исследование: мультилистовые Excel во всём цикле

Дата: 2026-08-04
Задача: файл заказчика с несколькими листами должен обрабатываться целиком, а не только первым
листом. Документ получает вкладки с названиями листов. Цикл перечень → полнота → смета →
оптимизация работает по всем вкладкам.

---

## 1. Как устроено сейчас

### 1.1 Точки, где берётся только первый лист

| Файл | Строка | Что делает | Кто зависит |
|---|---|---|---|
| `backend/app/utils/file_parser.py:159` | `ws = wb.active` | разбор гранд-сметы заказчика | `LIST_FROM_GRAND` (xlsx) |
| `backend/app/utils/xlsx_generic.py:154` | `ws = wb.active` | разбор перечня/полноты в строки документа | V0 всех generic-документов, документ входного файла |
| `backend/app/utils/xlsx_generic.py:218` | `ws = wb.active` | сборка xlsx из строк документа | «Применить» в перечне/полноте |
| `backend/app/utils/xlsx_cost_parser.py:60` | первый лист с «перечень» в имени | Path A сметы из загруженного файла | `ESTIMATE_FROM_LIST` |
| `backend/app/services/estimate_parser.py:159` | `ws = wb.active` | разбор чужой сметы в строки | `ESTIMATE_OPTIMIZATION`, V0 сметы |
| `backend/app/utils/xlsx_exporter.py:172` | один лист «Смета» | генератор файла сметы | `estimate_store.sync_artifacts` |
| `backend/app/utils/xlsx_optimizer.py:102,223` | `ws = wb.active` | разбор/запись при оптимизации по ABC | `routers/tasks.py` |
| `backend/app/services/excel_service.py:222` | листы «Перечень/Работы/Материалы/Записка» | генератор перечня | `LIST_FROM_GRAND`, `CHECK_*` |

Уже читают все листы: `utils/volume_probe.py`, `utils/xlsx_cost_parser.extract_total_cost`,
`utils/file_parser.parse_xlsx` (текстовое представление для ИИ), `routers/admin.py`.

### 1.2 Поток данных цикла

```
LIST_FROM_GRAND
  входной xlsx → parse_xlsx_grand (первый лист) → chunk_rows → Claude
  → accumulated_items  ──► task.progress_data['items']   (заморожено, «что выдал ИИ»)
                       └─► generate_list(items) → result.xlsx (4 листа)
                             → parse_xlsx_to_generic_rows(первый лист) → EstimateVersion V0

CHECK_LIST_COMPLETENESS
  source_task.progress_data['items'] → Claude → all_items → generate_list → V0

ESTIMATE_FROM_LIST
  Path B: source_task.progress_data['items']
  Path A: parse_list_sheet(загруженный xlsx, лист с «перечень» в имени)
  → цены (прайс/кеш/ИИ) → _run_estimate_step3 → generate_estimate_xlsx (один лист)
  → estimate_store.write_items → EstimateVersion(slot='estimate') + task.cost

ESTIMATE_OPTIMIZATION
  файл сметы → parse_estimate_excel (первый лист) → EstimateVersion(slot='result')
```

Важное следствие: **цикл идёт по `progress_data['items']`, а не по файлу.** Значит, если позиция
несёт признак листа, он доезжает до конца цикла сам собой — переразбирать xlsx на каждом шаге не
нужно.

### 1.3 Модель документа

* Документ = `(WorkflowCard, kind)`; `kind ∈ {list, completeness, estimate, optimization,
  summary-section}` (`services/document_service.py`).
* Строки живут в `EstimateVersion.rows` — один JSON-массив на версию.
  * generic: `{"row_id": str, "cells": {"Колонка": значение}}`
  * estimate: `{"id", "lineage_id", "num", "type", "name", "unit", "qty", "price_work",
    "price_material", "cost", ...}` (`utils/estimate_rows.py`)
* Версии — это **варианты оптимизации** (V0 оригинал, «Смета заказчика», «Без лишнего»…), а не
  листы. Версия несёт черновик, `rev`, коэффициент, историю правок, ссылку из
  `workflow_cards.primary_version_id` и снимок в `summary_estimates.sections`.
* В редакторе уже есть слово «вкладка» в двух смыслах: вкладки версий
  (`EditorVersionPanel`) и вкладки «Все / Работы / Материалы» (`EditorTab` в
  `stores/documentEditor.ts`). Оба заняты — листу нужен третий, отдельный уровень.

## 2. Варианты решения

### Вариант A — лист как измерение версии (`estimate_versions.sheet_name`)

Каждый лист = своя строка `EstimateVersion`. Документ становится `(card, kind, sheet)`.

* **+** Строки листа физически разделены; черновик и `rev` на лист.
* **−** Ломает смысл версии: «V1 — без лишнего» пришлось бы заводить на каждый лист, и матрица
  версия×лист расползается по всему коду (`primary_version_id`, `get_working_version`,
  сравнение версий, разделы сводной, `estimate_store`, `document_service.pick_version`).
* **−** Миграция БД + переписывание разрешения документа + новый параметр во всех 14 ручках
  `routers/documents.py`.
* **−** `task.cost` и файл сметы собираются из одной версии — придётся собирать из N.

### Вариант B — лист как поле строки (`row.sheet`)

Строки всех листов лежат в одном массиве `rows` по порядку; каждая несёт `sheet: "Раздел 1"`.
Вкладка в редакторе — фильтр по этому полю. Генератор xlsx группирует строки по `sheet` и пишет
по листу на группу.

* **+** Ноль изменений в модели БД, версиях, правах, черновике, `rev`, истории, сводной.
* **+** Признак листа едет по циклу вместе с позицией (`progress_data['items']` → полнота →
  смета) без единой новой связи между задачами.
* **+** Обратная совместимость даром: строка без `sheet` = документ из одного листа, вкладок нет,
  поведение прежнее.
* **+** «Применить» по-прежнему присылает весь документ — сцепка вкладок и черновика не нужна.
* **−** Порядок строк внутри массива должен уважать группировку по листам (иначе выгрузка
  перемешает). Решается сортировкой по (индекс листа, позиция) при сборке файла.
* **−** Операции над строками (вставка, удаление, перетаскивание) должны работать внутри листа —
  нужна аккуратность на фронте.
* **−** Колонки у разных листов могут отличаться (у generic-документов): таблица показывает
  колонки активного листа, а не объединение.

### Вариант C — карточка на лист

Каждый лист → отдельная `WorkflowCard`.

* **−** Пользователь просил вкладки внутри одного документа, а не N смет в проекте.
* **−** Разносит один тендер по нескольким карточкам, ломает сводную и итог контракта.

### Вывод

**Берём вариант B.** Он единственный, который не трогает несущие конструкции (версии, права,
черновик, `rev`, сводная) и при этом даёт ровно то, что просили: один документ — несколько
вкладок по названиям листов. Стоимость — аккуратность в трёх генераторах xlsx, трёх парсерах и
операциях над строками в редакторе.

Такую же модель используют промышленные импортёры таблиц (SheetJS: `workbook.SheetNames` +
`sheet` на каждой записи; pandas: `read_excel(sheet_name=None)` → dict листов): лист — атрибут
данных, а не отдельная сущность хранилища.

## 3. Что придётся тронуть

### Backend

1. `utils/xlsx_generic.py` — `parse_xlsx_to_generic_rows`: разбирать все листы (шапка ищется в
   каждом отдельно), класть `sheet` в строку; `rows_to_xlsx`: лист на группу, свой набор колонок
   у каждого листа.
2. `utils/file_parser.py` — `parse_xlsx_grand`: обходить `wb.worksheets`, помечать строки листом;
   `chunk_rows`: не смешивать листы в одном чанке.
3. `utils/xlsx_cost_parser.py` — `parse_list_sheet`: брать все листы с данными, а не первый
   «перечень»; `sheet` в позицию.
4. `services/estimate_parser.py` — `parse_estimate_excel`: все листы, `sheet` в строку.
5. `services/excel_service.py` — `generate_list`: при нескольких листах — лист на источник
   (плюс «Пояснительная записка»); при одном — прежние 4 листа.
6. `utils/xlsx_exporter.py` — `generate_estimate_xlsx`: лист на группу со своим блоком итогов,
   плюс общий итог; возвращаемый `grand_total` — сумма по всем листам.
7. `utils/estimate_rows.py` — `item_to_row` / `row_to_item`: `sheet` в списке переносимых полей.
8. `services/task_processor.py` — сохранять `sheet` при разборе ответов Claude по чанкам;
   `_create_initial_generic_version` — без изменений (парсер сам разберёт все листы).
9. `utils/xlsx_optimizer.py` — `parse_estimate_xlsx` / `generate_optimized_xlsx`: все листы.
10. `utils/xlsx_statement.py` — выгрузка-ведомость: лист на группу (или колонка «Лист»).
11. Санитайзер имени листа: Excel запрещает `: \ / ? * [ ]`, длину > 31, пустое имя и дубли.
    Нужен один помощник, а не три копии.

### Frontend

12. `stores/documentEditor.ts` — состояние активного листа (`sheet`), список листов из строк.
13. `components/editor/adapters/types.ts` + оба адаптера — `sheetOf(row)`, `withSheet(row, name)`,
    колонки по активному листу, итоги по листу и по документу.
14. `components/editor/DocumentEditor.tsx` — полоса вкладок листов; фильтрация `displayedRows`;
    вставка/удаление/перетаскивание строк внутри листа; итоги «по листу / по документу».
15. `components/editor/rowOps.ts`, `actions/priceInsert.ts` — новые строки наследуют активный лист.
16. `pages/ProjectCardPage.tsx` — активный лист в адресе (`?sheet=`), рядом с `stage`, `version`,
    `tab`.
17. `utils/estimateCalc.ts` — итоги с разбивкой по листам.

### Тесты

18. `backend/tests/test_xlsx_generic_headers.py`, `test_generic_service_rows.py` — круговой прогон
    многолистового файла.
19. Новый тест на согласие «экран = файл» для многолистовой сметы (точные числа).
20. Фронтовые тесты на вкладки листов и на то, что правка в одной вкладке не трогает другие.

## 4. Риски и краевые случаи

| Риск | Как закрываем |
|---|---|
| Служебные листы гранд-сметы («Титульный», «Подписи») дадут пустые вкладки | лист, из которого не извлеклось ни одной строки, не попадает в документ |
| Имена листов совпадают после обрезки до 31 символа | санитайзер добавляет суффикс `(2)` |
| Старые документы без `sheet` | строка без поля = единственный безымянный лист, вкладок не показываем |
| Один лист в файле | поведение обязано остаться прежним — закрепляем тестом |
| Черновик, сохранённый до правки | строки без `sheet` попадут в лист по умолчанию, данные не теряются |
| Чанки Claude мешают листы → позиции получают чужой лист | чанкуем строго внутри листа |
| Стоимость обработки: N листов = N× чанков | это и есть запрошенная работа; предупреждаем оценкой объёма (`eta_service.measure_task_volume` уже считает по всем листам) |
| «Применить» с активной вкладкой шлёт только её строки | store держит **все** строки, вкладка — только фильтр показа |

## 5. Рекомендация

Реализовать вариант B в четыре фазы, каждая самостоятельно проверяема:

1. **Фаза 1 — фундамент**: признак листа в строках/позициях, санитайзер имён, generic-парсер и
   generic-генератор на все листы. Проверяется круговым прогоном xlsx → строки → xlsx.
2. **Фаза 2 — перечень и полнота**: `parse_xlsx_grand` по всем листам, чанки внутри листа,
   `generate_list` с листом на источник. Цикл перечень → полнота работает по вкладкам.
3. **Фаза 3 — смета и оптимизация**: `parse_list_sheet`, `parse_estimate_excel`,
   `generate_estimate_xlsx` с итогами по листу и общим итогом, `xlsx_optimizer`.
4. **Фаза 4 — редактор**: вкладки листов, фильтрация, операции внутри листа, итоги, адрес страницы.

Ключевое правило проекта — «экран и скачиваемый файл считают по одной формуле» — при разбивке на
листы становится главным местом ошибки. Каждая фаза, трогающая деньги, закрывается тестом с
точными числами по многолистовому файлу.
