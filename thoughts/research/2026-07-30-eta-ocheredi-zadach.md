# Исследование: расчётное время старта и выполнения задачи в очереди

Дата: 2026-07-30
Задача: показать в очереди, когда задача запустится и через сколько будет результат.
Оценка — по объёму работы (позиции перечня, листы проекта, позиции гранд-сметы).

## 1. Что уже есть в коде

### Очередь и воркер
- `backend/app/services/job_queue.py` — durable-очередь на таблице `jobs`.
  Порядок выдачи: **round-robin по владельцу** (наименьшее число running-job у владельца),
  тай-брейк `priority DESC, created_at ASC` (`claim_one`, строка 115).
- `backend/app/worker.py` — пул из `WORKER_CONCURRENCY` слотов (по умолчанию **4**, `config.py:52`).
  Один слот = одна job. Job'ы бывают разных kind: `task.process`, `task.optimize`,
  `task.fix_prices`, `version.optimize`, `version.fill_prices`, `retrain`.
- Batch-режим (`ESTIMATE_FROM_LIST` + `processing_mode='batch'`): задача живёт в `processing`
  **без job** (`_stage='batch_pending'`), досчитывает `batch_poller`. Слот воркера при этом
  НЕ занят — важно для модели ожидания.

### Что видно в UI сейчас
- `frontend/src/components/dashboard/DashboardQueue.tsx` — таблица «Активная очередь»:
  тип, проект, **сколько уже висит** (`elapsedLabel` от `created_at`), прогресс, статус.
  Прогноза нет — пользователь видит «5 ч 57 мин» и не понимает, ждать ещё час или сутки.
- `frontend/src/pages/TaskStatus.tsx` — карточка задачи (основной экран для менеджера),
  есть heartbeat-индикатор живости, прогноза тоже нет.
- Данные очереди отдаёт `GET /dashboard/stats` → `active_queue: list[ActiveTask]`
  (`backend/app/routers/dashboard.py:36`, 178-202).

### Откуда взять объём работы (units)
| Тип задачи | Единица | Источник на момент создания |
|---|---|---|
| `LIST_FROM_GRAND` | строк в xlsx | загруженный файл (`raw_file_bytes` в `create_task`) |
| `LIST_FROM_PROJECT` | страниц PDF | `get_pdf_page_count` (`utils/pdf_ocr_extractor.py:153`) |
| `CHECK_LIST_COMPLETENESS` | позиций | `source_task.progress_data["items"]` |
| `CHECK_PROJECT_COMPLETENESS` | позиций | то же |
| `ESTIMATE_FROM_LIST` (Path B) | позиций | `source_task.progress_data["items"]` (`tasks.py:574`) |
| `ESTIMATE_FROM_LIST` (Path A) | строк xlsx / страниц | загруженный файл |
| `ESTIMATE_OPTIMIZATION` | позиций | `payload["items"]` при запуске |

То есть объём **известен до старта обработки** во всех случаях — отдельного «прохода
разведки» не нужно.

### Чего НЕ хватает
1. **Фактической длительности обработки.** У `tasks` есть только `created_at`/`updated_at`.
   `updated_at - created_at` = ожидание в очереди + расчёт. При ожидании в 5 часов это
   негодная база для калибровки. `jobs.claimed_at` не подходит: его двигает heartbeat,
   он равен времени последнего сигнала, а не старта.
2. **Сохранённого объёма.** Позиции считаются уже внутри обработки; в БД числа нет.

Вывод: нужны поля `started_at` / `finished_at` и `volume_units` / `volume_kind` в `tasks`
(миграция 041 — следующий номер, последняя `040_add_system_events.py`).

## 2. Как эту задачу решают другие

- **Slurm `squeue --start` / backfill-планировщик** — симуляция расписания: берём заявленную
  длительность каждой задачи, раскладываем по свободным слотам, получаем время старта.
  Ключевая идея: прогноз старта = симуляция, а не формула.
- **GitLab CI / Buildkite «estimated wait time»** — историческая медиана длительности job
  того же типа × число задач впереди / число раннеров.
- **AWS Batch, Azure Batch** — не показывают ETA вовсе, только позицию: признание того, что
  ложная точность хуже отсутствия числа.
- **Google/Uber ETA** — базовая формула `база + коэффициент × объём`, коэффициент
  пересчитывается на скользящем окне последних наблюдений (онлайн-калибровка).
- Общий приём во всех зрелых системах: **медиана, а не среднее** (одна задача-выброс на
  6 часов не должна ломать прогноз) и **явное «примерно»** в интерфейсе.

## 3. Варианты решения

**A. Жёсткие константы «секунд на единицу» в конфиге.**
+ 20 строк кода, ноль миграций.
− Мгновенно устаревают: смена модели/промпта/лимита web-поиска меняет время в разы.
  Проект активно меняет промпты (см. `.business` и историю коммитов) — константы будут врать.

**B. Историческая медиана длительности по типу задачи (без объёма).**
+ Самокалибруется, миграция минимальная (`started_at`/`finished_at`).
− Игнорирует объём — а именно его просил учитывать пользователь. Перечень на 30 позиций и
  на 1200 позиций получат одинаковый прогноз (в проекте разброс реально ×40).

**C. Линейная модель `T = база + ставка × units`, ставка калибруется по истории (медиана
   `длительность / units` по последним N завершённым задачам того же типа), fallback на
   константы, пока истории нет. Ожидание в очереди — симуляция list-scheduling по
   `WORKER_CONCURRENCY` слотам.**
+ Учитывает объём (требование пользователя) и самокалибруется (не устаревает).
+ Симуляция даёт честное «когда стартует» с учётом уже бегущих задач и их остатка.
+ Устойчива: медиана гасит выбросы, клампы не дают выдать «через 3 секунды» или «через
  неделю».
− ~150 строк сервиса + миграция + тесты.

**D. Регрессия/ML по признакам.**
− Оверкилл: 6 типов задач, десятки наблюдений в неделю. Данных на обучение нет.

## 4. Вывод и рекомендация

**Выбираем C.** Это то, что делают Slurm и CI-системы, и это единственный вариант, который
одновременно (1) учитывает объём, как просил пользователь, (2) не устаревает при смене
промптов, (3) отвечает на оба вопроса — «когда стартует» и «когда будет готово».

Конкретика реализации:
1. Миграция 041: `tasks.started_at`, `tasks.finished_at`, `tasks.volume_units`,
   `tasks.volume_kind` (все nullable, `IF NOT EXISTS`).
2. Объём считается при создании задачи (дёшево: `fitz` для PDF, `openpyxl read_only` для
   xlsx, `len(items)` для Path B), в потоке, ошибка probe → `volume_units=None` (не ломаем
   создание задачи).
3. `started_at`/`finished_at` проставляются в `TaskProcessor.update_status`.
4. Новый `backend/app/services/eta_service.py`:
   - `calibrate(db)` → по типам: медиана сек/единица за последние N завершённых задач
     (нужно ≥3 наблюдения, иначе константа по умолчанию);
   - `estimate_queue(db, tasks)` → симуляция по слотам, для каждой задачи
     `{wait_s, run_s, ready_at, confidence}`.
5. Отдаём в `GET /dashboard/stats` (очередь) и `GET /tasks/{id}/status` (карточка).
6. UI: колонка «Готовность» в `DashboardQueue`, строка «Результат примерно к HH:MM
   (≈ N мин)» в `TaskStatus`.

Ограничения, которые надо честно принять и отразить в UI:
- round-robin по владельцу не воспроизводится симуляцией точно → прогноз старта
  приблизителен при нескольких владельцах в очереди;
- пауза по балансу API, ретраи и рестарты воркера прогноз не учитывает;
- поэтому число показываем только с «≈» и никогда как точное время.
