## I. ЧТО РЕАЛИЗОВАНО ХОРОШО — не трогать

### 1. Архитектура хранения смет (EstimateVersion)

Система версий сметы сделана грамотно: каждая версия хранит `rows` как JSON-снапшот, есть `is_rolled_back`, `file_slot`, `version_display_name`. Откат без потери данных, история правок через `TaskHistory`. Это правильное решение — у конкурентов (даже западных) этого нет.

### 2. Многоуровневый поиск цен

Стратегия `exact match → embedding similarity (Cohere, порог 0.93) → web search` — технически сильное решение. Numpy-матрицы в памяти для быстрого cosine similarity, batch embedding для 10–20 позиций одновременно, кеш загружается при старте. Быстрее и дешевле, чем гонять каждый запрос в Cohere.

### 3. Защита от зависших задач при рестарте

`restore_stuck_tasks()` в lifespan — правильный паттерн. Задачи, застрявшие в `processing`, автоматически переводятся в восстанавливаемое состояние.

### 4. Retry-логика на уровне чанков

`_call_claude_json_with_retry()` с задержками `(5s, 15s, 30s)` и `_interruptible_claude_json_with_retry()` — транзиентные ошибки Claude не роняют задачу.

### 5. Чанкование с сохранением прогресса

`progress_data` в JSONB позволяет продолжить задачу после сбоя с нужного чанка:
```python
start_chunk = progress_data.get("chunks_done", 0)
```

### 6. Трекинг стоимости API

`ApiCallLog` с разбивкой на `input / output / cache_read / cache_creation` токены — полная себестоимость каждой задачи. Редкость для внутренних инструментов.

### 7. Soft delete везде

`deleted_at` на Task и Project, корзина с восстановлением — данные не теряются.

### 8. Prompt caching для PDF

Ephemeral cache (5 мин TTL) на страницы PDF при OCR — экономит деньги на повторных обработках одного документа.

## II. КРИТИЧЕСКИЕ УЯЗВИМОСТИ — провалишься уже сейчас

### 🔴 КРИТИЧНО 1: Нестабильность цен между запусками

**Проблема.** Для позиций, не найденных в прайсе (unmatched), цена определяется Claude через web search. Каждый запрос — новый поиск, новый набор источников, новая «средняя из трёх». Одна и та же позиция в разные дни легко даёт разброс 15–40%.

**Механизм провала.** `PROMPT_ESTIMATE_FROM_LIST` требует «среднюю из 3 источников г. Екатеринбург», но Claude при каждом вызове находит разные сайты, разные прайсы, разные даты обновления. Нет фиксации источников. Нет кеширования результатов web search по имени позиции.

**Когда провалишься.** Прямо сейчас — при любом повторном создании сметы на тот же перечень.

**Решение.** Кешировать результаты web-поиска по `normalize(name)` в таблице `price_works` / `price_materials`. Если позиция уже искалась за последние 30 дней — брать из кеша. Это же решает требование «расхождение ≤ 5%».

**Оценка:** 2 дня.

---

### 🔴 КРИТИЧНО 2: Потеря позиций при чанковании больших смет

**Проблема.** `_chunk_by_work_boundaries()` делит список на чанки по 200 элементов. Claude обрабатывает каждый чанк независимо. При мёрдже результатов используется `id` позиции. Если Claude пропустил позицию в чанке — она тихо исчезает. Нет проверки: «количество выходных позиций = количество входных».

**Механизм провала.** Смета из 300+ позиций → Claude в чанке 2 из 3 пропустил 5 строк → в итоговой смете нет этих работ → финансовые потери на тендере.

**Код.** `task_processor.py`, строки 1745–1780: есть retry для пропущенных ID малым батчем, после чего логируется `"Some items remain unpriced after retry"` и задача продолжается. Позиция уходит в смету с нулевой ценой или без цены.

**Когда провалишься.** При каждой смете > 200 позиций.

**Решение.**
1. После каждого чанка: `missing = set(chunk_input_ids) - set(chunk_output_ids)`. Если не пусто — повтор чанка целиком (2 попытки).
2. После финального мёрджа: если пропуски остались — добавить строки с `price = None`, `flag = "requires_manual_review"`, показать красным в UI.
3. Счётчик «N позиций требуют ручной проверки» с фильтром.

**Оценка:** 1–2 дня.

---

### 🔴 КРИТИЧНО 3: Нет валидации итоговой суммы

**Проблема.** После того как Claude проставил цены, нет проверки адекватности результата. Если Claude выдал 1 руб/м² вместо 1000 руб/м² (потеря разряда, путаница единиц: тонна/кг, штука/100 штук) — смета уходит к пользователю с неверной суммой.

**Когда провалишься.** При любой работе с нестандартными позициями.

**Решение.**
- Цена `work_price` не должна отличаться от медианы по аналогичным работам в прайсе более чем в 10×.
- Итоговая стоимость на 1 м² (если есть площадь) должна попадать в диапазон [5 000, 150 000] ₽/м² для общегражданского строительства.
- Аномалия → флаг `price_anomaly = true` на строке, оранжевая подсветка в UI, tooltip «Цена необычно [высокая/низкая] по сравнению с аналогами».

**Оценка:** 2 дня.

---

### 🟠 СЕРЬЁЗНО 4: Файлы в БД — переполнение через 1–2 месяца

**Проблема.** `TaskInputFile.content` и `TaskResult.file_data` — `LargeBinary` в PostgreSQL. Нет retention policy.

**Расчёт.** 10 задач/день × 30 МБ в среднем = 300 МБ/день = 9 ГБ/месяц. Через 2–3 месяца активной работы БД наполнится или упрётся в лимит плана на Render.com.

**Когда провалишься.** Через 1–2 месяца.

**Решение.** S3-совместимое хранилище (Cloudflare R2 или Yandex Object Storage) для файлов. В БД — только метаданные + ссылка. Retention: входные файлы удалять через 30 дней, результаты — через 90 дней.

**Оценка:** 3–4 дня.

---

### 🟠 СЕРЬЁЗНО 5: JWT без ротации, единый пароль на всех

**Проблема.** `USER_PASSWORD` и `ADMIN_PASSWORD` — единые пароли для команды. Если сотрудник уволился — нужно менять пароль для всех. Нет персональных аккаунтов. JWT на 24 часа, нет refresh token, нет инвалидации сессии.

**Когда провалишься.** При первом уходе сотрудника.

**Решение (краткосрочное).** Таблица `users` с `username, hashed_password, role, is_active`. Не ломает текущую auth-архитектуру — только расширяет проверку.

**Оценка:** 1 день.

---

### 🟠 СЕРЬЁЗНО 6: Нет мониторинга и алертов

**Проблема.** Нет уведомления, если задача зависла, Claude вернул 500, или смета сформирована с аномальными ценами. Dashboard есть, но его нужно открывать руками.

**Когда провалишься.** При первой задаче, зависшей на 2 часа без уведомления.

## III. ЧТО ПРОВАЛИТСЯ ЧЕРЕЗ НЕДЕЛЮ

### 🟡 7: Polling каждые 2–3 секунды

Frontend делает `GET /tasks/{id}/status` каждые 2–3 секунды. При 3–5 одновременных задачах — 10–15 запросов/сек только на polling. На дешёвом плане Render.com это риск rate limit и лишней нагрузки.

**Решение.** Server-Sent Events (SSE): `GET /tasks/{id}/stream` с `text/event-stream`. Frontend: `EventSource`. Снижает нагрузку в 10×.

**Оценка:** 1 день.

---

### 🟡 8: .gsn файлы ГРАНД-Сметы не поддерживаются

Есть явный запрет на `.gsn`. Но именно `.gsn` — нативный формат ГРАНД-Сметы. Пользователи будут приходить с ним и получать «файл не поддерживается». Файл `.gsn` — это XML под другим расширением.

**Оценка:** 2 дня.

---

### 🟡 9: Нет визуального прогресс-бара для больших смет

При 300+ позициях разбитых на чанки пользователь видит текст «Обрабатываю чанк 2 из 3». Нет прогресс-бара с процентом. Пользователи обновляют страницу, убивая polling.

`progress_data` уже содержит `chunks_done / total_chunks` — данные есть, нужно только показать в UI.

**Оценка:** 1 день.

## IV. ЧТО ПРОВАЛИТСЯ ЧЕРЕЗ МЕСЯЦ

### 🟡 10: Деградация качества без обратной связи

Нет цикла: пользователь принял/отредактировал цену → цена попадает в прайс → улучшает будущие поиски. `manually_edited_at` фиксирует факт редактирования, но не передаёт значение обратно в базу цен.

**Эффект.** Через месяц web-поиск по тем же популярным позициям даёт то же качество, хотя накоплено 500+ реальных принятых цен.

**Оценка:** 2 дня.

---

### 🟡 11: Масштабирование на 2+ одновременных пользователя

Нет очереди задач — каждая задача запускается как FastAPI background task в том же процессе. При 3+ одновременных задачах с web search все конкурируют за один asyncio event loop. Rate limit от Claude срабатывает чаще.

**Решение.** arq (async job queue) или Celery + Redis. arq проще интегрируется с FastAPI.

**Оценка:** 3 дня.

## V. РАБОТА С БОЛЬШИМИ СМЕТАМИ — специальный раздел

### Точка отказа 1: Тихая потеря позиций при чанковании
→ см. Критично 2. Приоритет №1.

### Точка отказа 2: Ошибка объёмов при двухпроходной обработке

`LIST_FROM_PROJECT_PASS2` делает второй проход для заполнения `quantity = null`. Если в первом проходе 150 позиций, а во втором Claude вернул 140 — при мёрдже 10 позиций останутся с `null`. Нет проверки полноты мёрджа.

**Решение.** `assert len(pass2_result) >= len(null_items)` перед мёрджем.

### Точка отказа 3: Timeout на больших PDF

`TASK_TIMEOUT_SECONDS: 600` (10 минут). PDF на 200 страниц с OCR → Tesseract на каждую → Claude по чанкам → может занять 15–20 минут. Задача упадёт с timeout.

**Решение.** Отдельный timeout для PDF/OCR задач: 1800 секунд.

### Точка отказа 4: Некорректный маппинг колонок в чужих Excel

`estimate_parser.py` определяет колонки по ключевым словам. Если колонка называется «Стоимость материалов» вместо «Цена материалов» — парсер не сопоставит. Нет fallback на позицию колонки.

**Решение.** Fuzzy-маппинг (расстояние Левенштейна) + fallback: 1-я числовая колонка = цена работ, 2-я = цена материалов.

### Точка отказа 5: Нет контрольной суммы при экспорте

После формирования `EstimateVersion.rows` и сохранения в БД — при экспорте в XLSX нет проверки, что сумма в файле = сумме в БД.

**Решение.** После генерации XLSX: парсинг итогового листа, сравнение с `sum(row.cost for row in rows)`. Расхождение > 1% → ошибка экспорта.

### Незакрытая ниша

Ни один продукт на российском и зарубежном рынке **не умеет**:
- Принять произвольный XLSX/PDF от заказчика/конкурента
- Перебить в корпоративный формат
- Проверить полноту по нормативной базе РФ

Это и есть ниша smeta-ai. Окно возможностей открыто — ближайшие игроки (FreeSmetaOnline, ПростоСмета) двигаются из другой точки (генерация с нуля) и при наличии инвестиций могут дорасти через 1–2 года.
