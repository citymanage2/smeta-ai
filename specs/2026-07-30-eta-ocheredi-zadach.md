# Спека: расчётное время старта и готовности задачи

Дата: 2026-07-30
Исследование: `thoughts/research/2026-07-30-eta-ocheredi-zadach.md`

## Проблема

В «Активной очереди» видно только сколько задача уже висит («5 ч 57 мин»). Непонятно:
запустится она через минуту или через три часа, и сколько будет считаться. Менеджер не
может сказать клиенту, когда будет смета, и не понимает, ждать или отменить и перезапустить.

## Цель

Для каждой активной задачи показывать: **когда начнётся расчёт** и **когда будет результат** —
исходя из объёма работы (позиции перечня / листы проекта / позиции гранд-сметы) и того,
что сейчас в очереди.

## Что входит в объём (Scope)

1. Объём работы фиксируется в момент создания задачи (число позиций, страниц или строк).
2. Фактическая длительность расчёта пишется в БД (начало и конец обработки).
3. Прогноз считается по калиброванной на истории ставке «секунд на единицу» с симуляцией
   очереди по числу слотов воркера.
4. Прогноз отдаётся в API очереди (`/dashboard/stats`) и карточки задачи (`/tasks/{id}/status`).
5. Прогноз показывается в таблице «Активная очередь» и на странице статуса задачи.

## Не входит (Non-Goals)

- Изменение порядка выполнения задач, приоритетов, числа воркеров.
- Прогноз для задач в паузе (ждут баланса) и для повторных попыток после сбоя.
- Точность «до минуты»: показываем оценку с «≈», не обещание.
- Уведомления/пуши о готовности.
- Прогноз стоимости (уже есть отдельно).

## Критерии приёмки

**AC-1.** У задачи в статусе `pending` в очереди видно ожидаемое время старта
(«старт ≈ через 25 мин») и ожидаемое время готовности («готово ≈ 14:10»).

**AC-2.** У задачи в статусе `processing` видно ожидаемое время готовности с учётом уже
затраченного времени; если расчётное время вышло, показывается «завершается» (а не
отрицательное или «через 0 мин»).

**AC-3.** Прогноз длительности зависит от объёма: перечень на 1000 позиций получает
существенно больший прогноз, чем на 50 позиций (при одинаковом типе задачи).

**AC-4.** Прогноз старта учитывает: число слотов воркера (`WORKER_CONCURRENCY`), задачи,
которые уже считаются (их остаток), и очередь впереди.

**AC-5.** Ставка «секунд на единицу» калибруется по фактическим длительностям завершённых
задач того же типа; при отсутствии истории (<3 наблюдений) используется значение по
умолчанию, а прогноз помечается как грубый.

**AC-6.** Если объём определить не удалось (битый файл, нестандартный формат) — задача
создаётся штатно, прогноз строится по медианной длительности типа, без падений.

**AC-7.** Batch-задачи (`_stage='batch_pending'`) не считаются занимающими слот воркера при
расчёте ожидания для остальных.

**AC-8.** На странице задачи (`TaskStatus`) видно строку с ожидаемым временем готовности,
пока задача не завершена.

## Ограничения

- Порядок выдачи из очереди — round-robin по владельцу, симуляция воспроизводит его
  приблизительно (по `created_at`). Расхождение допустимо, в UI — «≈».
- Расчёт прогноза не должен добавлять к `/dashboard/stats` заметной нагрузки: один
  дополнительный запрос за калибровкой, не N+1.
- Пробинг объёма при создании задачи не должен блокировать ответ дольше ~1 с и не должен
  ронять создание задачи при любой ошибке.
- Изменение моделей → обязательная миграция с `IF NOT EXISTS` (правило проекта).

## Как проверяем

- Юнит-тесты на симуляцию очереди (слоты, остаток бегущих, batch без слота).
- Юнит-тесты на калибровку (мало данных → дефолт; выброс не ломает медиану).
- Тест на пробинг объёма (pdf/xlsx/Path B/битый файл).
- Тест API: поля прогноза приходят в `/dashboard/stats` и `/tasks/{id}/status`.
- Фронт-тест: отображение «старт ≈ …» / «готово ≈ …» и «завершается» при просрочке.
