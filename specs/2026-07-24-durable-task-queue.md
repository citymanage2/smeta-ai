# Spec: durable-очередь задач для мультиюзера

**Дата:** 2026-07-24
**Research:** [thoughts/research/2026-07-24-durable-task-queue.md](../thoughts/research/2026-07-24-durable-task-queue.md)
**Timeweb-чек-лист:** [plans/2026-07-24-timeweb-архитектура-и-доработки.md](../plans/2026-07-24-timeweb-архитектура-и-доработки.md)
**Статус:** решения зафиксированы — личные аккаунты (owner_id) + DIY-claim (SKIP LOCKED) + Timeweb App Platform (Docker Compose).

## Problem

Обработка задач сейчас — fire-and-forget через FastAPI BackgroundTasks в том же web-процессе. Для нескольких пользователей это ломается:
- CPU-работа (xlsx/PDF/OCR) блокирует единственный event loop → одна тяжёлая задача морозит всех.
- Задачи «в полёте» живут в памяти → рестарт/редеплой/краш теряет их.
- Нет глобального лимита к Anthropic → N юзеров × чанки → 429/paused каскадом.
- Нет честности: один юзер с 20 задачами блокирует остальных.
- Система не различает людей — только 2 общих пароля.

## Goal

До 3 активных пользователей ставят до 20 задач каждый; задачи обрабатываются **реально параллельно**, **не теряются** при рестарте, **не блокируют друг друга**, с **честным** распределением между пользователями и **предсказуемой** нагрузкой на Anthropic.

## Scope

1. **Реальные пользователи.** Индивидуальные аккаунты (логин+пароль на человека), `owner_id` у задачи. Роль (`user`/`admin`) сохраняется.
2. **Durable-очередь** на PostgreSQL: отдельная таблица очереди, атомарный claim через `FOR UPDATE SKIP LOCKED` + короткая транзакция, visibility-timeout + heartbeat, авто-возврат зависших job.
3. **Отдельный worker-процесс** (та же кодовая база): пул async-слотов, забирает job из очереди, гоняет обработку; вся CPU-работа — вне web.
4. **Продьюсеры только ставят в очередь.** Убрать все `background_tasks.add_task(...)` (7 основных + 4 вспомогательных). Убрать `_recover_stuck_tasks`.
5. **Честность (round-robin по owner_id):** приоритет владельцу с наименьшим числом задач «в работе», тай-брейк по времени постановки.
6. **Лимиты нагрузки:** глобальный лимит одновременных job (env, 3–6) + глобальный семафор одновременных вызовов Anthropic (защита от 429). Внутризадачный `FAST_CHUNK_CONCURRENCY` — в env.
7. **Поллеры** batch/resume/cleanup переезжают в worker (`max_instances=1`), из web убираются.
8. **Deploy Timeweb App Platform (Docker Compose):** один App = web-контейнер (первый, с доменом) + worker-контейнер; managed PostgreSQL; прод-compose без `volumes`/`--reload`; миграции гонит один сервис.

## Acceptance Criteria

- [ ] AC1. Каждый менеджер входит под своим логином; у созданной задачи проставлен `owner_id`; в списке/аудите видно владельца.
- [ ] AC2. Задачи обрабатывает отдельный worker-процесс; web во время тяжёлой генерации xlsx/PDF/OCR остаётся отзывчивым (эндпоинты отвечают).
- [ ] AC3. Рестарт worker/web в середине обработки не теряет задачу: после перезапуска она возвращается в очередь и доигрывается с чекпоинта (или с начала, если чекпоинта нет). `batch_pending` не трогается.
- [ ] AC4. Одновременно исполняется не более N job (env, дефолт в диапазоне 3–6); лишние ждут в очереди.
- [ ] AC5. Round-robin: если юзер A поставил 20 задач, а юзер B — 1 позже, задача B начинает исполняться, не дожидаясь опустошения очереди A.
- [ ] AC6. Два worker-слота не берут одну и ту же job (проверка на гонку claim).
- [ ] AC7. Глобальный лимит одновременных вызовов Anthropic соблюдается; под нагрузкой нет каскада 429 (при исчерпании баланса задача корректно уходит в `paused` и позже возобновляется).
- [ ] AC8. Все 6 типов задач + 4 вспомогательных раннера (optimization, fix-prices, version-steps, retraining) идут через очередь; двух разных механизмов фона не остаётся.
- [ ] AC9. Поллеры batch/resume/cleanup работают из worker в одном экземпляре; в web их нет.
- [ ] AC10. Прод-конфигурация: один App (web+worker) в docker-compose без запрещённых директив, managed Postgres; миграции применяются один раз без гонки.

## Constraints

- Postgres-only, без Redis/новых брокеров. Без внешних библиотек очередей (procrastinate/celery/arq) — claim на своей таблице.
- Драйвер asyncpg; пул поднять под число воркеров.
- Alembic: следующая миграция `030_`, `IF NOT EXISTS`, линейная цепочка от `029`.
- Timeweb App Platform запрещает `volumes/privileged/network_mode:host` в compose → база только managed.
- Обратная совместимость: существующие задачи (`owner_id IS NULL`) не должны падать; чекпоинты (`progress_data`) и `resume_from_batch` переиспользуются как есть.

## Non-Goals

- Не мигрируем на Redis/Celery/procrastinate.
- Не переписываем саму логику обработки задач (`TaskProcessor` и хендлеры остаются) — меняем только КАК она запускается.
- Не строим админ-панель управления пользователями с UI ролей/прав (достаточно создания аккаунтов + логина).
- Не делаем горизонтальное масштабирование на несколько worker-контейнеров в этой итерации (закладываем возможность, запускаем один).
- Не трогаем внешний Anthropic Batch API flow по существу (batch_pending остаётся особым случаем).
