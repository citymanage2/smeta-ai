# Методология: Шаг 3 — Оптимизация по технологиям

**Дата:** 2026-04-23  
**Статус:** Согласовано  
**Контекст:** Третий шаг модуля оптимизации. Работает с Версией 2 (результат Шага 2).

---

## Цель

Найти позиции, где CityManage может выполнить ту же работу **дешевле за счёт другой технологии** — без изменения конечного результата для заказчика.

Два направления анализа:

| Направление | Код | Описание |
|---|---|---|
| Технологическая замена | `technology` | Та же работа, другим способом — производительнее, механизированно, с меньшими трудозатратами |
| Оптимизация операций | `operations` | Меньше вспомогательных операций за счёт технологической синергии |

## Два этапа внутри шага

### Этап А — ABC-анализ (код, без AI, мгновенно)

Выполняется сразу при нажатии кнопки, до запроса к Claude.

**Алгоритм:**
1. Отбираем строки с типом `work` (только работы, без материалов и секций)
2. Считаем суммарную стоимость всех работ
3. Сортируем работы по убыванию `cost`
4. Считаем накопленный итог от суммы работ, присваиваем группу:
   - **Группа A** — работы, формирующие 0–80% суммы работ → идут в VE-анализ Claude
   - **Группа B** — работы, формирующие 80–95% суммы работ → не анализируются
   - **Группа C** — работы, формирующие 95–100% суммы работ → не анализируются
5. Поле `abc_group` обновляется в строках-работах активной версии (сохраняется в БД)

**Результат отображается в UI сразу:**
```
Группа А: 7 позиций  •  3 840 000 ₽  •  79% суммы работ  →  анализируются
Группа Б: 12 позиций  •  720 000 ₽  •  15% суммы работ  →  не анализируются
Группа В: 18 позиций  •  240 000 ₽  •  5% суммы работ  →  не анализируются
```

---

### Этап Б — VE-анализ группы A (Claude)

Запускается сразу после ABC-анализа.

При большом числе позиций группы A (> 10) — чанкинг по 5–8 позиций, результаты объединяются.

## Промпт Claude

**Вход:** JSON позиций группы A

```
Ты — опытный инженер-сметчик со знанием ГЭСН-2017/ФСНБ-2022.

Тебе переданы позиции группы А из сметы — наиболее дорогостоящие виды работ (около 80% суммы).

Для каждой позиции найди возможности снизить НАШУ СЕБЕСТОИМОСТЬ при том же конечном результате для заказчика.

Два направления анализа:

1. ТЕХНОЛОГИЧЕСКАЯ ЗАМЕНА — та же работа, но другим способом.
   Более производительным, механизированным или с меньшими трудозатратами.
   Примеры:
   - Ручная штукатурка → Механизированная (от 900 м²)
   - Мокрая стяжка → Механизированная полусухая (от 300 м²)
   - Ручная окраска → Безвоздушное распыление (большие ровные поверхности)
   - Ручная засыпка грунта → Механизированная (от 50 м³)

2. ОПТИМИЗАЦИЯ ОПЕРАЦИЙ — меньше вспомогательных операций за счёт технологической синергии.
   Примеры:
   - Механизированная штукатурка даёт более гладкую поверхность → 1 слой шпаклёвки вместо 2
   - Однослойные покрытия совмещают грунтование и нанесение в один проход

Для каждого предложения обязательно:
- Укажи расценку ФСНБ/ГЭСН для новой технологии
- Посчитай новую стоимость позиции и экономию в рублях и процентах
- Учти все дополнительные затраты (аренда оборудования и т.п.)
- Проверь 5 критериев перед тем, как предлагать:
  1. Конечный результат для заказчика не изменится
  2. Новая технология соответствует ГОСТ/СП, расценка есть в ФСНБ/ГЭСН
  3. ТЗ тендера не прописывает технологию жёстко (если ТЗ не передан — указать «требует проверки»)
  4. Технология реализуема: нужное оборудование и компетенция есть или доступны
  5. Экономия > 5% от стоимости позиции с учётом всех доп. затрат

Отклони предложение, если хотя бы один критерий не пройден.
Не предлагай замены, в которых не уверен — лучше пропустить, чем ошибиться.

Верни JSON:
{
  "proposals": [
    {
      "row_id": "id строки",
      "position_name": "Наименование работы",
      "position_cost": число,
      "optimization_type": "technology" | "operations",
      "title": "Краткое название предложения (Было → Стало)",
      "what_changes": "Что именно меняется в способе выполнения",
      "what_stays": "Что остаётся неизменным для заказчика",
      "fsnb_code_alternative": "Код расценки ФСНБ/ГЭСН для новой технологии",
      "cost_before": число,
      "cost_after": число,
      "savings_rub": число,
      "savings_pct": число,
      "additional_benefit": "Дополнительная выгода или null",
      "conditions": "Условие применения и выполняется ли оно по данной смете",
      "risks": "Риски или null",
      "filter_passed": true | false,
      "filter_notes": "Что требует проверки или null"
    }
  ],
  "summary": "Найдено X предложений, потенциальная экономия Y руб. (Z% суммы группы А)"
}
```

```

```

Состояния: `inactive` (до фиксации Версии 2) | `active` | `running` (spinner) | `done` (галочка)

### Последовательность отображения

1. Кнопка нажата → мгновенно появляется ABC-разбивка (этап А, код)

3. Пока Claude думает — ABC-разбивка уже видна, под ней spinner «Анализируем группу А…»

### Действия с предложением

- **[Принять −248 000 ₽]** — строка обновляется в гриде: новая цена (зелёная), в поле `optimization_note` записывается что изменено. Счётчик экономии обновляется.
- **[Отклонить]** — предложение отклонено, строка без изменений.
- Оба действия можно отменить (toggle).

### Кнопка фиксации версии

| Состояние | Лейбл кнопки |
|---|---|
| Анализ ещё не запущен | Неактивна |
| Анализ завершён, принято 0 | «Зафиксировать Версию 3 без изменений» |
| Принято ≥ 1 | «Зафиксировать как Версию 3» |

**Версия 3 обязательна.** Без её создания кнопка Шага 4 остаётся неактивной.

При принятии предложения в строке сметы обновляются:
- `price_work` → пересчитанная по новой расценке
- `cost` → пересчитывается автоматически
- `optimization_note` → «Технол. замена: ручная → механизированная. −248 000 ₽»

## Решения по UX

1. **Группа B в Шаге 3** — не анализируется. Только Группа A. Группа B переходит в Шаг 4.

2. **Дополнительная выгода от технологии** — применяется автоматически при принятии основного предложения. В панели изменений явно показывается что именно изменилось:
   ```
   ✓ Принято: Ручная штукатурка → Механизированная  −248 000 ₽
     + Автоматически: 2-й слой шпаклёвки удалён  −85 000 ₽
     Итого по предложению: −333 000 ₽
   ```

3. **Предложения без проверки ТЗ** — скрыты за спойлером, аналогично `confidence: low` в Шаге 2:
   ```
   Ещё 1 предложение требует проверки ТЗ  ▶ Показать
   ```
   При раскрытии — явная пометка «⚠ Проверьте ТЗ тендера перед принятием».
