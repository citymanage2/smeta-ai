# Spec — уведомление о восстановлении баланса API

Дата: 2026-07-28
Research: `thoughts/research/2026-07-28-balance-restored-notification.md`

## Проблема

Когда баланс Anthropic исчерпан, задачи уходят в `paused` и возобновляются
автоматически раз в 10 минут. Но возобновление молчаливое: пользователь, пополнив
счёт, видит всё тот же застывший текст «⏸ На паузе: баланс API исчерпан» и не может
понять, дошло ли пополнение, работает ли поллер и что вообще происходит.

## Цель

Пользователь узнаёт о смене состояния, не заходя в админку и не спрашивая
разработчика:
- пополнение дошло → уведомление «Баланс API пополнен, возобновлены задачи: N»;
- пополнение не дошло → на карточке задачи видно время последней проверки и ответ API.

## Scope

1. `resume_poller` перед возобновлением делает пробный вызов API (`api_ping`).
2. При неуспехе задачи не перезапускаются; их `progress_message` обновляется
   текстом с временем проверки и причиной.
3. При успехе задачи возобновляются (как сейчас) и в БД пишется системное событие
   `balance_restored` со списком id возобновлённых задач.
4. `GET /notifications/system?since_id=N` отдаёт новые события с учётом RBAC.
5. Фронт опрашивает эндпоинт и показывает toast + звук + браузерное уведомление.

## Non-Goals

- Push/WebSocket/SSE — поллинга достаточно.
- E-mail и Telegram-уведомления.
- Уведомление в момент наступления паузы (уже есть тост в `useGlobalTaskPoller`).
- Изменение интервала поллера (остаётся 10 минут).
- Общая лента уведомлений в UI (история, «колокольчик») — только всплывающее событие.

## Acceptance Criteria

### Backend

- **AC1.** Нет `paused`-задач → `api_ping` не вызывается вообще (нулевая стоимость).
- **AC2.** Есть `paused` и ping НЕ `ok` → ни одна задача не меняет статус, job не
  создаётся, событие не пишется. Возврат `[]`.
- **AC3.** Есть `paused` и ping НЕ `ok` → у каждой paused-задачи обновлён
  `progress_message`: содержит время проверки (МСК) и причину — «баланс всё ещё
  исчерпан» при `is_balance_error`, иначе «API недоступен: <код>». `progress_log`
  не растёт.
- **AC4.** Ping `ok` → поведение прежнее: `paused→pending` + durable-job
  `task.process`; задачи с отправленной batch-пачкой → `processing` без job.
- **AC5.** Ping `ok` и захвачена ≥1 задача → создана строка `system_events` с
  `kind='balance_restored'` и `payload.resumed_task_ids` = список захваченных id
  (включая batch-задачи, вернувшиеся в `processing`).
- **AC6.** Ping `ok`, но захватить нечего (все перехвачены параллельно) → событие
  не пишется.
- **AC7.** `GET /notifications/system?since_id=N` возвращает события с `id > N`,
  по возрастанию id, максимум 20. Без авторизации — 401.
- **AC8.** Событие видно менеджеру (admin/head_of_sales) всегда; ПМ — только если
  среди возобновлённых есть его или общая задача. Список `tasks` в ответе
  отфильтрован по тем же правилам (`visibility_filter`).
- **AC9.** Миграция `040` создаёт таблицу с `IF NOT EXISTS`, повторный прогон
  безопасен.

### Frontend

- **AC10.** При появлении нового события показывается toast «✓ Баланс API пополнен»
  с описанием «Возобновлены задачи: N» и перечислением до 3 названий.
- **AC11.** Первый заход (курсора в `localStorage` нет) → тостов нет, курсор
  выставляется на максимальный id.
- **AC12.** Одно и то же событие не показывается дважды (курсор сохраняется).
- **AC13.** Скрытая вкладка не опрашивает сервер; при возврате на вкладку — опрос
  сразу, без ожидания интервала.
- **AC14.** Ошибка запроса не ломает приложение и не мешает поллеру задач.

## Constraints

- PostgreSQL 16 в проде, SQLite в тестах → JSONB через `with_variant` (как в `job.py`).
- Изменение `models/` ⇒ обязательная миграция с `IF NOT EXISTS` (CLAUDE.md).
- Существующие тесты `test_resume_poller.py` не должны ходить в сеть ⇒ инъекция
  `pinger`, как уже сделано для `runner`.
- Тексты — на русском, стиль как в существующих тостах (`utils/notify.ts`).
