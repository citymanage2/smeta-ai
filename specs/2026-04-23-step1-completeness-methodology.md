# Методология: Шаг 1 — Проверка полноты и соответствия объёмов

**Дата:** 2026-04-23  
**Статус:** Согласовано  
**Контекст:** Первый шаг модуля оптимизации тендерного предложения. Работает с нашей сметой себестоимости (EstimateVersion, version_label="original").

---

## Цель

Убедиться, что наша смета себестоимости:
1. Покрывает всё, что требует заказчик (по его файлам)
2. Содержит логически согласованные объёмы
3. Соответствует нормативным требованиям ГЭСН/ФСНБ по составу материалов

---

## Три подшага

### Подшаг 1.1 — Сверка с исходными данными заказчика

**Вопрос:** всё ли из того, что представил заказчик, учтено в нашей смете?

#### Условие активности кнопки

- Файл заказчика **загружен** → кнопка активна
- Файл заказчика **не загружен** → кнопка неактивна. Отображается сообщение:
  > «Файл заказчика не загружен. Если хотите проверить соответствие сметы с файлом заказчика — загрузите файл заказчика в поле.»
  
  При этом подшаг 1.2 остаётся активным.

#### Логика в зависимости от типа файла заказчика

**Тип: Смета**

Claude сравнивает позиции семантически — по смыслу, не по точному тексту наименований.

Результат — два списка:
- **Не учтено у нас** — позиции из сметы заказчика, которых нет в нашей смете (или есть, но объём существенно ниже)
- **Есть у нас, нет у заказчика** — позиции нашей сметы сверх сметы заказчика → автоматически передаются как «подозрительные» в список Шага 2

Промпт (вход: JSON нашей сметы + JSON сметы заказчика):
```
Ты — опытный сметчик. Тебе переданы две сметы: наша смета себестоимости и смета заказчика.

Сравни позиции по смыслу (наименования могут отличаться).

Найди:
1. Позиции из сметы заказчика, которых НЕТ в нашей смете или объём которых у нас существенно ниже.
2. Позиции нашей сметы, которых НЕТ в смете заказчика (возможно лишние).

Верни JSON:
{
  "missing_in_ours": [
    {
      "client_name": "Наименование у заказчика",
      "client_unit": "ед. изм.",
      "client_qty": число или null,
      "reason": "Почему считаем отсутствующей"
    }
  ],
  "extra_in_ours": [
    {
      "our_row_id": "id строки нашей сметы",
      "our_name": "Наименование у нас",
      "reason": "Почему нет у заказчика"
    }
  ],
  "summary": "Краткое резюме сверки"
}
```

---

**Тип: Проект**

Claude извлекает из проекта перечень работ, которые должны быть выполнены по результату — даже если они не прописаны явно в спецификациях. Сравнивает с нашей сметой.

Промпт (вход: файл проекта + JSON нашей сметы):
```
Ты — опытный инженер-сметчик. Тебе переданы проектная документация и наша смета.

Проанализируй проект. Определи все виды работ, которые должны быть выполнены для достижения результата проекта — включая работы, логически вытекающие из проекта, даже если они не прописаны в спецификациях (подготовительные, демонтажные, сопутствующие).

Проверь, все ли эти работы присутствуют в нашей смете.

Верни JSON:
{
  "missing_in_ours": [
    {
      "name": "Наименование работы",
      "reason": "Почему требуется по проекту",
      "project_reference": "Раздел/лист проекта"
    }
  ],
  "extra_in_ours": [
    {
      "our_row_id": "id строки",
      "our_name": "Наименование",
      "reason": "Почему не следует из проекта"
    }
  ],
  "summary": "Краткое резюме"
}
```

---

**Тип: ТЗ**

Claude анализирует требования ТЗ, определяет какой состав работ нормативно необходим для их выполнения, сравнивает с нашей сметой.

Промпт (вход: файл ТЗ + JSON нашей сметы):
```
Ты — опытный инженер-сметчик со знанием ГЭСН-2017/ФСНБ-2022.

Тебе переданы техническое задание заказчика и наша смета.

Проанализируй ТЗ. Определи, какой состав работ и материалов нормативно необходим для выполнения требований ТЗ (по ГЭСН, СП, ГОСТ).

Проверь, все ли эти работы и материалы присутствуют в нашей смете.

Верни JSON:
{
  "missing_in_ours": [
    {
      "name": "Наименование работы/материала",
      "reason": "Почему требуется для выполнения ТЗ",
      "norm_reference": "ГЭСН/СП/ГОСТ код или раздел"
    }
  ],
  "extra_in_ours": [
    {
      "our_row_id": "id строки",
      "our_name": "Наименование",
      "reason": "Почему не следует из ТЗ"
    }
  ],
  "summary": "Краткое резюме"
}
```

**Тип: Другое**

Claude анализирует документ в свободном режиме: пытается определить требования заказчика и сверить с нашей сметой. Если документ не содержит требований к работам — сообщает об этом.

---

#### Связь с Шагом 2

Все позиции из поля `extra_in_ours` (есть у нас, нет у заказчика) **автоматически добавляются в список «подозрительных»** для Шага 2 — «Проверка на лишние позиции». Пользователь увидит их там с пометкой «Отсутствует у заказчика».

### Подшаг 1.2 — Проверка соответствия объёмов

**Вопрос:** логичны ли объёмы внутри сметы относительно друг друга?

Работает **независимо от наличия файла заказчика**. Анализирует только нашу смету.

Claude ищет внутренние противоречия объёмов — без обращения к нормативам:
- Объём грунтовки < объёму окрашиваемой поверхности
- Объём раствора непропорционален площади штукатурки
- Объём арматуры непропорционален объёму бетона
- Объём утеплителя не соответствует площади утепления
- Объём монтажа конструкций не совпадает с объёмом поставки материала

Промпт (вход: JSON нашей сметы):
```
Ты — опытный сметчик. Проанализируй смету на предмет логических несоответствий объёмов.

Ищи пары и группы связанных позиций, где объёмы противоречат друг другу (без обращения к нормативам — только внутренняя логика сметы).

Примеры несоответствий:
- Объём грунтовки должен быть ≥ объёму окраски
- Объём раствора для штукатурки пропорционален площади × толщина слоя
- Количество материала для монтажа должно соответствовать количеству монтируемых единиц

Для каждого несоответствия посчитай, какой объём ожидается исходя из других позиций сметы.

Верни JSON:
{
  "volume_issues": [
    {
      "row_id": "id строки с несоответствием",
      "name": "Наименование",
      "current_qty": число,
      "expected_qty": число,
      "expected_range": "от X до Y" или null,
      "related_row_ids": ["id связанных строк"],
      "reason": "Объяснение несоответствия с расчётом"
    }
  ],
  "summary": "Краткое резюме"
}
```

### Подшаг 1.3 — Нормативная проверка по ГЭСН

**Вопрос:** все ли материалы учтены для каждой работы по нормативам ГЭСН/ФСНБ?

Самый глубокий подшаг. Для каждой работы из сметы Claude проверяет:
- Все ли нормативно необходимые материалы присутствуют
- Соответствуют ли объёмы расходным нормам ГЭСН

При больших сметах (>50 позиций работ) — чанкинг по 20–30 работ, результаты объединяются.

Промпт (вход: JSON нашей сметы — только строки типа "work" с их материалами):
```
Ты — опытный инженер-сметчик со знанием ГЭСН-2017/ФСНБ-2022, ФЕР/ТЕР.

Для каждой работы в перечне проверь:
1. Все ли нормативно необходимые материалы учтены (по ГЭСН/ФСНБ для данного вида работ).
2. Соответствуют ли объёмы материалов расходным нормам ГЭСН, исходя из объёма работы.

Добавляй в результат только реальные несоответствия. Не добавляй позиции, которые корректны.

Верни JSON:
{
  "missing_materials": [
    {
      "work_row_id": "id работы",
      "work_name": "Наименование работы",
      "material_name": "Наименование недостающего материала",
      "unit": "ед. изм.",
      "recommended_qty": число или null,
      "norm_reference": "ГЭСН код и наименование",
      "reason": "Почему необходим"
    }
  ],
  "volume_corrections": [
    {
      "row_id": "id материала",
      "name": "Наименование материала",
      "current_qty": число,
      "recommended_qty": число,
      "norm_reference": "ГЭСН код",
      "reason": "Расчёт по норме"
    }
  ],
  "summary": "Краткое резюме"
}
```

## UX: рабочая область Шага 1

### Кнопки тулбара

```
[1.1 Сверка с заказчиком]  →  [1.2 Проверка объёмов]  →  [1.3 Проверка по ГЭСН]
```

Состояния каждой кнопки: `inactive` | `active` | `running` (spinner) | `done` (галочка)

Правила разблокировки:
- 1.1 → активна если загружен файл заказчика; неактивна с сообщением если нет
- 1.2 → всегда активна (независимо от 1.1)
- 1.3 → активна после запуска 1.2 (или 1.1 если 1.2 пропущена)

### Накопление результатов

Результаты подшагов накапливаются в панели под тулбаром. Панель разделена на секции:

```
┌─ Результаты Шага 1 ────────────────────────────────────────┐
│                                                             │
│  [1.1] Сверка с заказчиком                     ▼           │
│  ├─ Не учтено у нас: 3 позиции                             │
│  │   • Демонтаж старого покрытия, 120 м² [Добавить]        │
│  │   • Грунтовка по бетону, 80 м²         [Добавить]       │
│  │   • ...                                                  │
│  └─ Есть у нас, нет у заказчика: 2 позиции → передано в ш.2│
│                                                             │
│  [1.2] Проверка объёмов                        ▼           │
│  ├─ Несоответствий: 1                                       │
│  │   • Грунтовка: у нас 50 м², ожидается ≥120 м² [Испр.]   │
│  │                                                          │
│  [1.3] Проверка по ГЭСН                        (не запущен)│
│                                                             │
│         [Зафиксировать как Версию 1]                       │
└─────────────────────────────────────────────────────────────┘
```

### Кнопка версии

- До первого сохранения: **"Зафиксировать как Версию 1"**
- После сохранения: **"Обновить Версию 1"** (появляется если запущен ещё один подшаг)
- Откат: удаляет Версию 1, возвращает к исходной смете. Запись в TaskHistory.

Версия фиксирует **только принятые пользователем изменения** (нажатые "Добавить" / "Исправить"), а не все предложения подшагов.
